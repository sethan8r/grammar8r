# Grammar8r — Правила разработки

## Рабочий процесс

**Код без явной команды не писать.**

Порядок работы:
1. Пользователь даёт ТЗ или задачу.
2. Claude изучает существующий код, задаёт уточняющие вопросы, описывает план в чате.
3. Пользователь уточняет, корректирует, даёт добро.
4. Только после явной команды ("пиши", "давай", "начинай") — пишется код.

То же самое для правок: сначала описать что и как изменится, потом ждать подтверждения.

**Язык общения — русский.** Все описания, комментарии, пояснения и сводки в сессии — на
русском языке. В том числе краткие описания скриптов перед запуском (см. ниже).

### Запуск диагностических/проверочных скриптов (read-only)

Для одноразовых скриптов-сверок (посчитать, сравнить, проверить — ничего не меняющих в репо)
не нужно отдельным сообщением спрашивать "запускать?" и ждать ответа, прерывая поток. Достаточно
**кратко описать прямо в сообщении что и зачем** (что скрипт делает, что покажет) и сразу вызывать
инструмент — пользователь сам разрешит/отклонит запуск через permission-prompt в моменте, без
дополнительного раунда переписки. Это не относится к изменению файлов / коду по ТЗ — там обычное
правило (см. выше): описать → дождаться "пиши"/"давай".

### Закреплённые рабочие привычки (фидбек пользователя)

Постоянные договорённости о том, КАК Claude работает над этим проектом (раньше жили только в
локальной памяти — продублированы здесь, чтобы переживали смену машины/сессии):

- **Сборку по умолчанию Claude НЕ запускает** — пользователь сразу заливает приложение на телефон
  кнопкой в Android Studio: ошибку компиляции присылает, иначе сразу проверяет на устройстве (одна
  сборка вместо двух). Сам компилирую/гоняю тесты, только когда это реально экономит время:
  крупные структурные правки (перенос кода между модулями, Gradle-конфиги), где ошибки пойдут пачкой
  и пинг-понг выйдет дольше; тесты логики ядра (`gradlew :grammar-core:test`); пересборка контента
  (`check.py` / `json_to_db.py`) или явная просьба. Запуск подтверждается через permission-prompt.
  Установка на устройство — всегда пользователь.
- **История git — ценность (полгода работы).** Никаких команд, переписывающих историю: `rebase`,
  `commit --amend`, `reset --hard`, `push --force`. Крупные переделки — в отдельной ветке, в `master`
  только после проверки пользователем. Перенос файлов — `git mv` отдельным коммитом без правок
  внутри (так git связывает старый и новый путь и `git log --follow` показывает историю).
- **Файлы репо (теорию, планы, код) меняю только через Edit/Write** — чтобы пользователь видел каждую
  правку в IDE. Скриптами — только чтение, проверки и сборка сидов, не замена текста в файлах.
- **Python на Windows — через `py`** (не `python`). Сложный одноразовый скрипт писать в файл, прогнать,
  потом удалить — не пихать многострочник в `-c`.
- **Перед написанием микротемы — ВСЕГДА читать шапку её ТЕМЫ в `grammar8r_plan.md`** (блок строк
  🎯/⚠️/💬/🔤 под узлом темы, над списком микротем), а не только ветку самой микротемы. Там живут
  правила, действующие на всю тему и часто отменяющие общий канон: что тема НЕ переучивает, красная
  нить, обязательные элементы каждой микротемы (напр. диалоги в «Погоде»), в какую категорию слив и
  какие исключения по сливу (производные можно, потолок 5 слов можно превысить). Пропустил шапку —
  написал микротему не по ТЗ.
- **Собираю или правлю ДЕРЕВО темы — сначала прогоняю инвентарь ролей** (`tasks/theory_content_guide.md`
  → §3 «ДЕРЕВО ТЕМЫ — ПРОГНАТЬ ИНВЕНТАРЬ РОЛЕЙ ФОРМЫ»): выписать ВСЕ роли изучаемой формы/слова в
  языке и каждой назначить исход (разбираем здесь · строкой на узнавание · чужой дом с проверкой,
  что дом есть в плане). Собирать дерево от долгов курса и списков сочетаний — НЕДОСТАТОЧНО: так
  из «Герундия» дважды выпали причастный оборот и принцип «сказуемое одно, второй глагол меняет
  форму». Просьба «обнови/напиши нормально дерево» = прогнать инвентарь целиком, а не причесать
  формулировки веток.
- **Самопроверка микротемы — ПОЛНЫЙ проход по чек-листу, а не грепы и не «по памяти».** Когда
  пользователь просит «проверь себя по правилам брифа и гайда» (или сразу после написания
  микротемы), порядок обязательный:
  1. **Перечитать весь написанный блок инструментом Read** — от `## Microtopic` до Sync, целиком.
     По памяти не проверять: память видит то, что задумано, а не то, что написано.
  2. **Пройти `theory_content_guide.md` §9 и §7 ПУНКТ ЗА ПУНКТОМ** плюс «❌ Антипаттерны»
     `exercise_templates.md` — по каждой карточке отдельно, ни одного пункта не пропуская.
  3. **Отдельно — то, что грепом не ловится:**
     - полнота (§3): формы конструкции · инвентарь слота · пять чужих фраз из пройденного;
     - каждое упражнение глазами пользователя: однозначен ли ответ, нельзя ли из чипов/вариантов
       собрать ДРУГОЕ верное предложение, не копирует ли теорию карточки, не подсказывает ли правило;
     - каждый AI-промт по блокам 1а/1б/задание/инвентарь/оценка и правилу «ИИ проверяет только то,
       что объяснила ЭТА карточка» (ничего из следующих карточек);
     - переводы: дословный и живой различаются, иначе второй лишний (§3 гайда).
  4. **В отчёте — по пунктам:** что проверено, что найдено, что исправлено. Грепы (бэктики у ✓/✗,
     ключевые слова плашек в подзаголовках, сроки обучения) — дополнение, а не замена проверки.
  Поймано 23.09.2026 на МТ258: «проверка» из одних грепов пропустила дыру в полноте (отрицание,
  `being built`, `who is` + прилагательное), WordArrangement с двумя верными сборками из дистракторов
  и строку промта про непройденную карточку.
- **«Прогнать чек» / `check.py` прошёл ALL GREEN → СРАЗУ отметить микротему `✅` в `grammar8r_plan.md`**
  тем же заходом, без отдельной просьбы. Сама фраза «прогнать чек» = сигнал ставить ✅.
- **Архитектурные/спорные развилки — обсуждать прозой** (рекомендация + trade-off'ы + где сомнение),
  а НЕ через `AskUserQuestion` с готовыми вариантами. Multiple-choice — только для простых развилок.
- **Где что записывать:** правила написания контента → `tasks/theory_content_guide.md` /
  `tasks/phases/phase1/theory_content_brief.md`;
  рабочие привычки Claude → этот раздел `CLAUDE.md`; `grammar8r_plan.md` — это СТРУКТУРА (темы/карточки),
  правилами и канонами его НЕ засорять. TODO-пометки вешать на ещё НЕ написанный контент, не на готовый.
  Не тратить ходы на косметический порядок записей в планах/логах.

### Фиксация карточек в `grammar8r_plan.md`

При написании карточек микротемы — сразу добавлять их названия и краткое содержание (1–2 предложения
на карточку: что объясняет, на чём строится / что нового даёт) прямо в `grammar8r_plan.md`, под
соответствующей микротемой. Это не дублирование теории — а памятка для себя и пользователя, чтобы
не путаться при возврате к плану позже и видеть с одного взгляда, что уже покрыто и чем отличается
от соседних карточек/микротем (особенно важно когда темы пересекаются по содержанию, как
"Как думает английский язык" и "Word Order: SVO" из "Основ").

### ⚠️ КРИТИЧНО: консистентность ENUM-ов между клиентом и внешними системами

При любом изменении этих ENUM-ов (`db_schema.md`) — обязательно проверять смежные системы:

**`AiConfigProfile`** — больше не клиентский enum. Хранится только на сервере в таблице `ai_exercise_prompts`. При добавлении нового профиля — менять только серверный конфиг, клиент не трогать.

**`AiExerciseWordsSource`** (источники слов из Words8r) →
- При добавлении нового варианта: убедиться что такая категория существует или появится в Words8r
- Категории в Words8r создаются по ходу курса — когда пользователь синкает слова из микротем (например "Informal English" появляется после прохождения темы "Разговорный английский")
- Новый вариант в ENUM без реальной категории в Words8r = заблокированные упражнения у всех пользователей
- Обновлять: `db_schema.md` + проверить `words8r_plan.md` что категория там запланирована

**`AiExerciseInputMode`** (типы ввода ответа) →
- При добавлении нового варианта: UI-компонент AI-экрана должен уметь его рендерить
- Если компонент не обрабатывает новый вариант → краш или пустой экран
- Обновлять: `db_schema.md` + AI-экран Composable

## Тема и визуальный стиль

> ⚠️ **ВАЖНО: дизайн может смениться полностью.**
> Grammar8r стартует с дизайном как в Words8r, но в будущем может получить новый визуальный язык.
> Всё что связано с дизайном **обязано быть изолировано**:
> - цвета — только через `Color.kt` и `MaterialTheme`, никаких хардкод-значений в Composable
> - отступы и размеры — только через именованные константы или токены, не `16.dp` прямо в коде
> - переиспользуемые элементы — вынесены в `ui/components/`, не дублируются по экранам
> - Composable-экраны — только UI, никакой логики, чтобы при смене дизайна трогать только `ui/`
>
> Смена дизайна должна сводиться к правке `Color.kt`, `Theme.kt` и компонентов — и не затрагивать ViewModel, UseCase, Repository.

**Цвета, скругления, отступы — 1 в 1 как в Words8r** (до смены дизайна).

Эталон только для визуала: `E:\AndroidProjects\SethanWords\app\src\main\java\dev\sethan8r\sethanwords\ui\theme\`

Words8r как референс — **только тема**. Архитектура и структура кода там не образцовая, не копировать. Делать надо по заветам прода и бест практис, как бы этот код выглядил нга проде по структуре

## Архитектура и структура кода

### Принципы

- **Каждый класс — одна ответственность.** ViewModel не знает про Room напрямую, Repository не знает про UI.
- **Никакой смешанной логики.** Бизнес-логика в UseCase/Repository, UI-логика в ViewModel, отображение в Composable.
- **Никакого дублирования.** Если что-то используется дважды — вынеси в общий компонент или утилиту.
- **Структура сразу как на проде.** Не "потом порефакторим" — сразу правильно.
- **Пакеты всегда сгруппированы по смыслу — наводить красоту по ходу, а не «потом».** Не сваливать
  файлы плоско в один пакет. Группировать по бизнес-контексту (`theory/`, `exercise/`, `auth/`,
  `subscription/` …) и зеркалить раскладку между слоями (`data/.../entity/{theory,exercise,word}` ↔
  `grammar-core` → `model/{theory,exercise,…}`). Как только в пакете становится тесно (ориентир ~8–10 файлов)
  или вырисовывается явный кластер — сразу разносить по подпакетам. Однофайловый подпакет под
  отдельный контекст — нормально (он растёт). Исключение: общий UI-kit в `ui/components/` держим
  плоским, пока не сложится кластер (тогда — подпапка фичи, напр. `ui/components/exercise/`).

### Слои

Доменный слой живёт в отдельном модуле `grammar-core` (почему — «Модули проекта» ниже),
остальные — в Android-модуле:

```
grammar-core/src/main/kotlin/dev/sethan8r/grammar/core/
  model/       ← доменные модели
  repository/  ← интерфейсы репозиториев
  usecase/     ← бизнес-логика

grammar-app-android/src/main/java/dev/sethan8r/grammar/app/
  data/
    local/       ← Room DB, DAO, Entity
    remote/      ← API-клиент
    mapper/      ← Entity/JSON → доменные модели
    repository/  ← реализации интерфейсов из grammar-core
  di/          ← Hilt-модули
  ui/
    theme/       ← Color.kt, Theme.kt, Type.kt
    components/  ← переиспользуемые Composable
    screens/
      <feature>/
        <Feature>Screen.kt
        <Feature>ViewModel.kt
```

### Правила

- Composable получает только UI-state и коллбеки, никаких ViewModel внутри composable напрямую (только на уровне экрана).
- ViewModel не импортирует ничего из `data/` напрямую — только через интерфейсы и юзкейсы `grammar-core`.
- Зависимости через DI (Hilt).
- Модели не текут между слоями: Entity → доменная модель → UI-state — отдельные классы.

### Модули проекта

```
grammar-shared       ← КОНТРАКТ API клиент ↔ сервер: DTO, enum-ы. Чистый Kotlin/JVM
grammar-core         ← ЯДРО клиента: доменные модели, интерфейсы репозиториев, юзкейсы. Kotlin/JVM, ноль Android
grammar-app-android  ← Android-приложение: Compose UI, ViewModel, Room, Hilt, навигация, assets/content.db
grammar-app-ios      ← будущее iOS-приложение (Xcode + SwiftUI). Сейчас только README, НЕ Gradle-модуль
grammar-server       ← Spring Boot-сервер на JAVA (Фаза 4; решение 02.07.2026). В папке пока пустой
                       Ktor-шаблон — заменяется на Spring Boot при старте Фазы 4
```

Направление зависимостей (нарушать нельзя):

```
            grammar-shared
             ↑          ↑
      grammar-core   grammar-server
        ↑        ↑
    android     ios (позже, через XCFramework)
```

- `grammar-core → grammar-shared` через `api`: типы контракта (`SubscriptionTier`,
  `ProgressEventType`) входят в публичные сигнатуры ядра.
- `grammar-server` **никогда** не зависит от `grammar-core`: ранжирование поиска, проверка ответов,
  правила прохождения — клиентская логика, серверный jar её тащить не должен. Поэтому `core` и
  `shared` — два модуля, а не один.
- Пакет и `applicationId` Android-модуля — `dev.sethan8r.grammar.app` — **не менять**: у
  `applicationId` другое значение = на телефоне это другое приложение, прогресс не подхватится.

#### Зачем ядро вынесено — будущая iOS-версия

Возможна iOS-версия с той же логикой 1-в-1 и нативным UI. Прод-стандарт для такого (Cash App,
Netflix, McDonald's): **общее Kotlin-ядро с логикой + нативный UI на каждой платформе**. Kotlin/Native
компилирует ядро в нативный фреймворк, Xcode подключает его как обычную библиотеку, Swift вызывает
функции ядра напрямую. Всё, что лежит в `grammar-core`, на iOS достаётся бесплатно и работает
одинаково. Всё, что застряло в Android-модуле, придётся писать второй раз на Swift — и две копии
неизбежно разъедутся (Правило №0 в масштабе двух платформ).

Сейчас `grammar-core` — обычный JVM-модуль: Kotlin Multiplatform под Windows не проверить (iOS
собирается только на Mac), а ежедневная цена у него заметная. Перевод на KMP — в день старта iOS,
условия и порядок — `tasks/ios_portability_plan.md`. Писать код сейчас надо так, чтобы этот перевод
был сменой плагина, а не переписыванием.

#### Где что живёт — правило размещения

| Что | Куда |
|---|---|
| Доменные модели и доменные enum-ы | `grammar-core` → `model/` |
| Интерфейсы репозиториев | `grammar-core` → `repository/` |
| Любая логика: алгоритмы, проверка ответов, подсчёт прогресса, ранжирование, правила лимитов | `grammar-core` → `usecase/` |
| Тесты этой логики | `grammar-core/src/test` |
| Реализации репозиториев: Room (Entity, DAO), мапперы, сеть, DataStore | `grammar-app-android` → `data/` |
| Hilt-модули (`@Module`, `@Binds`, `@Provides`) | `grammar-app-android` → `di/` |
| ViewModel, Composable, навигация, `strings.xml`, ресурсы | `grammar-app-android` → `ui/` |
| DTO и enum-ы API | `grammar-shared` |

**Проверка при создании любого класса: «тестируем без Android?» → его место в `grammar-core`.**
Сомневаешься — тоже в ядро. ViewModel держит только UI-state и реакции на действия: каждая строчка
логики во ViewModel — это будущий дубль на Swift.

#### Ограничения ядра — переносимость на iOS

- **`android.*` / `androidx.*`** — в classpath ядра их нет, такой код просто не скомпилируется.
- **`java.*` / `javax.*`** (кроме `javax.inject`) — на JVM доступны, поэтому их ловит Gradle-проверка
  `checkCorePortability`: она идёт перед компиляцией ядра и валит сборку со списком строк-нарушителей.
- **Автоматически НЕ ловится, следить самому:** JVM-only функции самого Kotlin — `String.format` /
  `"%d".format(…)`, `@Synchronized`, `Thread`, `System.*`. Замены: строковые шаблоны, корутины и `Mutex`.
- **Даты:** в ядре — `kotlin.time` (`Instant`, `Duration`, `Clock`); календарные даты и часовые пояса —
  `kotlinx-datetime` (подключить, когда понадобятся). `java.time` — только в Android-модуле.
- **Публичный API ядра — простой:** data-классы, enum-ы, функции, `Flow`, `suspend`. В Swift он
  приходит через Objective-C-прослойку: дженерики частично схлопываются, у `sealed`-иерархий нет
  исчерпывающего `switch`. `sealed` использовать можно (они уже есть), но не усложнять сигнатуры без
  нужды. Внутри реализации ядра ограничений нет.
- **DI:** `@Inject constructor` на юзкейсах разрешён — Hilt приложения сам генерирует для них фабрики,
  ручная проводка не нужна. Hilt-модули в ядро не кладутся. При переводе на KMP аннотации придётся
  снять — это осознанный отложенный долг (см. `tasks/ios_portability_plan.md`).
- **Граница модуля в Kotlin:** smart cast не работает для публичных свойств классов из другого модуля
  (`if (line.text != null) use(line.text)` не скомпилируется в Android-модуле). Решение — прочитать
  в локальную `val`: `val text = line.text; if (text != null) use(text)`.
- **Тесты ядра:** `gradlew :grammar-core:test`. Тестовую `content.db` ядро собирает само, тем же
  `json_to_db.py`, в свой `build/` — от задач Android-модуля не зависит.

#### `grammar-app-ios`

Место под Xcode-проект: в `settings.gradle.kts` её нет, Gradle её не собирает. Связь односторонняя:
Xcode подключает фреймворк, собранный из `grammar-core`. Пока iOS не стартовал — в папке только
README, ничего туда не класть.

#### `grammar-shared`

`grammar-shared` — модуль-библиотека, который подключается и в клиенте, и в
`grammar-server` через `implementation(project(":grammar-shared"))`. При сборке его классы
компилируются один раз и упаковываются в оба артефакта (APK и серверный jar). Общий у них
только исходник — это гарантирует, что клиент и сервер сериализуют/десериализуют один и
тот же JSON и не могут разъехаться: правка контракта ломает компиляцию обеих сторон сразу,
а не сериализацию в проде.

**Что в нём ЛЕЖИТ (и только это):**
- `@Serializable` DTO запросов/ответов API: AI-упражнения, авторизация (JWT), подписка,
  синк прогресса, лимиты, modal-баннеры;
- enum-ы контракта: тир подписки, `AiExerciseInputMode`, коды ошибок API и т.п.

**Что в нём лежать ЗАПРЕЩЕНО:** Room-сущности, UI-модели, доменные модели и бизнес-логика
(их место — `grammar-core`), любые Android-зависимости. Модуль остаётся чистым Kotlin/JVM с теми же
ограничениями переносимости, что и ядро: через `grammar-core` он попадёт и в iOS-приложение. Принцип
«ну это же и там и там используется» — не основание класть в shared: только контракт API.

**Роль по фазам:** в Фазе 1 при создании серверных заглушек (`AuthRepository`,
`EntitlementsProvider`, `AiExerciseRepository`) их DTO кладутся сразу в shared — тогда в
Фазе 4 сервер реализует уже готовый контракт, ничего не переносится.

## Навигация и кнопка «Назад»

### Правило: никаких BackHandler в экранах

`BackHandler` — костыль, который нужен только когда подэкраны рендерятся через boolean-флаги внутри одного Composable (антипаттерн из Words8r). В Grammar8r так не делаем.

**Правильный подход:**

| Контент | Паттерн | Back работает |
|---------|---------|---------------|
| Полноэкранный подэкран (добавить слово, настройки) | Отдельный `composable` route в NavController | Автоматически через back stack |
| Подтверждение, информация, ввод | `AlertDialog` / `BottomSheet` | Автоматически — закрывает диалог |

Никаких `var showX by remember { mutableStateOf(false) }` + `if (showX) { FullScreenContent(); return }`.

### Исключение 1: режим внутри вкладки (поиск в теории)

Если вкладка имеет **режим** — не подэкран, а другое состояние той же вкладки, где шапка и нижняя
капсула навигации остаются на месте (эталон: поиск во вкладке «Учить»), — системная «назад» обязана
этот режим сворачивать. Отдельным роутом такое НЕ делаем: роут стоил бы плавной подмены тела,
отдельного ViewModel и разъехавшихся позиций скролла, а внешне это по-прежнему та же вкладка.

Разрешено: `BackHandler(enabled = <режим открыт>) { <закрыть режим> }` в Composable вкладки.
Правила: перехват включён ТОЛЬКО пока режим открыт (закрытый оставляет кнопку системе), и он
вызывает ту же функцию закрытия, что и кнопка в шапке, — никакой отдельной логики выхода.
Это не починка навигации: без перехвата «назад» на корневой вкладке закрывает приложение
(поймано на устройстве 05.09.2026, см. `search_feature_brief.md` §8.2.4).

### Исключение 2: guard-диалог (подтверждение выхода)

Если на экране есть несохранённый прогресс, который случайное нажатие «Назад» уничтожит
(начатое AI-задание — запрос уже потрачен; недопройденная серия упражнений и т.п.) —
перехват «Назад» ради диалога «Точно выйти? Прогресс будет потерян» — это **осознанная
фича, а не починка навигации**, и она разрешена.

Правила для этого исключения:
- Использовать официальный API — `PredictiveBackHandler` (дружит с жестом-превью «Назад»),
  не голый перехват.
- Реализуется ОДИН раз — общий компонент-обёртка в `ui/components/` («экран с подтверждением
  выхода»), переиспользуется везде, где нужен guard (AI-экран, случайная практика и т.д.).
  Копипаста перехвата по экранам — запрещена.
- Перехват — только для подтверждения: пользователь подтвердил → обычный `popBackStack()`,
  никакой ручной навигации.

`BackHandler` для «чтобы назад вообще работала» — по-прежнему запрещён: это всегда симптом
сломанного back stack (см. выше).

### System navigation bar (insets)

`enableEdgeToEdge()` включён в Activity. Базовая обработка — один раз на уровне `MainActivity`:

- Нижний nav bar: внешний `Box` с `.navigationBarsPadding()` + `NavigationBar(windowInsets = WindowInsets(0))`
- Scaffold прокидывает `innerPadding` в `NavHost`, но **низ инсета применяется ТОЛЬКО на вкладках**
  (там его держит боттом-бар): `bottom = if (showBottomBar) innerPadding.calculateBottomPadding() else 0.dp`.
  Верх/бока — всегда.

**Вкладки** (корневые destination с боттом-баром): insets самостоятельно НЕ трогают — низ держит
боттом-бар, верх/бока приходят из `innerPadding`. Никаких `navigationBarsPadding()`/`statusBarsPadding()`
внутри таких экранов.

**Полноэкранные роуты** (подэкраны теории, список карточек, сессия упражнений): низ НЕ резервируется —
контент уходит edge-to-edge под прозрачную системную полосу. Поэтому **низ держит сам экран**:

- Скроллящийся контент (`LazyColumn` `contentPadding` / `Column + verticalScroll` `padding(bottom=…)`) —
  через общий хелпер `ui/util/scrollBottomInset()` (= высота навбар-инсета + единый зазор `Dimens.bottomBarGap`).
  Любой новый полноэкранный скролл подключается им одной строкой — не считать инсет руками по экранам (Правило №0).
- Экран с прибитой к низу кнопкой/футером (как сессия упражнений) — корневой контейнер берёт
  `.windowInsetsPadding(WindowInsets.ime.union(WindowInsets.navigationBars))`: клавиатура скрыта → отступ над
  навбаром, открыта → вплотную к клавиатуре (`union` = max, без двойного отступа и без дыры).

Работает и с gesture navigation, и с 3-кнопочной (инсет берётся фактический). Голый `imePadding()`
на полноэкранном экране НЕ использовать — он не учитывает навбар (см. `union` выше).

    накрутки, но не наказывает за исправление внутри того же захода.
    ⚠️ Никаких «счётчиков попыток» в этой таблице НЕТ — попытки это UI-стейт сессии.
    ⚠️ Имя поля `correctFirstTry` осталось от старой логики и смыслу не соответствует (правильное —
    `solvedOnFirstPass`); переименование ждёт ближайшей миграции user.db по другой причине — см.
    `TODO(rename)` в `UserExerciseResult`.
  - `UserMicrotopicProgress.isCompleted` **НЕ ТРОГАТЬ** — зелёный сегмент остаётся.
  - `UserAiExerciseStats` **НЕ ТРОГАТЬ** — AI-прогресс сохраняется (Фаза 3).
- Состояние **текущего захода** (какие упражнения отвечены в этом прохождении) — рабочее
  состояние сессии в ViewModel, не статистика в БД; новый заход начинается с чистого листа сам.

## Перевод слов по долгому нажатию — глобальная функция (ОБЯЗАТЕЛЬНО)

**Любое английское слово в любом месте приложения должно реагировать на долгое нажатие.**
При зажатии → всплывает речевое облачко (comic speech bubble) с переводом и транскрипцией + кнопка "В мои слова".

### Как реализовано

Используется кастомный composable `TranslatableText` (`ui/components/TranslatableText.kt`).
**Везде где отображается английский текст — использовать `TranslatableText` вместо обычного `Text`.**

Детектирование слова — через официальный Jetpack API, без хаков:
```kotlin
Text(
    onTextLayout = { textLayoutResult = it },
    modifier = Modifier.pointerInput(Unit) {
        detectTapGestures(
            onLongPress = { offset ->
                val charPos = layout.getOffsetForPosition(offset)
                val wordRange = layout.getWordBoundary(charPos) // TextRange
                val word = text.substring(wordRange.start, wordRange.end)
                // показать TranslationPopup для word
            }
        )
    }
)
```

`TextLayoutResult.getWordBoundary(offset)` — возвращает границы слова под пальцем.
Системное выделение (SelectionContainer) **не используется** — нам не нужен drag handles и стандартный toolbar.

### Поток после зажатия

1. Проверяем кэш (`DictionaryCache` в Room) — если есть, показываем мгновенно
2. Нет в кэше → запрос в LingvoLive → fallback Yandex Dictionary → кэшируем ответ
3. Popup: слово + транскрипция + список переводов + кнопка "В мои слова"
4. "В мои слова" → экран с галочками (самые ходовые переводы первыми) → пользователь выбирает → слово летит в Words8r, категория **"МОИ СЛОВА"**

### Где работает — только КОНТЕНТ, не интерфейс

Работает на **контентном** английском тексте (то, что приходит из БД / от AI):
- Карточки теории (объяснение + примеры)
- Все типы хардкодных упражнений (предложения, слова, варианты ответов)
- AI-упражнения (умная практика)
- Все режимы вкладки Практика
- Таблицы-схемы порядка слов
- AI-уточнения ("Не совсем понял")

**НЕ работает на интерфейсном тексте:** заголовки упражнений и экранов, кнопки, подписи,
названия — даже если они на английском. Зажатие на них ничего не показывает.

Граница совпадает с правилом хранения строк: текст из `strings.xml` (интерфейс) → обычный
`Text`; текст из БД / от AI (контент) → `TranslatableText`.

### Правило при написании кода — оборачивать С ПЕРВОГО ДНЯ

`TranslatableText` создаётся в `ui/components/` с первого дня разработки как **тонкая
обёртка-пустышка** над `Text` (тот же API; внутри пока просто `Text`, без жеста и попапа).
Весь контентный текст рендерится через неё с самого начала — даже пока фича перевода не
реализована. Зачем: дорогая часть фичи — не попап, а ретрофит сотен call-site'ов; пустышка
сводит включение фичи к правкам в одном файле.

Вместе с пустышкой с первого дня закладываются: интерфейс `DictionaryRepository` в domain
(как остальные заглушки) и таблица `DictionaryCache` в схеме user.db (уже в `db_schema.md`).
Сам пузырь, жест и провайдеры (LingvoLive → Yandex → кэш) — отдельным шагом позже.

При создании любого экрана/компонента проверять: контентный текст — через `TranslatableText`?
Интерфейсный — через обычный `Text` из `strings.xml`?

## Качество кода (КРИТИЧНО)

Пишем код как старший Android-разработчик с многолетним стажем:

**Комментарии — короткие, по факту.** Инлайн-комментарий внутри функции — одна строка, суть, не поэма. Не расписывать очевидное. Большой комментарий уместен только над классом/публичным компонентом (KDoc — что делает класс/экран). Внутри тел функций — минимум, по делу.

**Без исторических шагов в комментариях.** Комментарий описывает, КАК код работает сейчас, — а не «было X, исправили на Y», не «используем A, а не B, потому что B дрейфовал» и не диалог с ревьюером. История правок живёт в git, не в коде. Если для понимания нужна причина выбора — одна короткая фраза о текущем поведении, без упоминания отвергнутых вариантов.

**Без костылей.** Использовать только официальные Android/Jetpack API по их назначению. Никаких хаков с отрицательными offset, z-index трюков для перекрытия системных виджетов, и прочих обходных решений.

**Разделение ответственности.** Если функционал логически отдельный — выносить в отдельный класс/файл:
- Бизнес-логика → ViewModel или Repository, не в UI
- Переиспользуемые UI-компоненты → отдельный @Composable файл в ui/components/
- Утилиты → отдельный object/class

**Если без костыля не обойтись** — сначала описать:
1. Вариант 1 (правильный) — почему не подходит в данном случае
2. Вариант 2 (правильный) — почему не подходит
3. Предлагаемый подход — что именно и почему это приемлемый компромисс

Только после одобрения — писать код.

для смахиваемых уведомлений использовать SwipeToDismissBox из Material3, не ручной Animatable.

**Без костылей.** Перед написанием кода — проверить, есть ли официальный Jetpack/Material3 API для этой задачи. Если есть — использовать его, не изобретать велосипед. Никаких хаков с отрицательными offset, z-index трюков, ручных `Animatable` там где есть готовый компонент, и прочих обходных решений.

**Примеры правильного выбора API:**
- Смахиваемые уведомления → `SwipeToDismissBox` (Material3), не ручной `Animatable` + `detectHorizontalDragGestures`
- Анимации появления/исчезновения → `AnimatedVisibility`, не ручное управление `alpha`
- Списки → `LazyColumn`/`LazyRow`, не `Column` с `forEach`

## Базовые правила Android-разработки (ПОСТОЯННЫЕ, для любой модели)

> Этот раздел — постоянный источник правды по качеству кода. Он обязателен для **любой**
> модели (Fable, Opus, Sonnet) перед написанием любого Kotlin-кода. Пока существует
> `tasks/words8r_lessons.md` — читать и его (детали и примеры из аудита Words8r);
> после его удаления этот раздел остаётся единственным нормативом.
>
> Установка: писать код как сеньор Android-разработчик в большой опытной команде.
> Каждый файл должен быть понятен человеку, который видит его впервые. «Работает же» —
> не аргумент; аргумент — «так делают в продакшене и это переживёт три года развития».

### Правило №0 — единственный источник правды

Любая доменная сущность или логика определяется в кодовой базе РОВНО ОДИН РАЗ.
Перед написанием кода спросить себя: «эта сущность/логика уже где-то существует?»
Если да — вынести и переиспользовать, а не копировать. Новая фича НЕ добавляется
копированием соседней. Две копии всегда разъезжаются — это вопрос времени.

### Типизация — запрет на stringly-typed код

- Любое конечное множество значений — `enum class` или `sealed class`, никогда строки.
  Строки в `when` по доменным значениям — запрещены.
- Доменная сущность определяется один раз со всеми атрибутами:
  `enum class Bucket(val from: Int, val to: Int?, val label: String)` — UI строит кнопки
  итерацией по `entries`, запрос — один параметризованный метод DAO. Добавление
  варианта = одна строка.
- В БД/JSON значения сериализуются строкой — конвертация в тип на границе data-слоя,
  один раз (TypeConverter / маппер).
- Никаких magic numbers и magic strings в логике: пороги, лимиты, длительности анимаций,
  ключи — именованные константы (`companion object` / `object Constants` рядом с владельцем
  смысла, не глобальная свалка).

### DI и тестируемость

- Hilt с первого коммита: `@HiltViewModel`, репозитории/DAO через `@Inject`,
  БД — `@Singleton` в `@Module`. Никаких `getInstance()` / `new` внутри ViewModel.
- ViewModel — обычный `ViewModel`, НЕ `AndroidViewModel`. Context в ViewModel не попадает
  вообще: ресурсы/prefs — через инжектируемую обёртку.
- Любой класс с логикой обязан быть тестируем без Android: чистый Kotlin + подменяемые
  зависимости.

### Логика живёт в domain, а не в ViewModel

- ViewModel = только UI-state и реакции на действия пользователя. ViewModel больше
  ~300 строк — сигнал, что в нём застряла доменная логика.
- Алгоритмы (планировщики, подбор вариантов, взвешенный выбор, агрегация статистики) —
  отдельные классы в domain (use case), покрываемые юнит-тестами.
- Репозиторий существует, только если несёт логику (маппинг, объединение источников,
  транзакции). Анемичные прокси «метод-в-метод» не писать.
- Общая механика между похожими экранами — отдельный класс-делегат со своим `StateFlow`,
  включаемый композицией, а не копипаста между ViewModel'ами и не наследование.

### Compose / UI

- Один файл = один экран ИЛИ один компонент. Ориентир до ~300–400 строк, больше — делить.
  Экраны тонкие: собирают компоненты и подключают ViewModel.
- Повторяющийся UI-паттерн — один параметризованный компонент в `ui/components/`.
- ВСЕ интерфейсные строки — в `strings.xml` с первого экрана, обращение к пользователю
  на «Вы». Хардкод текста в Composable запрещён. Динамический контент (теория,
  упражнения) — из БД.
- Одноразовые события ViewModel → UI (навигация, анимации) — через `Channel`/`SharedFlow`
  либо state с явным подтверждением. Продвижение бизнес-логики НЕ должно зависеть от того,
  доживёт ли `LaunchedEffect` до конца. Решения принимает ViewModel, UI только отображает.
- Жесты и анимации — только официальные API (`AnchoredDraggable`, `SwipeToDismissBox`,
  `AnimatedVisibility`); ручные `Animatable`-машины — только если официального API нет,
  и тогда по протоколу костылей (см. «Качество кода»).

### Данные

- **Критерий выбора хранилища:** «должно ли это пережить перенос на новый телефон вместе
  с прогрессом?» Да → Room. Нет (настройки поведения приложения) → Jetpack DataStore.
  Данные прогресса/обучения в prefs — запрещены.
- DataStore вместо SharedPreferences; обёртки в `data/preferences`, доступ через
  инжектируемый класс с типизированными `Flow`. Не плодить файл на каждую мелочь.
- Room: `exportSchema = true`, схемы в VCS, честные миграции с первого релиза + автотесты
  миграций (`MigrationTestHelper`). Никакого destructive fallback.
- `OnConflictStrategy.REPLACE` на пользовательских insert — не использовать бездумно:
  для пользовательских данных `ABORT`/`IGNORE` + явная обработка конфликта.
- Серии однотипных запросов — один параметризованный метод DAO, не N копий.
- Агрегатная статистика — SQL-агрегаты (`GROUP BY`), не последовательные suspend-запросы
  из ViewModel.
- Даты и время: в `grammar-core` — `kotlin.time` (`Instant`, `Duration`, `Clock`) и `kotlinx-datetime`
  для календарных дат; в `grammar-app-android` — `java.time` (`LocalDate`, `ZonedDateTime`). Доменные
  периоды (день/неделя/цикл стрика) — один утилитный класс в ядре. `Calendar` запрещён везде.

### Навигация

- Type-safe navigation (Navigation Compose 2.8+): роуты — `@Serializable` data class/object,
  аргументы типизированы. Конкатенация строк в роуты и ручной парсинг
  `arguments?.getString(...)` с молчаливыми дефолтами — запрещены.
- Видимость нижней панели — белый список корневых вкладок; любой новый экран
  по умолчанию полноэкранный.
- Полноэкранные состояния (активная сессия) — отдельные роуты, а не boolean-стейт
  внутри вкладки с колбэком наверх.

### Надёжность и релиз

- Поведение, различающееся между dev и релизом, — ТОЛЬКО через `BuildConfig`-поля или
  удалённый конфиг. Код с «TODO раскомментировать перед релизом» не пишется вообще.
  Проверка тира/лимитов — единый инжектируемый `EntitlementsProvider`, в debug подменяемый.
- Аналитика — один интерфейс `Analytics` с типизированными методами
  (`fun lessonStarted(mode: TranslationDirection)`), имена событий — константы в одном
  файле. Инжектится, в тестах — no-op.
- Мёртвый код (неиспользуемые перегрузки, закомментированные блоки «на потом») — удалять
  сразу, история есть в git. Исключение: закомментированные строки пользователя не трогать
  без запроса.
- В крэш-хендлере — только синхронная запись файла + проброс в исходный хендлер; никаких
  clipboard/`Thread.sleep` из хендлера.

### Чек-лист перед каждым новым модулем

1. Зависимости приходят через Hilt? (`getInstance`/`new` внутри ViewModel — стоп.)
2. Доменные значения — типы, а не строки? Источник правды — один?
3. Эта логика/UI уже существует? Выносим и переиспользуем, а не копируем?
4. Есть официальный Jetpack/Material3 API для задачи? (Проверить ДО написания своего.)
5. Логика тестируема без Android — и лежит в `grammar-core`, а не во ViewModel? ViewModel тонкий?
6. Все интерфейсные строки — в `strings.xml`, на «Вы»?
7. Данные прогресса — в Room (бекап/синк), настройки — в DataStore?
8. Файл не разросся за ~400 строк?
9. Нет «TODO раскомментировать»? Dev/prod — через BuildConfig?
10. События аналитики — через общий `Analytics`?
11. Цвета/отступы — через `Color.kt`/токены, английский текст — через `TranslatableText`?

## Контент теории и упражнений (КРИТИЧНО)

### ⭐ ГЛАВНЫЙ НАКАЗ ПО ТЕОРИИ (канон, не возвращаемся к обсуждению)

**Разжёвывать до предела.** Карточка должна объяснять так, чтобы понял даже самый неподготовленный
человек без знания английского. Это значит ВСЕГДА:
- **Глубокое сравнение с русским** — не «в английском так», а как это в русском, почему английский
  работает иначе, и где именно из-за этого спотыкается русскоязычный.
- **Объяснение логики «в корне»** — почему именно так надо делать, откуда правило берётся. Не
  «запомни», а «вот почему это устроено так — и теперь ты не забудешь».
- **Откуда ошибка в голове русского** — каждую типичную ошибку показываем не как «нельзя», а как
  «вот откуда мозг это тянет из русского, и почему здесь это не работает».
- **Много живых примеров** — из реальной жизни (работа, еда, чат, поездка), не учебниковые.
- **Плашки-ловушки** (`**Ловушка:** …`) — активно, чтобы ключевое притягивало взгляд.
- **Качественные AI-упражнения** — см. ниже про количество.

Лучше три понятные подробные карточки, чем одна перегруженная. Не экономим на объяснении.

### Количество AI-упражнений на карточку — гибко

На карточке может быть **1, 2 или 3 AI-упражнения** — по необходимости, если правило того стоит и
каждое проверяет свою грань. Может не быть **вообще ни одного** — у вводных/справочных карточек
(концепт-интро, карточка приоритета) AI не нужен. ID — `<topic>_card<N>_ex1`, `_ex2`, `_ex3`.
(Старое «одно `_ex1` на карточку» отменено.)

### Переводы примеров — НЕ переводим простое (с Present Simple и далее)

Команда «середины курса» дана (25.06.2026). С темы Present Simple и далее:
- **НЕ переводим:** слова из «Основ» и всех тем до текущей, базовую служебку (предлоги,
  местоимения, to be, do/does, артикли), приоритетные глаголы темы, и даже точечно незнакомое —
  пользователь зажмёт слово (long-press) и получит перевод сам. Это сознательная тренировка:
  человек должен учиться понимать смысл сам.
- **Переводим:** реально новые ключевые слова темы (+ их Words8r Sync).
- **Колонка RU в `#### Examples` — ОСТАЁТСЯ** (формат таблицы). Убираем только инлайновые
  тривиальные переводы в прозе теории (`I want to eat` *(Я хочу есть)* — больше не пишем).
- **Упражнения:** `TrueFalse` — без колонки RU (только EN + «Верно?», смысл ловит сам/long-press).
  `FORWARD_CHOICE`/`REVERSE_CHOICE` — перевод пока ДАЁМ (русский там часть задания), до отдельной
  команды. `WordArrangement` — `—` вместо перевода для знакомых слов.
- Исключение: если условие-инструкция упражнения формулирует *правило*, перевод этого
  условия-правила дать можно; сами предложения-специмены, которые юзер судит, — без перевода.

Полный канон переводов — `theory_content_guide.md` §3, §4, §6.

**Глаголы в тексте теории и в Words8r Sync — всегда с `to` и в базовой форме:** `to run`, `to think`, `to be`, `to have`.
Никаких окончаний: не `to running`, не `to swam`, не `to finished` — только чистый инфинитив.
Исключение — модальные глаголы (`can`, `must`, `should`, `may`): у них нет инфинитива с `to`, пишем без.
Правило касается упоминания глагола как слова (перечисления, примеры в теории, Sync-таблица). В предложениях-примерах глагол стоит в нужной форме как обычно (`She runs quickly`).

**⚠️ Кавычки — ЖЁСТКИЙ канон (по ЯЗЫКУ, не по длине).** Три знака, три непересекающиеся роли:
- `` `бэктики` `` — английская вставка, которую нужно **акцентировать** (слово/морфема/формула/
  предложение). UI красит цветом `InlineCode` + Medium, бэктики не видны. **Только в `#### Theory`
  и `#### Summary`** — в Clarification Options и в упражнениях НЕ использовать.
  ⚠️ **НЕ бэктить всё английское подряд — это перегруз и некрасиво** (см. ниже «Грань бэктиков»).
- `«гильеме»` — русскоязычное цитирование/называние (имена тем, «что делать?», русские фразы,
  смысловые глоссы «к, в»). Единственные кавычки, которые видит пользователь.
- `"прямые"` — ТОЛЬКО строка-условие упражнения (конвертер их срезает). В прозе теории `"` не писать.
Английское ВНУТРИ условия упражнения бэктиками не оборачивать. Полный канон + TODO ретрофита старых
тем — `theory_content_guide.md` → §8 «КАВЫЧКИ: ЖЁСТКИЙ КАНОН».

**⚠️ Транскрипция — ТОЛЬКО в двойных скобках `[[wɜːk]]` (канон 22.07.2026).** Одинарные `[…]` заняты
пропусками (`[___]`) и слотами-шаблонами (`[предмет]`), а отличить их от транскрипции по содержимому
нельзя (`[red]` — и слот, и чтение `read`). Поэтому маркер ставит автор: пишем `[[wɜːk]]`, `[[t]]` —
пользователь видит `[wɜːk]` серифным шрифтом покрупнее (UI срезает внешние скобки). Действует ВЕЗДЕ,
где текст читает пользователь: теория, Summary, Examples, условия и explanation упражнений,
Clarification. НЕ ставим: в колонке «Транскрипция» Sync-таблиц (структурное поле) и в
`Prompt Template` (уходит на сервер; требование к AI живёт в блоке «Роль» базового промта).
Слоты-шаблоны писать без скобок: `Формула: X + as well as + Y`. Полный канон — `theory_content_guide.md`
→ §8 «ТРАНСКРИПЦИЯ»; нарушения ловит `smell.py`.

**⚠️ Грань бэктиков (против перегруза — должно быть КРАСИВО).** Бэктик — это акцент «посмотри
именно сюда», а не разметка «здесь латиница». Если бэктить каждое английское слово — выделение
обнуляется, текст рябит, перегруз. Правило:
- **Бэктик уместен**, когда английское слово/короткая вставка сидит ВНУТРИ потока русского текста —
  тогда `word` слегка подсвечивается и его видно. В этом весь смысл выделения.
- **НЕ бэктить** перечисления и строки вида «англ. предложение — перевод» (каждый пример на своей
  строке, списком). Английские примеры-специмены по строкам — если нужно выделить, бери `**жирный**`,
  либо вообще без выделения. Россыпь `` ` `` по таким спискам = некрасиво и перегруз.
- Объект разбора (противопоставление форм, формула, ключевая форма ради которой карточка) — бэктик.
  Фоновое/повторное/служебное английское — голым. Критерий простой: **смотри, чтобы было красиво.**

**Строго следовать форматам упражнений из таблицы в grammar8r_plan.md.** Каждый тип упражнения имеет свой чёткий формат — не смешивать.

**⚠️ КРИТИЧНО: габариты табличных заданий (CATEGORIZATION, MATCHING, TABLE_FILL).** Эти типы
рендерятся как «таблица + пул на одном экране телефона» (две колонки друг напротив друга / поле
рядом с подсказкой). Поэтому при написании контента — **держать элементы КОРОТКИМИ**, чтобы и
таблица, и пул целиком влезали на один экран без бесконечной прокрутки:
- НЕ делать элементы пула/ячеек большими предложениями — это короткие слова или сжатые фразы.
- Длинные многословные подсказки/ситуации в CATEGORIZATION и MATCHING — запрещены (пул раздувается,
  на экран не помещается). Касается и левой колонки MATCHING.
- Ориентир: всё задание (условие + таблица + пул) видно на одном экране; перенос на 2–4 строки —
  норма, прокрутка-простыня — нет.
Это правило для **автора контента** (видно при написании теории) — рендер рассчитан на компактность.
Если конкретное задание выбивается по длине — переписать короче (об этом пользователь попросит на тестах).

**ErrorCorrection** — только сломанное английское предложение в условии, без русского перевода. Пользователь выбирает правильный английский вариант из 2–3 опций. Если нужен русский контекст → использовать FORWARD_CHOICE, а не добавлять русское к ErrorCorrection.

**Промт AI-упражнения** (хранится на сервере в `prompts.json`, не в клиенте) — всегда добавлять `Пример вывода AI:` с конкретным текстом который AI выдаст пользователю. Без примера нельзя проверить корректность задания.
Сам промт пишется ПОЛНЫМ по канону `theory_content_guide.md` §5 → «ПРОМТ ПИШЕМ ПОЛНЫЙ»: факты карточки
нашими формулировками + грамматический фон (что пользователь уже прошёл по курсу и чего ещё НЕ прошёл) +
задание с «держи простым» + инвентарь с ловушками-границами + оценка с отдельной строкой на каждую
ловушку карточки. ИИ проверяет ровно то, что мы рассказали. Эталон — `get_card530_ex1..ex3`.

## Конвейер контента: MD → JSON → content.db

Теория/упражнения/слова пишутся в MD (источник правды), конвертируются скриптами в `tasks/tools/`:
- **`md_to_json.py`** — ручной, парсит MD → JSON-сид (коммитим). Один парсер на все theory-файлы.
- **`json_to_db.py`** — автоматом при сборке (Gradle), собирает JSON → `content.db` в assets.

Подробно — `tasks/db_schema.md` → «Конвейер контента» и `tasks/theory_content_guide.md` → раздел 8.

> ⚠️ **ПРАВИЛО: после ЛЮБОЙ правки уже готовой теории (для которой уже есть seed) — ОБЯЗАТЕЛЬНО
> явно напомнить пользователю запустить `py md_to_json.py <файл>`.** Скрипт ручной, забыть легко,
> а теорию правим вместе — напоминание о перезапуске лежит на Claude при каждой такой правке.
> Иначе JSON-сид устареет относительно MD и сборка соберёт `content.db` из старых данных.
