# Рендер таблиц в теории — спецификация и пожелания

> **Назначение:** собрать в одном месте все требования к отображению таблиц теории, чтобы при
> будущих правках ничего не сломать. Согласовано в чате 16.06.2026 (итеративно, по скринам).
> **Код:** `grammar-app-android/.../ui/components/theory/TheoryBlockView.kt` → `TableBlock`, `layoutTable`,
> `wrapLongWords`, `wrapEveryWord`, `splitWord`, `squeezeColumns`, `measureColumns`, `measureColumn`,
> `distributeWidths`, `TableRow`.
> **Источник данных:** блок `{"type":"table", "header":[...], "rows":[[...]]}`.
> Статус: 🟡 эвристика, обкатывается визуально — пороги могут подкручиваться.

## Главное правило (не нарушать никогда)

**НИКОГДА не переносить 1–2 буквы на отдельную строку.** Сиротские «Личн/ое», «владее/т», «Местоимени/е»,
«Глаго/л» — недопустимы. Перенос от 3 букв — допустим. Это корневое требование, ради него сделано
всё остальное. Уточнение 06.07.2026: правило касается ЛЮБОЙ ячейки — и шапки, и тела.

## Требования

1. **Текст в ячейках — по левому краю** (`textAlign = Start`), прижат к верху ячейки.
   **Шапка — по центру** (`textAlign = Center`): её ячейки короткие, и по центру колонка читается
   как подпись столбца, а не как первая строка данных.

2. **Колонки «плавающие» (по содержимому), НЕ равные трети.** Колонка с длинным контентом
   получает больше места, с коротким — меньше. Равная ширина (`weight(1f)`) — отвергнута.

3. **Ширина колонки ≥ ширины её самого длинного слова.** Меряется реально (`TextMeasurer`, жирным
   14sp — худший случай). Поэтому слова НЕ рвутся по буквам в принципе (главное правило соблюдается
   автоматически). Остаток ширины раздаётся колонкам пропорционально их min-ширине → колонки с
   длинными словами/предложениями получают больше.

4. **Одиночные слова-ярлыки длиннее `MAX_WORD_LEN` (=9) делятся на ~равные части** (вставляем `\n`) —
   но ТОЛЬКО если таблица не влезает в ширину экрана нерезаной (см. итерацию 4),
   напр. «Местоимение» → «Местои/мение», «Притяжательное» → «Притяжа/тельное». Зачем: иначе колонка
   под короткий контент (ячейки по 2–4 буквы) была бы широкой только из-за длинного заголовка —
   а так место освобождается соседям (напр. колонке с предложениями).
   - Переноса «по правилам языка» (по слогам) НЕТ — Compose не умеет, и пользователь сказал «забей
     на правила, лишь бы не 1–2 буквы». Делим примерно пополам по символам (каждая часть ≥ ~5 букв).

5. **Многословные ячейки (предложения) — слова НЕ делим.** Они переносятся по пробелам естественно.
   Делим только ОДИНОЧНОЕ слово в ячейке (label-like: заголовок или односложная ячейка). Признак —
   в строке нет пробелов. Пример: «Когда использовать» (2 слова) не трогаем — переносится по пробелу.

6. **`**жирный**`-токены не делим** (маркеры разметки сломаются). Они и так короткие.

7. **Боковой отступ ячейки — `TABLE_CELL_PADDING_H`** (`Dimens.spaceMedium` = 12dp, дизайн 4G).
   Величина объявлена ОДНОЙ константой и используется и в рендере, и в `measureColumn`: разъедутся —
   замер разойдётся с экраном и слова начнут резаться.
   ⚠️ 12dp съедают ширину (на 3 колонках — 24dp плюс 2dp на полосы-разделители). Если на живых
   трёхколоночных таблицах пойдут переносы, откатить константу на `Dimens.spaceSmall` = 8dp —
   вертикальный отступ при этом остаётся 8dp, капсула визуально почти не меняется.

8. **Полосы-разделители колонок вычитаются из ширины ДО раскладки**
   (`maxWidth − outlineWidth × (колонок − 1)`), иначе сумма колонок с полосами вылезает за капсулу.

## Визуал (дизайн 4G · «реестр + контурная шапка», 19.09.2026)

Блок — не коробка, а `Column` из капсул: шапка одной контурной капсулой, каждая строка — своей
залитой. Ни фона, ни скругления, ни `clip` у самого блока нет; `HorizontalDivider` между строками
убран совсем — его работу делает зазор.

| Элемент | Оформление |
|---|---|
| Капсула строки | фон `Elevated`, скругление `Dimens.cornerSmall` (4dp) |
| Капсула шапки | без заливки, рамка `Dimens.outlineWidth` цветом `Inactive`, то же скругление |
| Зазор между капсулами | `Dimens.spaceTiny` (4dp) |
| Ячейка | padding `TABLE_CELL_PADDING_H` × `Dimens.spaceSmall` |
| Текст строки | `TextPrimary` 14sp / 20sp; первая колонка — `FontWeight.Medium`, остальные обычные |
| Текст шапки | `TextSecondary` 13sp / 16sp, `FontWeight.Medium`, обычный регистр, по центру |
| Разделитель колонок | полоса `Dimens.outlineWidth` цветом `Inactive` после каждой колонки, кроме последней |

- **Шапка обычным регистром, не капслоком:** капслок раздувает минимальную ширину колонки, а
  `measureColumns` считает ширины по самому длинному слову — заголовок начал бы отбирать место у
  колонки с предложениями.
- **Разделитель — полоса во всю высоту капсулы**, поэтому `Row` берёт `height(IntrinsicSize.Min)`,
  а полоса — `fillMaxHeight()`. Внутрь ячейки его класть нельзя: не накроет вертикальный padding.
- **Шапка и строка — один Composable** `TableCapsule(cells, widths, isHeader)`, две копии верстки
  не плодим.
- **Цвет капсулы — константа `Elevated`, не производная от `containerColor`.** Таблицы внутри плашек
  в контенте есть (8 штук), но тело плашки лежит на том же `containerColor` — а он всегда либо
  `CardBackground`, либо `Background`, оба темнее `Elevated`. Слияния не будет.

## Алгоритм — история итераций

> Прошлые итерации НЕ стираем: если вылезет новый баг раскладки, по этой истории видно, какая
> логика когда была и почему её меняли.

### Итерация 1 (16.06.2026) — УСТАРЕЛА (заменена итерацией 2)

1. `wrapLongWords(cell)` — для каждой ячейки: если это одиночное слово без `*` и длиннее
   `MAX_WORD_LEN` → режем на `ceil(len/MAX_WORD_LEN)` равных частей через `\n`. Иначе — без изменений.
2. `columnWidths(...)` в `BoxWithConstraints`:
   - для каждой колонки находим самый длинный токен (split по пробелам/`\n`, без `*`), меряем его
     ширину `TextMeasurer`-ом (bold 14sp) → это min-ширина колонки (+ 2× боковой отступ);
   - `extra = доступная ширина − Σ min`; раздаём **пропорционально min-ширине**;
   - если контент шире экрана (редко) — масштабируем пропорционально (fallback, без переполнения).
3. `TableRow` — ячейки фиксированной ширины (`Modifier.width(...)`), сумма = ширине таблицы.

**Найденный баг (скрин `img.png`, таблица «Что усиливаем | Чем | Пример»):** алгоритм знал про
колонку только одно число — ширину самого длинного СЛОВА — и остаток экрана раздавал пропорционально
ему же. Колонка «Что усиливаем» (длинное слово `прилагательное`, но мало текста в целом) получала
и большую min-ширину, и львиную долю остатка, которую ей некуда девать; а «Чем» (слова короткие, но
текста много: `really / a lot / very much`) получала крохи и складывалась в 3 строки. Эвристика
работала только когда «длинное слово» и «много текста» — одна и та же колонка (случай `img_1.png`,
поэтому там всё выглядело хорошо).

### Итерация 2 (06.07.2026) — min/ideal, как auto-layout таблиц в браузерах

`wrapLongWords` и шаг 3 (`TableRow`) — без изменений. Изменён только `columnWidths`:

1. Для каждой колонки меряется **два** числа (`TextMeasurer`):
   - **min** — ширина самого длинного слова (как раньше; гарантия «слова не рвутся» сохранена);
   - **ideal** — ширина самой длинной ЦЕЛОЙ строки ячейки (split только по `\n`, т.е. для обычной
     ячейки — вся ячейка в одну строку). Шире ideal колонке уже не нужно — контент влезает.
2. Каждой колонке гарантируется её min. Остаток раздаётся **пропорционально дефициту `ideal − min`**
   с потолком ideal: колонке, чей контент уже влезает, лишнее место не достаётся — оно уходит тем,
   кому реально не хватает. (Если `extra ≤ Σ дефицитов`, доля каждой колонки автоматически ≤ её
   дефицита — итеративное «обрезание по потолку» не нужно.)
3. Если места хватает всем до ideal (каждая ячейка помещается в одну строку) — излишек добивается
   пропорционально ideal, чтобы таблица по-прежнему заполняла всю ширину экрана.
4. Fallback «контент шире экрана → масштабируем пропорционально min» — как в итерации 1.

**Зачем менялось:** чинит перекос из бага итерации 1 — «Что усиливаем» с маленьким дефицитом почти
ничего не забирает, «Чем»/«Пример» получают место по реальной потребности. Случаи, где итерация 1
работала (`img_1.png`), не ломаются: когда дефициты распределены так же, как min-ширины, результат
совпадает со старым.

**Попутное уточнение измерения:** раньше ВСЕ ячейки мерились жирным 14sp (worst case), из-за чего
обычные (не заголовочные) ячейки переоценивались по ширине. Теперь заголовок меряется жирным,
тело — обычным начертанием — ровно как рендерит `TableRow`.

### Итерация 3 (06.07.2026) — фикс замера: мерить ТЕМ ЖЕ стилем, что рендерим

**Найденный баг (скрин `img_2.png`):** заголовок «Глагол» разорвало на «Глаго / л» — 1 буква на
новой строке, нарушение главного правила. Логика распределения тут ни при чём — разошлись **стиль
замера и стиль рендера**:
- мерили «голым» `TextStyle(14sp)`, а `Text` рендерит поверх `LocalTextStyle.current`
  (типографика Material: свой шрифт, `letterSpacing`) → слово на экране ЧУТЬ шире замера;
- итерация 2 это вскрыла: колонка без дефицита («Глагол» — одно слово, ideal = min) стала получать
  РОВНО min-ширину, запаса нет — и последняя буква выпала. В итерации 1 колонке всегда доставался
  лишний остаток сверху, он маскировал недомер (поэтому баг не стрелял раньше).

**Что изменено (только замер, распределение итерации 2 не тронуто):**
1. `columnWidths` принимает `LocalTextStyle.current` из композиции и меряет `baseStyle.merge(...)` —
   тем же результирующим стилем (шрифт, letterSpacing, 14sp/20sp), каким реально рендерит `TableRow`.
2. Кусок текста с `*` (жирный спан в теле) меряется жирным — раньше тело мерилось только обычным,
   тот же класс недомера.
3. `MEASURE_SLACK = 1.dp` к каждой колонке — гасит округления px↔dp (замер px → Dp → обратно в px
   в `Modifier.width`), где могло не хватить долей пикселя.

**Инвариант после фикса:** колонка ≥ ширины самого длинного слова В ТОМ ЖЕ стиле, каким оно
рендерится + запас → перенос посреди слова невозможен в принципе (не «1–2 буквы нельзя», а никакой).
Единственное исключение — fallback «контент шире экрана → масштабируем ниже min» (см. итерацию 1);
если он когда-нибудь стрельнёт — это сигнал, что контент таблицы слишком длинный (правится контент).

### Итерация 4 (24.08.2026) — ТЕКУЩАЯ: деление длинных слов стало условным

**Найденный баг (скрин `img.png`, карточка 231 «Подарок английского: одна форма на всех», таблица
`Кто | Форма`):** во всех строках колонки «Форма» слово `remembered` разорвано на `remem / bered`,
хотя в таблице всего 2 колонки и места на экране вагон. Раскладка тут ни при чём: `remembered` —
10 букв > `MAX_WORD_LEN`, и `wrapLongWords` резал его БЕЗУСЛОВНО, ещё до замера. Дальше
`columnWidths` честно мерил уже испорченный текст и давал колонке ширину под `bered`.

Причина в самом правиле п.4: деление задумано как размен «узкая колонка под длинный ярлык →
отдать место соседям», но применялось всегда, в том числе когда соседям место не нужно.

**Что изменено (логика распределения итераций 2–3 не тронута, только момент применения деления):**
`columnWidths` разделена на два чистых шага — `measureColumns` (min/ideal) и `distributeWidths`
(раздача ширины), а поверх них `layoutTable` делает два прохода:
1. меряем СЫРОЙ текст (без деления);
2. `Σ min ≤ ширины экрана` → таблица влезает нерезаной → рендерим как есть, деления нет;
3. не влезает → применяем `wrapLongWords` и меряем заново — дальше ровно поведение итерации 3
   (включая fallback «шире экрана → масштабируем пропорционально min»).

**Почему не ломает рабочее:** все случаи, где деление реально спасало («Местоимение»/«Притяжательное»
рядом с колонкой предложений), по сырым словам за экран не влезают → идут веткой 3 и считаются как
раньше, один в один. Инвариант «слово не рвётся посреди букв» держится и в новой ветке 2: min-ширина
колонки ≥ ширины целого слова тем же стилем + `MEASURE_SLACK`.

**Осознанный компромисс:** в пограничном случае (таблица влезает нерезаной еле-еле) колонка с длинным
ярлыком теперь берёт ровно свой min, и соседняя колонка с предложениями может перенестись на строку
больше, чем раньше. Приняли: лишняя строка переноса ПО ПРОБЕЛУ — норма, разрыв слова посреди букв —
нет. Если где-то это выглядит плохо — правится контентом (короче ячейка), не порогом.

**Отклонено:** просто поднять `MAX_WORD_LEN` до 11–12 — затыкает конкретное слово, а не класс
проблемы (следующее `understanding` порежется так же), и одновременно ослабляет порог там, где
деление нужно. Порог — не та ручка.

### Итерация 5 (05.09.2026) — ТЕКУЩАЯ: прицельное ужатие вместо сжатия ниже минимума

**Найденный баг (скрин `img.png`, карточка 486 «Шаг назад по времени = шаг от реальности», таблица
на 5 колонок):** заголовки разорваны как `Результа/т` и `Приме/р`, тело — `Нулево/й`, `настояще/е`,
`случитьс/я`. Сиротские 1–2 буквы по всей таблице, то есть прямое нарушение главного правила.

Резал НЕ `wrapLongWords` — он к этим словам не притрагивался: `Результат`, `настоящее`, `прошедшее`
ровно по 9 букв, а делится только слово **строго длиннее** `MAX_WORD_LEN`. Рвал сам Compose, потому
что сработала аварийная ветка `distributeWidths` («контент шире экрана → масштабируем пропорционально
min»): пять колонок дают Σ min ≈ 400dp против ≈ 330dp экрана, каждая колонка получала МЕНЬШЕ ширины
своего самого длинного слова, и Compose доламывал слова по символам где придётся. Ветка эта known
issue с итерации 1 и до сих пор списывалась на контент — но по скану сидов в неё попадает **15 таблиц
курса**, так что это класс проблемы, а не разовый случай.

**Что изменено — только третья ветка; пути «влезло сырым» и «влезло после деления ярлыков» не
тронуты вообще.** Это и есть гарантия безопасности: таблица, которая сегодня выглядит хорошо, в
новый код не заходит, а все, кто заходит, сегодня заведомо сломаны.

1. `splitWord(word, maxLen)` — общий чанкер: делит **сбалансированно** (куски отличаются не больше
   чем на букву) и ограничивает число частей так, чтобы кусок был не короче `MIN_CHUNK_LEN` (=3).
   Слово, которое нельзя поделить с соблюдением порога, остаётся целым. Для старого порога 9 новый
   чанкер даёт результат, идентичный прежнему `chunked(size)`, на всех словах длиной 10–18; расходится
   с 19 букв, а одиночных ячеек-слов такой длины в курсе нет ни одной (проверено скриптом по сидам) —
   то есть на текущем контенте замена доказуемо ничего не меняет.
2. `squeezeColumns(...)` — новый третий проход вместо падения в аварийное сжатие. Колонки
   обрабатываются **по возрастанию `ideal`**: первыми ужимаются колонки-ярлыки (потеря ширины им
   дешевле всего), колонки с предложениями — последними и на практике не трогаются вовсе. Каждой
   колонке понижается допустимая длина куска (8 → 3), и как только таблица влезла — **останов**;
   поэтому остальные колонки остаются нетронутыми и забирают освободившееся место обычной раздачей
   по дефициту (итерация 2). Освободившееся место достаётся колонке с самым большим дефицитом —
   как правило, колонке с примерами, что и требовалось.
3. Колонка не мельчится впустую: если понижение порога перестало давать выигрыш по ширине, в конце
   применяется **самое крупное** деление из тех, что дали лучшую ширину. Без этого пункта колонка
   «После if» доезжала до `нас/тоя/щее`, хотя её ширину держало слово `После` и хватало `насто/ящее`.
4. В третьем проходе делятся слова и **внутри многословных ячеек** (иначе `случиться` внутри
   «реально может случиться» не даёт колонке ужаться). Правило «предложения не делим» (п.5 требований)
   остаётся в силе для первых двух проходов: в третьем выбор стоит не между «целым словом» и
   «разрезанным», а между «разрезанным осмысленно» и «разрезанным Compose как попало».
5. Режем всегда ИСХОДНЫЙ текст ячейки, а не результат второго прохода: там перенос уже проставлен
   как `\n`, и повторное деление склеило бы куски слова через пробел (`Притяжа тельное`).
6. `measureColumns` разделена на `measureColumns` (все колонки) и `measureColumn` (одна) — третьему
   проходу нужен перезамер одной колонки, а источник правды по замеру должен остаться один.

Аварийное пропорциональное сжатие в `distributeWidths` **оставлено** как последний рубеж (таблица
колонок на десять). Реально недостижимо: при кусках по 3 буквы пять колонок дают ≈195dp против
≈330dp экрана.

**Проверено до сборки:** симуляция алгоритма прогнана по всем таблицам всех сидов курса — 15 таблиц
уходят в третий проход, сирот короче 3 букв не остаётся нигде, ни одна таблица не остаётся шире
экрана (то есть аварийная ветка не срабатывает ни разу).

### Известная неточность замера (осознанно принята 10.07.2026, НЕ чинить)

При ideal-замере (`widestPiece`, split по `\n`) строка ячейки меряется целиком одним стилем, и
проверка примитивная: есть в строке `*` → вся строка меряется ЖИРНЫМ. Строка вида `**жирное** обычный
хвост` замеряется шире реальной (жирным меряется и нежирный хвост) → ideal колонки слегка завышен.
Последствие микроскопическое: излишек ширины таблицы раздаётся между колонками чуть не в той
пропорции (пиксели, глазом не видно). На инвариант «слово не рвётся» НЕ влияет — он держится
отдельным min-замером, а тот точный (меряет по словам). Честный фикс — мерить строку кусками по
стилям — усложнение кода ради невидимого результата; решено не делать (Fable-ревью 10.07.2026).

## Точки настройки (если что-то не так визуально)

- `MAX_WORD_LEN` (порог деления одиночного слова; сейчас 9). Больше → меньше делений (длинные ярлыки
  в одну строку, колонки шире). Меньше → агрессивнее делим.
- Боковой отступ ячейки (`spaceSmall`).
- Стили измерения (14sp: заголовок bold, тело regular, куски с `*` — bold) — с итерации 3 строятся
  merge-ом поверх `LocalTextStyle.current`, чтобы совпадать с рендером `TableRow` вплоть до
  letterSpacing; если поменяется шрифт/размер таблиц — обновить merge и здесь.
- `MEASURE_SLACK` (сейчас 1dp) — запас на округления px↔dp; если снова где-то выпадет буква —
  первым делом проверить, не разошёлся ли стиль замера с рендером, а не крутить slack.
- Распределение `extra`: с итерации 2 — пропорционально дефициту `ideal − min` (потолок ideal),
  излишек сверх Σ ideal — пропорционально ideal. (В итерации 1 было пропорционально min — давало
  перекос, см. историю выше.)
