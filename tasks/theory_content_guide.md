# Theory Content Guide — Grammar8r

Правила и принципы написания теоретического контента.  
Читать перед написанием любой новой микротемы.

**Связанные документы:**
- [`exercise_templates.md`](phases/phase1/exercise_templates.md) — форматы всех 14 типов упражнений + DB-схемы

- [`db_schema.md`](db_schema.md) — схемы таблиц Room, ENUM-ы

## 1. Как работают ID

### Type-specific ID (реальные DB-идентификаторы)

Каждый тип упражнения нумеруется **независимо от 1**. `WordArrangement(id=1)` и `TrueFalse(id=1)` — разные упражнения, конфликта нет.

ID уникален внутри своего типа. Именно этот ID пишется в `CardExerciseIndex` и используется в БД. Это единственные ID которые имеют значение для приложения.

### Глобальный Ex N (только навигация)

`**Ex 47 · TrueFalse**` — номер 47 нужен только чтобы читать файл и ссылаться на упражнение в разговоре. В БД не хранится. Может быть непоследовательным из-за реорганизации карточек — это нормально.

### AI Exercise ID

Строковый, не числовой: `basics_card{N}_ex1` где N — номер карточки.  
Пример: карточка 29 → `basics_card29_ex1`. Числовой счётчик для AI не ведётся.

### Где живут счётчики

В конце каждого theory-файла — таблица со значениями **последнего использованного ID** по каждому типу. Перед написанием нового блока — прочитать эту таблицу и продолжить с "Следующий" значений. После написания — обновить таблицу.

### 🔢 Единый канон ID (между темами) — `theory/_id-registry.md`

ID **сквозные по всему курсу** и не должны пересекаться: `Microtopic`/`Card`/`Topic` — глобально уникальны; ID упражнений — уникальны **внутри своего типа** по всем темам; `course_word` — глобально уникальны и стабильны.

Канон — файл **`tasks/phases/phase1/theory/_id-registry.md`**, который **генерируется скриптом** `tools/test/id_report.py` из всех сидов (руками не править — выведен из данных, поэтому всегда точный).

**⚠️ Каждый раз тщательно сверять ID, чтобы не пересекались и были консистентны:**
1. **Перед** написанием новой темы — открыть `_id-registry.md` → раздел «Next free». Эти числа = откуда продолжать каждый тип (Microtopic, Card, WordArrangement, MultipleChoice·CHOICE и т.д.).
2. **При** написании — проставлять ID руками от этих значений (страховка; пишем аккуратно, без дыр и наложений), и вести таблицу счётчиков в конце файла.
3. **После** написания и конвертации — прогнать `py test/id_report.py`: он пересоберёт канон и покажет **коллизии** (если один id попал в двух местах). Должно быть `id collisions: 0`.

### ⚠️ ОДНА таблица счётчиков — всегда в конце файла

В файле всегда **одна** секция `## Счётчики IDs для продолжения` — в самом конце.

**Как добавлять новый блок или микротему:**
1. Вставить новый контент **перед** секцией `## Счётчики IDs`
2. Обновить **значения** в существующей таблице на месте — не создавать вторую

**Никогда** не добавлять вторую секцию `## Счётчики IDs`. Если в файле их больше одной — это ошибка: лишние удалить, оставить только ту что в конце с актуальными значениями.

## 2. Структура theory-файла

### Шапка файла темы (обязательная)

Каждый theory-файл начинается с шапки темы (пример — `01-basics.md`):
```
# N Title EN · Название RU

**ID:** N | **Order:** N | **isPretopic:** true       ← isPretopic только у «Основ»
**Описание:** краткое описание темы (1 строка)
**Группа слов:** group_id · Название группы
**Категория слов:** category_id · Название · source=course_words
```
- `# N Title · RU` — N = `GrammarTopic.id` (из канона `_id-registry.md` → Next free Topic).
- `**ID:** / **Order:**` — id и порядок темы. `**isPretopic:** true` — ТОЛЬКО для «Основ», у остальных строки нет.
- `**Описание:**` → `GrammarTopic.description`.
- `**Группа слов:**` → раздел Словаря (`course_word_groups`): `id · Название`.
- `**Категория слов:**` → категория по умолчанию для слов темы (`course_categories`): `id · Название · source=course_words`
  (где source = `course_words` или `irregular_verbs`). Все Words8r Sync файла идут в неё, если в секции не указано иное.

В самом конце файла — **одна** таблица `## Счётчики IDs для продолжения` (см. раздел 1).

### Что писать дальше

Список микротем и их порядок — в `grammar8r_plan.md` → раздел структуры соответствующей темы. Перед написанием: найти последнюю написанную микротему в файле и взять следующие по списку.

### Блоки

Каждые 3 микротемы оборачиваются в блок:
```
# БЛОК N · Микротемы X–Y
```

### Микротема

```
## Microtopic N — Title EN · Title RU

**ID:** N | **Order:** N

---

[карточки]

### Words8r Sync · Название раздела
| Слово | Переводы | Транскрипция |
```

### Карточка

```
### Card N · Название карточки

**ID:** N | **Order:** N

#### Theory
[теория]

#### Summary *(кнопка «?» в упражнениях)*
[2–3 предложения — краткий конспект правила]

#### Examples
| # | RU | EN |
|---|----|----|
| N | Русский пример. | English example. |

---

#### Exercises
[упражнения]

---

#### AI Exercise
[AI упражнение]

#### Clarification Options
- Вопрос 1?
- Вопрос 2?
- Вопрос 3?

---
```

### Карточка без упражнений

Иногда карточка содержит только теорию — без упражнений. Это нормально для справочных карточек (например, "Почему дни пишутся с заглавной"). В таком случае секция `#### Exercises` опускается, но `#### Clarification Options` остаётся.

## 3. Правила теории

### Главный принцип: объяснять, а не называть

Плохо: *"Несчётные существительные не имеют множественного числа."*  
Хорошо: *"Представь что advice — это не штука, а вещество. Как воду нельзя посчитать ('три воды' звучит странно), так и advice нельзя: 'three advices' — ошибка. Можно только 'three pieces of advice'."*

Пользователь после каждой карточки должен думать **"О, вот оно что!"** — а не "ещё одно правило".

### Объяснять через сравнение с русским

Не просто "в английском так", а почему это логично и откуда берётся ошибка у русскоязычного.

Шаблон объяснения:
1. Как это работает в русском (что привык делать пользователь)
2. Почему английский работает иначе
3. Конкретная ловушка которая из этого вытекает

Примеры:
- *"По-русски 'я знаю' и 'я знал' — один глагол с разным окончанием. В английском это два разных слова: know и knew. Мозг хочет добавить -ed к know — не выйдет."*
- *"По-русски 'мне холодно' — от ощущения. По-английски 'I am cold' — от субъекта. Дословный перевод 'to me cold' — бессмыслица."*

### Разжёвывать максимально подробно

Одно правило — одна карточка. Нюанс внутри правила — отдельная карточка.  
Лучше 3 понятные карточки чем 1 перегруженная.

Каждое утверждение подкрепляется примером. Каждое исключение объясняется — не просто "запомни", а почему оно такое.

Если есть логика даже за исключением — объяснить её:  
*"Почему 'at night', а не 'in the night'? Ночь воспринимается как особый момент темноты, а не период с чёткими границами — отсюда точечный 'at'."*

### Переводить все английские примеры

**Сейчас (начало курса, пользователь не знает английского):** переводить абсолютно всё — каждое слово, каждую фразу, каждое предложение.

> ⚠️ Ближе к середине курса, когда база накоплена, переводы в упражнениях могут убираться. Делать это только по явной команде. Пока команды не было — всегда переводить.

Форматы перевода:
- В таблице Examples: отдельная колонка RU
- В тексте теории: курсив или скобки после примера

```
"I have been waiting for an hour." — *Я жду уже час.*
walk over a hill *(подняться на холм и спуститься)*
```

### Ловушки — конкретно

Каждая ловушка: сломанный пример ✗ + правильный вариант ✓ + объяснение почему.

```
"I need an advice." ✗ → "I need some advice." ✓  
advice — несчётное, артикль a/an с ним невозможен.
```

Не писать просто "это ошибка" — писать откуда берётся ошибка.

### Clarification Options — что это

Заранее написанные вопросы для фичи "Не совсем понял" в конце каждой карточки. Пользователь тапает на вопрос → он уходит в AI → AI объясняет то же правило другими словами и с другим примером (не повторяет теорию карточки).

Писать 2–3 вопроса которые реально могут возникнуть у пользователя после прочтения карточки. Не общие ("расскажи про это правило"), а конкретные ("Почему 'at night', а не 'in the night'?").

### Разнообразие имён в примерах

Чередовать: Дима, Лена, Игорь, Катя, Рома, Саша, Вера, Тёма, Оля, Коля, Миша, Ира.  
Не повторять одно имя несколько раз подряд в одной карточке. Максим и Анна — избегать.

### Живые примеры

Примеры из реальной жизни, а не учебниковые. Не "The cat is on the mat" — а ситуации которые пользователь узнаёт:
- рабочий чат, кофейня, поездка, телефонный разговор
- эмоции, планы, бытовые действия

## 4. Упражнения

### Главный источник правил

**→ [`exercise_templates.md`](phases/phase1/exercise_templates.md)**

Там: форматы всех 14 типов, DB-схемы, правила explanation.

### Формат заголовка упражнения

```
**Ex N · [Точное имя типа]** *(ID: X)*
```

Имя типа — **точно как в таблице счётчиков** в конце theory-файла:

`WordArrangement` · `MultipleChoice · CHOICE` · `MultipleChoice · FORWARD_CHOICE` · `MultipleChoice · REVERSE_CHOICE` · `TrueFalse` · `ErrorCorrection` · `TextInput` · `Matching` · `Transformation` · `Categorization` · `TableFill` · `FindTheOdd` · `ConstructionMeaning` · `DialogRestore`

Примеры правильных заголовков:
```
**Ex 47 · TrueFalse** *(ID: 26)*
**Ex 48 · MultipleChoice · FORWARD_CHOICE** *(ID: 40)*
**Ex 49 · WordArrangement** *(ID: 27)*
```

### TrueFalse — формат утверждений

Каждое утверждение — **реальное предложение на английском** (+ русский перевод), часть из которых содержит грамматическую ошибку. Пользователь сам определяет: правильно или нет.

**Запрещено** писать мета-утверждения вроде `"Please" is a correct answer to "Thank you."` или `"Many" is used with uncountable nouns.` — это не тест на понимание грамматики, а тест на знание правил в абстракции. Вместо этого — конкретное предложение, которое либо грамматически верно, либо содержит ошибку:

❌ Плохо: `"I have some good news." is correct.`
✓ Хорошо: `I have some good news.` — *У меня есть хорошие новости.* — ✓

❌ Плохо: `"Please" is a correct answer to "Thank you."`
✓ Хорошо: `— Thank you! — Please.` — *— Спасибо! — Пожалуйста.* — ✗

### Ключевые правила кратко

**1 вопрос = 1 упражнение** для типов: `MultipleChoice · CHOICE`, `MultipleChoice · FORWARD_CHOICE`, `MultipleChoice · REVERSE_CHOICE`, `ErrorCorrection`, `ConstructionMeaning`, `DialogRestore`, `FindTheOdd`.

Упаковка нескольких вопросов в один `Ex N` — ошибка. Каждый вопрос получает свой `Ex N` и свой type-specific ID.

**Разнообразие обязательно.** На одну карточку — разные типы. Не делать подряд 3 MultipleChoice. Использовать менее частые типы: `Transformation`, `Categorization`, `FindTheOdd`, `Matching`, `ConstructionMeaning`, `DialogRestore` — они дают разные форматы взаимодействия.

**Прогрессия сложности:** в рамках одной карточки сначала выбор (CHOICE/FORWARD_CHOICE), потом ввод (TextInput/WordArrangement).

**Варианты** — только в формате:
```
- Вариант
- **Правильный вариант** ✓
- Вариант
```
Никакого `a) ... ✗ / b) ... ✓`.

**Дистракторы** — реалистичные ошибки, не абсурд. Дистрактор должен быть именно той ошибкой которую реально совершает русскоязычный.

### ErrorCorrection vs FORWARD_CHOICE — критичное различие

**ErrorCorrection** — условие задания содержит только **сломанное английское предложение**, без русского перевода.  
Пользователь читает EN и находит ошибку.

**FORWARD_CHOICE** — условие задания содержит **русское предложение** (или русский контекст), пользователь выбирает правильный EN вариант.

> Правило: если для понимания задания нужен русский контекст → FORWARD_CHOICE. Если ошибка видна из самого EN предложения → ErrorCorrection.

Никогда не добавлять русский перевод в условие ErrorCorrection — это нарушение формата.

### TrueFalse — детали формата

Всегда ровно **5 утверждений**. Обязательно минимум **2 верных** и **2 неверных** (пятое — любое).

**Сейчас (начало курса):** таблица с тремя колонками — EN, RU-перевод, Верно?:
```
| # | EN | RU | Верно? |
|---|----|----|--------|
| 1 | He go to work every day. | Он ходит на работу каждый день. | ✗ |
```

> ⚠️ Ближе к середине курса колонка RU может убираться — делать только по явной команде.

### WordArrangement — тире для знакомых слов

Слово считается **знакомым** если оно уже было дано к изучению и добавлено в словарь в Words8r Sync предыдущих карточек этого же файла.

В таблице слов: знакомые слова получают `—` вместо перевода (пользователь тапает на слово в приложении и получает перевод). Новые слова — полный перевод.

```
| Слово     | Перевод          | Лишнее? |
|-----------|------------------|---------|
| jumped    | прыгнул          | —       |  ← новое слово
| the box   | —                | —       |  ← знакомое слово
| into      | в (внутрь)       | ✗       |  ← дистрактор (новое)
```

## 5. AI упражнения

**Главный источник:** `grammar8r_plan.md` → раздел "AI-упражнения — модель данных и флаги"

### Обязательные поля

```
**ID:** basics_card{N}_ex1
**Title:** "Глагол + объект"
**Input Mode:** FREE_WRITE / FILL_BLANKS
**Words Source:** NONE
**AI Config Profile:** EXERCISE_LIGHT
**User Instruction:** "Что делать пользователю — без технических деталей"
**Prompt Template:** "... Пример вывода AI: 'конкретный текст'"
```

### Критичные правила

- `User Instruction` — только что делать. Без слов "AI", "FILL_BLANKS", технических деталей.
- `Prompt Template` **обязательно** заканчивается строкой `Пример вывода AI: '...'` с реальным примером текста который AI выдаст пользователю. Без этого нельзя проверить корректность задания.
- Ошибки AI объясняет **по-русски**, кратко, конкретно.
- `Words Source: NONE` для предтемы "Основы" (слов ещё мало). `GENERAL` — для тем где слова уже накоплены.
- `FILL_BLANKS` — когда AI присылает текст с пропусками `[___]`. `FREE_WRITE` — всё остальное.

## 6. Words8r Sync

В конце каждой **микротемы** (не карточки) — таблица слов для добавления в словарь:

```
### Words8r Sync · Краткое название

| Слово | Переводы | Транскрипция |
|-------|----------|-------------|
| word  | перевод  | [транскрипция] |
```

Включать: ключевые слова микротемы которые пользователь должен запомнить.  
Не включать: служебные слова уже изученные в предыдущих микротемах.  
Не включать: производные формы, которые логически вытекают из базовой. Если пользователь знает базу и может сам вывести форму — не добавлять.

> ⚠️ **ОБЯЗАТЕЛЬНО: никаких дублей слова внутри одной категории.**
> **Критерий дубля = одинаковое написание И одинаковый перевод** в одной категории. Перед
> добавлением проверить, не сливалось ли это слово с тем же переводом в Sync этой же категории
> раньше. Если да — НЕ добавлять второй раз (дубль в Словаре = путаница, два прогресса на одно слово).
> - **Разный перевод → НЕ дубль, оставляем.** Омонимы (`am` глагол vs `am`=a.m.; `past`=мимо vs
>   `past`=прошло) — это разные слова, оба остаются.
> - Дубли в **разных** категориях — допустимо (разные наборы для разных кнопок).
> Проверка на дубли (слово+перевод) в одной категории — часть самопроверки (раздел 9).

> **Пример:** `can` — добавить. `can't` / `cannot` — НЕ добавлять: отрицание очевидно из `can + not`.  
> Критерий: "Нужно ли учить это как отдельное слово, или оно выводится из уже известного?" Если выводится — не добавлять. (Но всякие слова с разным исуфиксами надо сливать, типа лучше спроси меня, а я скажу уже надо или нет)

## 8. Строгий MD-формат для конвертера (machine-readable) ⚙️

> ⚠️ **Зачем это.** Теория хранится в БД не строкой, а массивом **типизированных блоков**
> (`paragraph` / `heading` / `list` / `table` / `callout` — см. `db_schema.md` → «Блоки теории»).
> Скрипт-конвертер превращает MD → JSON-блоки **по разметке, а не по смыслу слов**. Поэтому
> разметка обязана быть единой: одинаковая мысль — одинаковое оформление во всех карточках.
> Несоблюдение → блок распарсится не тем типом → кривой рендер у пользователя.

### Как скрипт определяет тип блока внутри `#### Theory`

| Пишем так | Тип блока |
|-----------|-----------|
| Обычная строка прозы | `paragraph` |
| Строка **целиком** в болде: `**Краткие ответы:**` или `**also — "также"**` | `heading` |
| `**Ярлык:** текст на той же строке` (после `:**` есть тело) | `callout` |
| Строки на `- ` или `1. ` подряд | `list` (один блок) |
| Строки на `\| … \| … \|` подряд (с разделителем `\|---\|`) | `table` (один блок) |

**Правило-различитель heading vs callout (железное):** если после закрывающего `**` на строке
**ничего нет** — это `heading`. Если есть тело — это `callout`. Не нарушать: не писать ловушку
целиком внутри `**…**`, иначе она станет заголовком, а не плашкой.

### Канонические формы (писать ТОЛЬКО так)

**callout — врезка-плашка.** Формат: `**Ярлык:** текст.` Variant определяется по ярлыку:

| Ярлык (ключевое слово) | variant | Рендер |
|------------------------|---------|--------|
| Ловушка | `trap` | красная плашка |
| Не путай / Важно / Осторожно | `warning` | оранжевая плашка |
| Кстати / Запомни / Маленький секрет | `tip` | нейтральная плашка |
| Формула | `formula` | моноширинный бокс |
| любой другой | `note` | нейтральная |

**heading — подзаголовок секции.** Строка целиком в болде, обычно с `:`. Дальше идёт его тело
(`list`/`table`/`paragraph`). Пример: `**Краткие ответы:**`, затем список.

**Контраст ✗ / ✓ — это инлайн, НЕ блок.** Пишется внутри `paragraph`, `list` или `callout`:
- Инлайн: `"I too like pizza." ✗ → "I like pizza, too." ✓`
- Списком: `- "Me too!" ✓ — правильно` / `- "Me also!" ✗ — так не говорят`

Рендер сам красит `✓` зелёным, `✗`/`❌` красным. Не заводить под это отдельную структуру.

**Инлайн-разметка внутри текста любого блока — только два маркера:**
- `**жирный**` — выделение;
- `*курсив*` — перевод английского примера (`*Я жду уже час.*`) или пояснение в скобках.

Никакого другого markdown внутри строки (ссылок, вложенных таблиц, заголовков `#`). Структура —
только на уровне блоков.

### Якоря карточки (скрипт ключуется на них дословно)

```
### Card N · Заголовок
**ID:** N | **Order:** N
#### Theory            → блоки до следующего ####
#### Summary *(кнопка «?» в упражнениях)*   → текст в поле summary
#### Examples          → таблица | # | RU | EN |  → JSON examples
#### Exercises         → блоки **Ex N · Тип** *(ID: N)*
#### AI Exercise       → РАЗДЕЛЯЕТСЯ конвертером на client seed + server seed (см. ниже)
#### Clarification Options   → список  -   → JSON clarificationOptions
### Words8r Sync · …    → таблица | Слово | Переводы | Транскрипция |  → строки course_words
```

Заголовок упражнения — строго `**Ex N · ТочноеИмяТипа** *(ID: N)*` (имена типов — раздел 4).
Варианты ответа — строго `- Вариант` / `- **Правильный** ✓`. Опция-«прочерк» пишется как `- —`.

> ⚙️ **Точный парсер-контракт каждого из 12 типов упражнений** (как именно оформлять, чтобы
> конвертер не переделывать) — в [`exercise_templates.md`](phases/phase1/exercise_templates.md) →
> раздел «Эталонный MD-формат для конвертера». Там образец + поля DB для каждого типа.

### AI Exercise — конвертер делит блок на ДВА выхода ⚠️

Промт — секрет, в APK его быть не должно. Поэтому из `#### AI Exercise` конвертер пишет два места:

| Поле в MD | Куда |
|-----------|------|
| `ID`, `Title`, `Input Mode`, `Words Source`, `User Instruction` (+ `cardId` от карточки) | **client seed** → content.db `ai_exercises` |
| `Prompt Template`, `AI Config Profile` | **server seed** (`prompts_seed.json`) → серверная `ai_exercise_prompts`, в APK НЕ идёт |

Связь — по `id` (`basics_card1_ex1`): клиент шлёт серверу только id, сервер по нему берёт промт+профиль.
В MD по-прежнему пишем ВСЕ поля рядом (удобно ревьюить) — разделяет их конвертер, не автор.

### Words8r Sync → `course_words` (конвертер сидирует слова автоматически)

Конвертер тянет слова не только в теорию, но и в **БД-заготовку слов** — из таблиц
`### Words8r Sync · …`. Искать слова вручную потом не нужно.

**Откуда категория/группа.** Объявляются **в шапке theory-файла** (один раз на тему):

```
**ID:** 1 | **Order:** 1 | **isPretopic:** true
**Группа слов:** basics · Основы
**Категория слов:** grammar_basics · Grammar Basics · source=course_words
```

**Категория задаётся НА ТЕМУ** (одна на весь файл). Для предтемы «Основы» это `grammar_basics`:
все слова всех 15 микротем `01-basics.md` идут в `grammar_basics` — по микротемам ничего
указывать не нужно. В других темах будет своя категория (Present Simple → basic_verbs и т.д.).

> ⚠️ Редкий случай: если в будущей теме ОДНА микротема должна открывать слова в ДРУГУЮ
> категорию (тема с несколькими категориями, напр. Времена → Basic Verbs + Verb Forms) —
> переопределить точечно в заголовке секции. Это исключение, не правило:
> ```
> ### Words8r Sync · Неправильные глаголы [category: verb_forms]
> ```

**Что парсит конвертер из таблицы** `| Слово | Переводы | Транскрипция |`:
- `word` ← Слово, `translation` ← Переводы, `transcription` ← Транскрипция;
- `microtopicId` ← id текущей микротемы (ключ открытия);
- `categoryId` ← категория секции/темы; `id` ← присваивается **детерминированно и стабильно**
  (чтобы не осиротел прогресс в user.db при пересборке content.db).

Правила содержания Words8r Sync (что включать/не включать) — раздел 6.

## 9. Самопроверка формата после написания (обязательный шаг)

### 🔄 Рабочий цикл написания темы (КАНОН)

1. **Пишем 1–3 микротемы** по эталонам (раздел 8 + `exercise_templates.md`: эталоны и «❌ Антипаттерны»).
2. **Claude отдельным проходом проверяет СВОЁ оформление** по чеклисту ниже (до показа пользователю).
3. **Пользователь делает ревью** содержания.
4. **Правки** вносятся вместе с пользователем.
5. **⚠️ ТОЛЬКО после явного одобрения и явной команды пользователя** — прогон `py check.py <файл>`.
   **Claude НЕ запускает тесты сам** (ни после написания, ни после правок) — ждёт явной команды.
6. `ALL GREEN` → коммит / следующие микротемы.

> Разделение «пишу → ревью → правки → (по команде) тесты» резко снижает ошибки и не гоняет
> скрипты вхолостую. Тесты — финальный шаг, и только по слову пользователя.

Что проверять на шаге 3 (по каждой новой карточке):
- [ ] Каждая ловушка — `**Ловушка:** тело` (тело снаружи болда), а не целиком в `**…**`
- [ ] Подзаголовки секций — строка целиком в болде; после `**` ничего нет
- [ ] Контраст оформлен инлайн через `✗ / ✓`, не как отдельная самопальная структура
- [ ] Внутри строк только `**жирный**` и `*курсив*` — иного markdown нет
- [ ] Все якоря `#### …` на месте и названы дословно (Theory/Summary/Examples/Exercises/AI Exercise/Clarification Options)
- [ ] Таблицы имеют строку-разделитель `|---|`; списки начинаются с `- ` или `1. `
- [ ] Заголовки упражнений строго `**Ex N · Тип** *(ID: N)*`; варианты `- ` / `- **…** ✓`
- [ ] Английские примеры переведены (раздел 3); имена чередуются (раздел 3)

Если что-то не по формату — править ДО сдачи на конвертацию. Конвертер падает громко на
нарушениях, но дешевле поймать их этим чеклистом, чем гонять скрипт по сломанному файлу.

> ⚠️ **Перед написанием упражнений — перечитать «❌ Антипаттерны» в [`exercise_templates.md`](phases/phase1/exercise_templates.md).**
> Это список конкретных ошибок оформления, которые ломают парсинг (мета-TrueFalse, перемешанный
> Matching, `___` в TableFill, italic-обёртки, `*Explanation: …*`, аннотации в FindTheOdd и т.д.).

**После ревью и правок — ОДНА команда прогоняет всё** (из `tasks/tools/`):
```
py check.py <путь-к-теме.md>
```
Она пересобирает сид и гоняет все проверки, выдавая сводку:
```
VALIDATION (типы/ограничения) : PASS
DEEP (дубли/enum/explanation) : PASS
ID collisions                 : PASS
SMELL (мусор)                 : N  (легит-стрелки/слэши — глянуть глазами)
GAPS (инфо, не баг)           : N
=> ALL GREEN ✓
```
Рабочий цикл: написал 1–3 микротемы → ревью с пользователем → правки → **`py check.py <файл>`** →
`ALL GREEN` → коммит/дальше. Если не GREEN — скрипт печатает детали, чинить и перегнать.
(Отдельные скрипты — `test/deepcheck.py`, `test/smell.py`, `test/id_report.py`, `test/verify_dump.py <ids>` — для точечной диагностики.)

## ⚙️ Памятка против «гниения контекста» при написании теории

Держать в голове постоянно (перечитать перед каждой новой микротемой):
1. **Пишу блоками раздела 8.** Ловушка = `**Ловушка:** тело`. Подзаголовок = вся строка в болде.
   Контраст = инлайн `✗/✓`. Внутри строки только `**…**` и `*…*`.
2. **Якоря `#### …` дословно** — иначе скрипт не найдёт секцию.
3. **ID по типам** — продолжаю с таблицы счётчиков в конце файла (раздел 1), обновляю её.
4. **Перевожу все английские примеры** (раздел 3), **чередую имена** (раздел 3).
5. **После написания — самопроверка раздел 9**, отдельным проходом, до конвертера.
6. **⚠️ ПРАВИЛО ДЛЯ CLAUDE: после ЛЮБОЙ правки уже готовой теории, для которой есть seed —
   ОБЯЗАТЕЛЬНО явно напомнить пользователю: «нужно запустить `py md_to_json.py <файл>`,
   иначе JSON-сид устареет относительно MD».** Скрипт ручной, забыть легко, а теорию правим
   вместе — поэтому напоминание о перезапуске лежит на Claude при каждой такой правке.
