Правила и принципы написания теоретического контента.  
Читать перед написанием любой новой микротемы.

**Связанные документы:**

## 1. Как работают ID

### Type-specific ID (реальные DB-идентификаторы)

Каждый тип упражнения нумеруется **независимо от 1**. `WordArrangement(id=1)` и `TrueFalse(id=1)` — разные упражнения, конфликта нет.

ID уникален внутри своего типа. Именно этот ID пишется в `CardExerciseIndex` и используется в БД. Это единственные ID которые имеют значение для приложения.

### Глобальный Ex N (только навигация)

`**Ex 47 · TrueFalse**` — номер 47 нужен только чтобы читать файл и ссылаться на упражнение в разговоре. В БД не хранится. Может быть непоследовательным из-за реорганизации карточек — это нормально.

### AI Exercise ID

Строковый, не числовой: `<topic>_card{N}_ex{K}` где N — номер карточки, K — номер AI на этой карточке.  
Пример: карточка 29 → `basics_card29_ex1`. На карточке может быть **1, 2 или 3** AI-упражнения
(`_ex1`, `_ex2`, `_ex3`) — или **ни одного**. Числовой сквозной счётчик для AI не ведётся —
нумерация `_exK` локальна внутри карточки.

### Где живут счётчики

В конце каждого theory-файла — таблица со значениями **последнего использованного ID** по каждому типу. Перед написанием нового блока — прочитать эту таблицу и продолжить с "Следующий" значений. После написания — обновить таблицу.

### 🔢 Единый канон ID (между темами) — `theory/_id-registry.md`

ID **сквозные по всему курсу** и не должны пересекаться: `Microtopic`/`Card`/`Topic`/`Category` — глобально уникальны; ID упражнений — уникальны **внутри своего типа** по всем темам; `course_word` — глобально уникальны и стабильны.

> `Category` (`GrammarTopicCategory.id`) — отдельный трек, как `Topic`. Перед заведением нового
> раздела — смотреть `_id-registry.md` → Next free **Category**. Раздел объявляется в шапке
> каждой темы-пакета (см. «Темы внутри раздела» в разделе 2) — `id_report.py` агрегирует все
> объявления и проверяет что они согласованы (`category mismatch`, если разъехались).

Канон — файл **`tasks/phases/phase1/theory/_id-registry.md`**, который **генерируется скриптом** `tools/test/id_report.py` из всех сидов (руками не править — выведен из данных, поэтому всегда точный).

**⚠️ Каждый раз тщательно сверять ID, чтобы не пересекались и были консистентны:**
1. **Перед** написанием новой темы — открыть `_id-registry.md` → раздел «Next free». Эти числа = откуда продолжать каждый тип (Microtopic, Card, WordArrangement, MultipleChoice·CHOICE и т.д.).
2. **При** написании — проставлять ID руками от этих значений (страховка; пишем аккуратно, без дыр и наложений), и вести таблицу счётчиков в конце файла.
3. **После** написания — прогнать **`py check.py <файл>`** (из `tasks/tools/`): одна команда пересобирает сид и запускает все проверки разом, включая `id_report.py` (коллизии ID), deepcheck и smell. Должно быть `ALL GREEN ✓`. Запускать отдельные скрипты (`test/id_report.py`, `test/deepcheck.py` и т.д.) не нужно — только для точечной диагностики если `check.py` упал.

### ⚠️ ОДНА таблица счётчиков — всегда в конце файла

В файле всегда **одна** секция `## Счётчики IDs для продолжения` — в самом конце.

**Как добавлять новый блок или микротему:**
1. Вставить новый контент **перед** секцией `## Счётчики IDs`
2. Обновить **значения** в существующей таблице на месте — не создавать вторую

**Никогда** не добавлять вторую секцию `## Счётчики IDs`. Если в файле их больше одной — это ошибка: лишние удалить, оставить только ту что в конце с актуальными значениями.

## 2. Структура theory-файла

> 🗝️ **Структурный канон (запомни перед написанием любой темы):**
> - **Один файл = одна GrammarTopic.** В одном файле может быть несколько микротем — это норма.
> - **Папка-пакет (`03-language-structure/`) = один GrammarTopicCategory (раздел).** У раздела нет
>   своего файла — он объявляется в шапке каждого файла-темы внутри папки.
> - **Дерево в UI:** раздел → темы → микротемы → карточки. Нельзя пропускать уровни.
> - **Сколько микротем в теме?** Ориентир: 2–6. Если одна — пользователь проваливается в список
>   из одного пункта, что выглядит криво. Дели контент на микротемы сразу при написании.

### Шапка файла темы (обязательная)

Шапка у всех тем **общая** — один и тот же набор полей. Часть строк ситуативна и просто
**опускается**, если неприменима (`isPretopic` — только у «Основ», `Раздел` — только у тем
внутри раздела). Не нужно ничего писать «для общности» там, где поле не применяется — пустых
заглушек не оставляем, строку просто не пишем.

Полный вид (когда применимо всё), пример без раздела — `01-basics.md`:
```
# N Title EN · Название RU

**ID:** N | **Order:** N | **isPretopic:** true       ← isPretopic только у «Основ»
**Раздел:** R · Название раздела · order=K            ← только у тем ВНУТРИ раздела (см. ниже)
**Раздел · Описание:** Краткое описание раздела       ← идёт сразу следующей строкой за «Раздел»
**Описание:** краткое описание темы (1 строка)
**Теги:** тег, тег, тег                              ← скрытые теги поиска (см. ниже)
**Группа слов:** group_id · Название группы
**Категория слов:** category_id · Название · source=course_words
**Слова курса — стартовый ID:** N
```
- `# N Title · RU` — N = `GrammarTopic.id` (из канона `_id-registry.md` → Next free Topic).
- `**ID:** / **Order:**` — id темы и её порядок. Если тема внутри раздела — `Order` отсчитывается
  **внутри раздела** (своё пространство нумерации на каждый раздел), а не в общем списке.
  `**isPretopic:** true` — ТОЛЬКО для «Основ», у остальных строки нет.
- `**Раздел:**` / `**Раздел · Описание:**` — см. подраздел «Темы внутри раздела (категории)» ниже.
- `**Описание:**` → `GrammarTopic.description`.
- `**Теги:**` → `GrammarTopic.searchKeywords`. Скрытое поле поиска, пользователю не видно.
  Правила написания — подраздел «Теги для поиска» ниже. Строки нет → `null`, тема ищется
  только по заголовку.
- `**Группа слов:**` → раздел Словаря (`course_word_groups`): `id · Название`.
- `**Категория слов:**` → категория по умолчанию для слов темы (`course_categories`): `id · Название · source=course_words`
  (где source = `course_words` или `irregular_verbs`). Все Words8r Sync файла идут в неё, если в секции не указано иное.
- `**Слова курса — стартовый ID:**` — ⚠️ **обязательная строка для каждой темы с Words8r Sync**
  (включая первую — `01-basics.md` пишет `1`). `course_word.id` назначается конвертером
  автоматически по порядку появления слов в Sync-таблицах, но он должен быть **глобально
  уникален и стабилен** (см. раздел 1 → канон ID, `_id-registry.md` → Next free → `course_word`).
  Конвертер не может вычислить продолжение сам надёжно (темы пишутся и пересобираются в любом
  порядке) — поэтому стартовое значение объявляется явно, как и остальные ID. Перед написанием
  темы — посмотреть `_id-registry.md` → Next free → `course_word`, вписать это число сюда.
  ⚠️ Никогда не менять это число у уже изданной темы «задним числом» — сдвинет ID всех её слов
  и осиротит прогресс пользователей в user.db.

В самом конце файла — **одна** таблица `## Счётчики IDs для продолжения` (см. раздел 1).

### Темы внутри раздела (категории) — `GrammarTopicCategory`

> Полная схема — `db_schema.md` → `GrammarTopicCategory`. Здесь — как это пишется в MD.

Иногда несколько тем образуют один смысловой блок, и пользователю удобнее видеть их
свёрнутыми под общим заголовком, а не вперемешку с остальными темами в общем списке —
например «Устройство языка» (темы «Как думает английский язык», «Части речи», «Служебные
глаголы», «Глаголы V1/V2/V3», «Инфинитив»). Такой блок = **раздел** (`GrammarTopicCategory`).

⚠️ Вложенность — **только один уровень**: раздел → темы → микротемы → карточки. Раздела
внутри раздела не бывает.

**Когда заводить раздел (критерий, уточнён 06.08.2026).** Раздел нужен, когда несколько идущих
**подряд** тем образуют один замкнутый блок — как правило, пара «простое + длительное», закрытая
Compare-темой, или общая идея вроде «Устройство языка». Такие блоки и учатся пачкой, поэтому в
списке им место под одним заголовком. По этому критерию в разделы упакованы `Present: Simple и
Continuous` (id 3), `Past: Simple и Continuous` (id 4), `Future Simple: will и going to` (id 5) и
`Present Perfect: Simple и Continuous` (id 6).
Что разделом НЕ делаем: длинную цепочку разных тем подряд — просто чтобы «покороче было».

⚠️ **Название раздела — по составу, а не по времени вообще.** Именно `Present: Simple и Continuous`,
а не «Настоящее время»: Present Perfect и Present Perfect Continuous стоят в курсе намного позже, за
блоком будущего, а темы раздела обязаны идти подряд — раздел «Настоящее время» без половины
настоящих времён путал бы больше, чем плоский список. Перфекты стоят подряд там, где стоят, и
собраны в свой раздел `Present Perfect: Simple и Continuous` (id 6).

**Как объявляется.** У раздела нет своего MD-файла — он целиком объявляется прямо в шапке
**КАЖДОЙ** темы, которая в него входит (по аналогии с `Группа слов`/`Категория слов` —
повторяем во всех файлах раздела, так каждый файл самодостаточен для ревью):
```
**Раздел:** 1 · Устройство языка · order=1
**Раздел · Описание:** Как устроен английский язык на уровне логики — структура, части речи, служебные элементы
```
- `1` — `GrammarTopicCategory.id` (из канона `_id-registry.md` → Next free **Category**), глобально уникален
- `Устройство языка` — `GrammarTopicCategory.title`
- `order=1` — `GrammarTopicCategory.order`: позиция раздела в ОБЩЕМ списке вкладки Теория
  (раздел и темы без раздела делят одно пространство нумерации)
- `**Раздел · Описание:**` → `GrammarTopicCategory.description`

**⚠️ Все объявления одного `id` обязаны совпадать дословно** — `title`, описание и `order=`
должны быть одинаковыми во всех файлах раздела. Конвертер пишет запись раздела в каждый
`seed/<тема>.json`, `json_to_db` дедуплицирует по `id`, а `tools/test/id_report.py`
проверяет согласованность и кричит `category mismatch`, если где-то разъехалось — например
скопировали шапку и забыли поправить `order=` в новом файле.

**Структура файлов — «пакет» на раздел.** Темы одного раздела складываются в отдельную
папку; имя файла нумеруется по `order` темы внутри раздела (только для навигации по диску,
в БД номер не попадает):
```
theory/
├── 01-basics.md                          (Topic id=1, без раздела)
├── 02-transcription.md                   (Topic id=5, без раздела, order=2)
├── 03-language-structure/                ← пакет = раздел "Устройство языка" (id=1, order=3)
│   ├── 01-how-english-thinks.md          (Topic id=2, Раздел: 1, order=1)
│   ├── 02-parts-of-speech.md             (Topic id=3, Раздел: 1, order=2)
│   ├── 03-auxiliary-verbs.md             (Topic id=4, Раздел: 1, order=3)
│   ├── 04-verb-forms.md                  (Topic id=6, Раздел: 1, order=4)
│   └── 05-infinitive.md                  (Topic id=7, Раздел: 1, order=5)
├── 04-present/                           ← пакет = раздел "Present: Simple и Continuous" (id=3, order=4)
│   ├── 01-present-simple.md              (Topic id=8, Раздел: 3, order=1)
│   ├── 02-present-continuous.md          (Topic id=9, Раздел: 3, order=2)
│   └── 03-compare-present.md             (Topic id=10, Раздел: 3, order=3)
├── 05-verb-adjective-preposition.md      (Topic id=11, без раздела, order=5)
├── 06-descriptions-comparisons/          ← пакет = раздел "Описания и сравнения" (id=2, order=6)

│   ├── 01-past-simple.md                 (Topic id=14, Раздел: 4, order=1)
│   └── 02-past-continuous.md             (Topic id=15, Раздел: 4, order=2)
├── 08-passive-basics.md                  (Topic id=16, без раздела, order=8)
├── 09-linking-words.md                   (Topic id=17, без раздела, order=9)

Имя папки пакета — `NN-slug`, где `NN` = `order` раздела в общем списке (для той же навигационной
читаемости, что и у файлов внутри). `py check.py <файл>` по-прежнему работает на одном файле —
структура раздела однофайловый воркфлоу не ломает.

> ⚙️ **Пакеты в `seed/` зеркалят пакеты в `theory/` — автоматически.** `md_to_json.py` сам видит,
> что MD лежит в `theory/<package>/...`, и кладёт сид в `seed/<package>/...` с той же структурой:
> ```
> theory/03-language-structure/01-how-english-thinks.md
>   -> seed/03-language-structure/how-english-thinks.json (+ _prompts.json)
> ```
> Файлы прямо в `theory/` (как `01-basics.md`) — без подпапки, как раньше (`seed/basics.json`).
> Ничего настраивать не нужно — конвертер определяет это по самому пути MD-файла. Раз тем будет
> много, одинаковая структура папок `theory/` ↔ `seed/` облегчает ориентацию: где тема — там и сид.
> `id_report.py` / `word_dup_report.py` сканируют `seed/**/*.json` рекурсивно — подпапки видят сразу.

#### ⚠️ В ДЕРЕВЕ ПЛАНА НОМЕРА НЕ ПРОСТАВЛЯЕМ (канон 08.09.2026)

В `grammar8r_plan.md` микротемы и карточки ещё **не написанной** темы пишутся **без номеров**:
`├── МТ · Название · Название` и `├── Card · Название карточки`. Номер (`Microtopic N`, `Card N`)
назначается **только в момент написания самого theory-MD** — из `_id-registry.md` → Next free.

Причина: дерево живёт годами и правится постоянно — карточки добавляются, сливаются, переезжают
между микротемами и между темами. Номер, проставленный заранее, к моменту написания почти всегда
врёт, а сверять и переписывать его по всему дереву дороже, чем взять свежий из реестра.

- Ссылаться по номеру на **уже написанный** контент (`Card 425`, `MT132`) в плане — можно и нужно:
  там номер реальный, он и служит адресом.
- Уже пронумерованные ветки ненаписанных тем задним числом не чистим (общее правило «канон — в
  гайд, готовое не переписываем»); при написании такой темы номера берутся из реестра, а не из плана.

### Блоки

⚠️ **Маркеры `# БЛОК N · Микротемы X–Y` больше НЕ пишем (отменено 30.06.2026).** Конвертер
`md_to_json.py` их просто пропускает (строки 602–603, «навигационные разделители») — в JSON/БД
они не попадают, смысловой нагрузки ноль. Границы секций держат `## Microtopic` и `### Card`
(их же используют тест-скрипты как STOP-маркеры), отдельный разделитель не нужен. В старых файлах
оставлять как есть (парсер их игнорирует), в новых — не добавлять.

### Микротема

```
## Microtopic N — Title EN · Title RU

**ID:** N | **Order:** N
**Теги:** тег, тег, тег

---

[карточки]

### Words8r Sync · Название раздела
| Слово | Переводы | Транскрипция |
```

#### ⚠️ Название микротемы — ВСЕГДА двойное: `English · Русское`

Формат заголовка обязателен: `## Microtopic N — Английское название · Русское название`.

- **Английское — первым, русское — вторым.** Разделитель — ровно ` · ` (пробел, `·`, пробел).
  Порядок не путать: `Noun · Существительное` ✓, `Существительное · Noun` ✗.
- **Зачем двойное.** UI рисует EN основным цветом и жирным, а RU — мельче и серым под ним
  (компонент `DualTitle`). В шапке карточек микротемы показывается **только английская часть**.
  Поэтому одинарное название (только EN или только RU) ломает единый вид списка микротем.
- Это правило для **микротем**. Заголовки карточек (`### Card N · …`) двойными делать не нужно —
  у них своё короткое имя по сути карточки.
- ⚠️ **Заголовок карточки — простым текстом, БЕЗ инлайн-выделения** (ни бэктиков, ни жирного).
  В названии нечего «акцентировать». Пишем «Правописание: -s, -es, -ies», а не «Правописание: `-s`…».

#### ⚠️ Нейминг с оглядкой на поиск (для НОВЫХ микротем)

Названия тем, микротем и карточек — главный источник поиска: они весят больше тегов. Плохое имя
тег вытянуть может, но это лечение симптома. Правила выведены из живых прогонов:

1. **Ключевое слово — ПЕРВЫМ в русской части.** Совпадение с первым словом названия даёт бонус
   к очкам. `Negative · Отрицание: don't / doesn't` находится по «отрицание» увереннее, чем
   `Negative · Образование: отрицание`, где первым стоит пустое «Образование».
2. **Чем название короче, тем оно точнее.** Очки считаются в том числе от доли названия, покрытой
   запросом: слово, найденное в имени из двух слов, весит больше, чем то же слово в имени из шести.
   Длинный «полный» заголовок сам себя разбавляет.
3. **Не начинать со служебной обёртки:** «Образование:», «Форма:», «Что такое», «Все ситуации».
   Эти слова никто не ищет, а позицию первого слова они съедают. Лучше `Форма: be + V3` →
   `be + V3 · Как собрать страдательный залог`.
4. **Название микротемы не должно повторяться в другой теме.** Сейчас `Usage · Употребление` стоит
   у трёх разных времён — для поиска они неразличимы, наверх выйдет случайная. Уточняем, чем
   именно эта: `Usage · Когда нужен Present Simple`.
5. **Английская часть — реальный термин, каким его ищут:** `used to`, `was / were`, `-ing`,
   `Past Simple`. Не выдуманный ярлык ради красоты — по нему тоже ищут.
6. **Название карточки — это тоже индекс.** Оно даёт очки своей микротеме (в выдаче не видно),
   поэтому пишется смыслом («Маркеры прошлого: словарь и слово ago»), а не «Пункт 1» или
   «Продолжение».
7. **Русское имя обязательно там, где тема названа по-английски.** У темы это закрывается тегом
   (жёсткое правило 3 ниже), у микротемы — русской частью двойного названия.

> Уже написанные микротемы под эти правила НЕ переписываем (канон применяется к новому контенту).
> Там, где старое имя мешает поиску, разрыв закрывается тегами.

#### Теги для поиска — `**Теги:**` (скрытое поле)

Поиск во вкладке «Теория» ищет по названиям темы, микротемы и **карточек** (названия карточек —
скрытый сигнал, в выдаче они не показываются). Тег закрывает разрыв между тем, как микротема
названа у нас, и тем, как её назовёт пользователь: у нас «Time markers · Маркеры прошлого» —
он ищет «указатели времени» или «когда это было».

**Тег — это синоним названия и короткое «о чём это», написанное словами пользователя.**
Не список токенов из теории и не симптом ошибки (`I didn't went` — не тег: сценарий «AI прислал
в теорию по ошибке» отменён).

- **Тег темы — широкий зонт:** как человек назовёт тему целиком. `прошедшее время`,
  `рассказать о прошлом`. Особенно важен там, где название темы **не двойное**: тема
  «Past Simple» по-русски не находится вообще ничем, кроме тегов.
- **Тег микротемы — то, чем она отличается от соседок по теме:** `прошлая привычка`,
  `не делал`, `указатели времени`. Общие слова темы здесь не повторяем — они уже на теме.
- Ориентир **4–8 тегов** на уровень, фраза 1–6 слов, строчными, через запятую.
- Не дублировать собственный заголовок и названия своих карточек — они и так в индексе.
- Пишем то, чего в заголовках **нет**. Формулировка «как спросил бы новичок» ценнее «правильной».

##### ⚠️ Жёсткие правила (проверены на живых прогонах поиска — не нарушать)

1. **Тег тем дороже, чем полнее его покрывает запрос.** Очки тега считаются от доли покрытых в нём
   слов: тег из двух слов, совпавший целиком, бьёт тег из шести, где совпало два. Поэтому тег —
   короткая точная фраза (`прошлая привычка`, `когда ставить s`), а не длинное описание: лишнее
   слово в теге снижает его собственные очки на любом запросе.
2. **Пишем ГЛАГОЛОМ ПОЛЬЗОВАТЕЛЯ, а не термином.** Человек ищет «когда **ставить** s», а не «когда
   нужна s»; «как **задать** вопрос», а не «образование вопроса». Тег с чужим глаголом не находится
   вообще — это уже ловилось на прогоне.
3. **Тег темы с английским названием ОБЯЗАН содержать её русское имя.** «Past Simple» по-русски
   не находится ничем, кроме тега: пишем `прошедшее простое`, `длительное время`, `страдательный
   залог`. Без этого запрос «простое» или «длительное» не найдёт тему вообще.
4. **Слово, общее для всей темы, в тегах микротем ЗАПРЕЩЕНО.** `прошедшее`, `настоящее`, `время`
   живут в теге ТЕМЫ. В теге микротемы такое слово не различает ничего (оно подходит всем соседкам),
   зато разбавляет тег и снижает его очки — см. правило 1.
5. **Тег не должен держаться на служебных словах.** `как`, `что`, `это`, `так`, `сказать` при
   поиске выбрасываются совсем, предлоги и союзы весят почти ноль. Тег `как сказать` = пустой тег.
   Смысл несут слова ПОСЛЕ них: `не делал`, `где ты был вчера`.
6. **Ценность тегу даёт РЕДКОЕ слово.** Движок взвешивает слова по тому, как часто они встречаются
   по курсу: `время`, `глагол`, `предложение`, `английский` есть почти везде и почти ничего не
   весят; `подлежащее`, `наружу`, `безличное`, `ago` весят много. Тег, собранный из одних общих
   слов, работать не будет, даже если написан правильно по всем остальным правилам.
7. **Теги соседних микротем не пересекаются.** Общий тег ничего не различает: если он подходит
   трём микротемам сразу — он либо принадлежит теме, либо не нужен.
8. **Не писать теги-синонимы своего же тега.** `прошлая привычка` + `привычки в прошлом` — это один
   тег, второй только разбавляет.
9. **Морфология берётся на себя движком.** Падеж, число и опечатка в одну букву уже прощаются
   (`маркеры прошлое` находит «Маркеры прошлого»), сокращения раскрываются (`didn't` = `did not`).
   Писать варианты одного слова НЕ нужно.
10. **Но однокоренное ≠ одна форма.** Движок сводит формы одного слова, а не родственные слова:
   `умею` и `умение`, `день` и `дни`, `сравнивать` и `сравнение`, `делают` и `сделали` для него
   разные. Поэтому в теге пишем то слово, которым спросит человек (`умею и могу`, а не `умение`),
   и не рассчитываем, что отглагольное существительное найдётся по глаголу. Это ограничение
   осознанное: настоящая лемматизация требует словаря и в офлайн-поиске по оглавлению курса
   не окупается.

11. **⚠️ ТЕГ — ЭТО ПОИСКОВЫЙ ЗАПРОС, А НЕ ПРИМЕР ИЗ КАРТОЧКИ** (фидбек 17.08.2026, жёстко).
   Перед тем как записать тег, спросить себя: **напечатает ли человек это в строке поиска?**
   Если нет — тег мусорный, он занимает место и разбавляет выдачу.
   - ❌ Так НЕЛЬЗЯ: `я поел`, `он уехал`, `потерял ключи`, `уронил телефон` — это примеры-специмены
     из теории. Никто не открывает поиск, чтобы «с нихуя» вбить «я поел»: человек ищет объяснение,
     а не пересказывает пример.
   - ✓ Так НАДО — формулировка цели/затруднения, с которым лезут в поиск:
     `have eaten или ate`, `зачем говорить have done`, `сказать что уже сделал`,
     `итог важнее момента`.
   - Рабочие шаблоны живого запроса: «X или Y» (выбор двух форм, которые человек путает),
     «зачем/почему …», «как сказать …», «что значит …», плюс сама английская форма, которую он
     видел и не понял (`has gone`, `used to`, `-ing`).
   - Тег-пример допустим ровно в одном случае: если это **устойчивая фраза**, которую человек
     реально гуглит целиком (`it's been a while`, `long time no see`), — то есть сам объект поиска.
   ⚠️ Применяется к НОВОМУ контенту; уже написанные микротемы под этот канон не переписываем
   (общее правило «канон — в гайд, готовую теорию не трогаем»).

12. **⚠️⚠️ ТЕГ-ПЕРЕСКАЗ СЦЕНЫ — БРАК. Ищи абсурдные теги перед сдачей** (фидбек 23.08.2026, жёстко;
   правило 11 нарушалось СНОВА, поэтому расписано отдельно). Тег должен называть **грамматическую
   трудность**, а не пересказывать бытовую сценку из карточки. Человек идёт в поиск за объяснением
   формы — он не набирает симптом, ситуацию или ощущение персонажа.
   - ❌ Реальный брак, так писать НЕЛЬЗЯ: `почему я запыхался`, `видно чем человек занимался`,
     `i've been thinking мягкий заход`, `делаю уже два года`. Это подписи к иллюстрациям, а не запросы:
     никто не открывает поиск по курсу грамматики, чтобы вбить «почему я запыхался».
   - ✓ Так надо — назвать саму развилку/форму, из-за которой человек и полез искать:
     `have been без for и since`, `процесс кончился а форма длительная`, `have you been drinking упрёк`,
     `i've been thinking вместо i think`.
   - **Тест на абсурд (обязательный, прогнать по КАЖДОМУ тегу):** представь строку поиска и спроси —
     «человек, который этого правила НЕ знает, напечатает это?». Если фраза имеет смысл только для
     того, кто уже прочитал карточку (он вспоминает пример), — тег мусорный, выбрасывай.
   - Второй признак брака: тег понятен только вместе с примером карточки. Тег обязан быть
     самодостаточным — читаем его отдельно, без контекста микротемы, и он всё ещё звучит как запрос.
   - Это ловится на **самопроверке §9** отдельным пунктом чеклиста: перечитать все теги микротемы
     подряд и вычистить пересказы сцен.

13. **⚠️⚠️ АНГЛИЙСКИЙ ТЕГ — ТОЛЬКО КОРОТКАЯ ФОРМА, А НЕ КУСОК ПРЕДЛОЖЕНИЯ** (фидбек 06.09.2026,
   жёстко; правила 11–12 нарушались СНОВА, но уже на английских тегах, поэтому расписано отдельно).
   Правило 11 разрешает тегом «саму английскую форму, которую он видел и не понял» — и это
   разрешение регулярно превращают в брак, вставляя тегом фрагмент примера из карточки.
   - ✓ Так МОЖНО — форма, которую человек встретил в чужой речи и пошёл выяснять: `used to`,
     `has gone`, `would of`, `if i were you`, `had knew`, `-ing`. Один-три слова, узнаваемая
     конструкция или частая ошибка. Пара через «или» — тоже, но только если это ДВЕ короткие формы,
     которые реально путают: `have eaten или ate`, `will или going to`, `were или was`.
   - ❌ Так НЕЛЬЗЯ — фрагмент предложения-примера с подлежащим и обстоятельствами:
     `wouldn't be tired now`, `would come или would have come`, `if i had been sleeping`,
     `i've been thinking мягкий заход`. Никто не ищет по огрызку чужой фразы: человек его не помнит
     дословно, а если бы помнил — вопроса бы не было.
   - **Тест перед сдачей:** мог бы этот тег стоять в чужой речи ЦЕЛИКОМ, отдельной единицей
     (`used to` — да, `wouldn't be tired now` — нет, это половина предложения из нашей же карточки)?
     Нет — выбрасывай и бери либо русскую формулировку затруднения (`можно ли смешивать типы`,
     `где ставить would`), либо имя самой конструкции (`третий тип условных`).
   - Побочный эффект, из-за которого это ещё и вредно: длинный английский огрызок почти всегда
     длиннее 6 слов и режет собственные очки тега (правило 1).

Конвертер предупреждает (не роняет сборку): дубль тега внутри уровня, тег длиннее 6 слов, тег
целиком состоящий из слов собственного заголовка. Тегов нет → `null`, объект ищется по заголовку —
темы без тегов работают как раньше.

### Карточка без упражнений

## 3. Правила теории

### Главный принцип: объяснять, а не называть

Плохо: *"Несчётные существительные не имеют множественного числа."*  
Хорошо: *"Представь что advice — это не штука, а вещество. Как воду нельзя посчитать ('три воды' звучит странно), так и advice нельзя: 'three advices' — ошибка. Можно только 'three pieces of advice'."*

Пользователь после каждой карточки должен думать **"О, вот оно что!"** — а не "ещё одно правило".

### Объяснять через сравнение с русским

Не просто "в английском так", а почему это логично и откуда берётся ошибка у русскоязычного.

Шаблон объяснения:
1. Как это работает в русском (что привык делать пользователь)
2. Почему английский работает иначе
3. Конкретная ловушка которая из этого вытекает

Примеры:
- *"По-русски 'я знаю' и 'я знал' — один глагол с разным окончанием. В английском это два разных слова: know и knew. Мозг хочет добавить -ed к know — не выйдет."*
- *"По-русски 'мне холодно' — от ощущения. По-английски 'I am cold' — от субъекта. Дословный перевод 'to me cold' — бессмыслица."*

### Разжёвывать максимально подробно

Одно правило — одна карточка. Нюанс внутри правила — отдельная карточка.  
Лучше 3 понятные карточки чем 1 перегруженная.

Каждое утверждение подкрепляется примером. Каждое исключение объясняется — не просто "запомни", а почему оно такое.

Если есть логика даже за исключением — объяснить её:  
*"Почему 'at night', а не 'in the night'? Ночь воспринимается как особый момент темноты, а не период с чёткими границами — отсюда точечный 'at'."*

### Переводы примеров (обновлено 25.06.2026 — команда «середины курса» дана)

**Темы «Основы» … «Устройство языка» (включая Инфинитив):** переводить всё — пользователь
ещё копит базу.

**С темы Present Simple и далее — НЕ переводим простое.** База накоплена, и пользователь должен
учиться понимать смысл сам (зажал слово → long-press дал перевод). Правило:

- **НЕ переводим:** слова из «Основ» и всех пройденных тем; базовую служебку (предлоги,
  местоимения, to be, do/does, артикли); приоритетные глаголы текущей темы; и даже точечно
  незнакомое слово — расчёт на long-press.
- **Переводим:** реально новые ключевые слова темы (в момент введения) + их Words8r Sync.
- **Колонка RU в таблице `#### Examples` — ОСТАЁТСЯ всегда** (это формат таблицы, по ней удобно
  читать связку RU↔EN). Убираем только **инлайновые тривиальные переводы в прозе теории** — вот
  такие `I want to eat` *(Я хочу есть)* больше НЕ пишем (раньше писали).

#### ⚠️⚠️ КОЛОНКА RU В `#### Examples` — ЗЕРКАЛО АНГЛИЙСКОГО, А НЕ ВОЛЬНЫЙ ПЕРЕСКАЗ (канон 08.09.2026)

Колонка RU существует ровно для одного: пользователь читает две ячейки рядом и **видит связку
RU↔EN** — какое русское слово чем стало по-английски. Как только перевод «уходит в художественность»,
связка рвётся, и строка превращается в мусор: английское предложение стоит одно, русское — про своё.
Реальный брак, из-за которого правило и записано: `Does Vera get a discount there?` было переведено
как «Ей там дают скидку?» — подлежащее исчезло, `get` («получает») подменилось безличным «дают»,
и по такой паре понять устройство фразы невозможно.

**Три требования к каждой строке RU (проверять по всем примерам перед сдачей карточки):**

1. **Подлежащее и все участники — на месте.** Есть в EN имя или существительное — оно есть и в RU,
   и **кириллицей** (`Вера получает там скидку?` ✓, `Ей там дают скидку?` ✗, `Vera получает…` ✗).
   Менять названного человека на местоимение («ей», «там кому-то») запрещено: пользователь ищет
   глазами, где в английском стоит подлежащее.
2. **Ключевой глагол переводится СВОИМ смыслом, тем самым, ради которого написана карточка.**
   Тема про `get` = «получать» → в RU стоит «получает», а не «дают»/«полагается»/«действует».
   Безличный оборот на месте личного — та же ошибка: он прячет ровно то, что мы объясняем.
3. **Тип предложения совпадает:** вопрос переводится вопросом, отрицание — отрицанием, команда —
   командой. Не «сглаживать» в утверждение ради гладкости русского.

Естественность русского при этом не отменяется — речь не о подстрочнике. Правило простое: **из
двух одинаково живых вариантов берём тот, где ближе структура**; если живой вариант ломает
связку (теряет подлежащее, подменяет глагол), берём чуть менее гладкий, но честный.

⚠️ Не путать с каноном «конструкцию переводим ДВАЖДЫ» ниже: там дословный вариант нужен в **прозе
теории**, чтобы показать устройство. В колонку RU таблицы `#### Examples` он не тащится — там
по-прежнему один живой перевод, просто не расходящийся с английским по составу.

#### ⚠️ Скобка-глосс `*(перевод)*` в прозе — ТОЛЬКО там, где long-press не выручает (канон 10.08.2026)

Повторный фидбек пользователя: глоссы к обычным словам он вычищает из теории почти всегда, оставляя
единицы. Причина простая — **зажать слово и получить перевод пользователь может сам**, и это
сознательная тренировка (см. «Переводы примеров» выше). Лишний глосс = недоверие к читателю и рябь
в тексте.

- ❌ **НЕ глоссировать обычное слово, которое мы же сливаем в Sync этой микротемы.** `to rent`
  *(снимать, арендовать)*, `weekend` *(выходные)*, `definitely` *(точно, определённо)* — глосс не
  нужен: слово попадёт в Словарь, а прямо сейчас его переведёт long-press.
- ✓ **Глосс НУЖЕН для конструкции из двух и более слов.** Long-press переводит **одно** слово —
  значит `as soon as`, `be about to`, `the day after tomorrow`, `it's been a while` пользователь
  сам не разберёт: их смысл даём прямо в тексте.
- ✓ **Глосс НУЖЕН, когда на этом значении держится объяснение.** Знакомое слово во ВТОРОМ,
  неочевидном смысле (`will` как «хотеть» в разборе `when I will come`; `shall` как «быть должным»),
  или слово, без точного понимания которого разваливается сама мысль карточки. Здесь перевод —
  часть аргумента, а не подсказка.
- Критерий одной фразой: **«достаточно ли зажать одно слово, чтобы понять?»** Да → глосса нет.
  Нет (составная конструкция / нужен конкретный оттенок значения) → глосс даём.
- Это про **прозу теории**. Колонка RU в `#### Examples` остаётся всегда — она формат таблицы,
  а не глосс.

#### ⚠️⚠️ КОНСТРУКЦИЮ переводим ДВАЖДЫ: дословно и по-живому (канон 06.09.2026)

Правило выше запрещает глоссы к обычным **словам** (их переведёт long-press). С **конструкциями**
всё наоборот: у них перевода не хватало, и пользователь на этом спотыкался (фидбек по микротеме
`Wish / If only` — перевод либо не давался вовсе, либо давался криво). Конструкция — это `I wish`,
`If only`, `unless`, `in case`, `used to`, `would rather`, `had better`, `I'd like` и вся прочая
сборка из нескольких слов, у которой смысл не выводится из слов по отдельности.

**Каждой такой конструкции при введении даём ДВА перевода подряд, в одну строку:**

```
дословно «…», по-живому «…»
```

- **Дословный** показывает **УСТРОЙСТВО**: почему фраза собрана именно так и что за чем идёт.
  Из «хотел бы я, **чтобы** у меня была машина» сразу видно, что после `wish` идёт целая часть
  с подлежащим, — и почему `I wish a car` ✗ невозможно.
- **Живой** показывает **СМЫСЛ**: как это скажет русский человек. «Вот бы у меня была машина»,
  «жаль, что у меня нет машины».
- Оба нужны, и порознь они не работают: один дословный оставляет корявую фразу без смысла, один
  живой прячет устройство — а именно на устройстве стоят все ловушки карточки.

**⚠️ Дословный ≠ буквальный подстрочник.** Если буквальный вариант звучит по-русски дико или
казённо — не оставляй его таким, подбери ближайший естественный оборот, который сохраняет
структуру. Реальный пример: `I wish I had more time` буквально — «я **желаю**, чтобы у меня было
больше времени», а это звучит как тост на празднике; правильный дословный — «**хотел бы я**, чтобы
у меня было больше времени»: структура та же, а тон живой. Критерий: дословный перевод обязан
оставаться **читаемой русской фразой**, иначе он не объясняет, а отпугивает.

**⭐ Если у конструкции есть прямой русский аналог слово-в-слово — назвать его ПЕРВЫМ.** Это самый
дешёвый способ понимания из всех: объяснять нечего, надо только показать совпадение.
`If only` = «**если бы только**» · `in case` = «**на случай**» (а вовсе не «если») ·
`as long as` = «**пока / при условии что**» · `even if` = «**даже если**». Такое совпадение —
подарок, и терять его нельзя: без него человек будет переводить конструкцию наугад.

**Где это писать:** в прозе `#### Theory` при первом появлении конструкции, и дальше по списку
примеров той же карточки (`- **English example.** — дословно «…»; по-живому «…»`). Колонка RU в
`#### Examples` остаётся живой всегда — дословный вариант туда не тащим, он объясняющий, а не
переводческий.

Форматы перевода (там, где перевод всё же нужен — новое слово):
- В таблице Examples: отдельная колонка RU
- В тексте теории: курсив или скобки после примера

```
"I have been waiting for an hour." — *Я жду уже час.*
walk over a hill *(подняться на холм и спуститься)*
```

Переводы в упражнениях — см. §4 (TrueFalse, FORWARD/REVERSE_CHOICE). В WordArrangement перевод слов
не пишется вовсе (2 колонки `Слово | Лишнее?`, long-press переведёт).

### Звуки — только транскрипцией в двойных квадратных скобках `[[…]]`

Любой **звук** в теории записывается транскрипцией — `[[t]]`, `[[d]]`, `[[ɪd]]`, `[[ʃ]]`, `[[k]]` —
как в теме «Транскрипция». Пользователь к этому моменту уже умеет читать транскрипцию, поэтому
отдельные звуки и окончания обозначаем именно так, единообразно со всем курсом. Скобки **двойные** —
полный канон и причина в §8 → «ТРАНСКРИПЦИЯ»; UI покажет их пользователю одинарными.

- ✓ `после [[t]] и [[d]] окончание -ed читается как лишний слог [[ɪd]]`
- ✗ `после [t] и [d] …` — одинарные скобки заняты пропусками и слотами, транскрипцию по ним не отличить
- ✗ `после t и d окончание читается /ɪd/` — слэши `/…/` не использовать, это не наш формат
- ✗ описывать звук словами («звук «д»») там, где уместна транскрипция

Двойные скобки — именно для звуков/транскрипции. Это не мешает обычному тексту: буквы как буквы
пишем как есть (`окончание -ed`, `буква y`), а вот их **звучание** — `[[ɪd]]`, `[[d]]`.

### Ловушки — конкретно

Каждая ловушка: сломанный пример ✗ + правильный вариант ✓ + объяснение почему.

```
"I need an advice." ✗ → "I need some advice." ✓  
advice — несчётное, артикль a/an с ним невозможен.
```

Не писать просто "это ошибка" — писать откуда берётся ошибка.

### ⚠️⚠️ ПОЛНЫЙ НАБОР ФОРМ КОНСТРУКЦИИ — ПРОВЕРЯТЬ ДО НАПИСАНИЯ (канон 05.09.2026, жёстко)

Повторный провал: микротема пишется по дереву плана, а в дереве расписан только **утвердительный**
случай — и конструкция уезжает в БД без отрицания и без вопроса. Так было в Conditionals: план
описывал `if + Present → will`, вопросы в нём не значились вообще, и карточки ушли бы без них,
если бы пользователь не спросил. Дерево плана — **не** гарантия полноты: оно фиксирует замысел, а
за полноту грамматики отвечает автор карточки.

**Перед написанием ЛЮБОЙ конструкции прогнать её по чек-листу форм** (не «если вспомню», а всегда):

1. **Утверждение** — база, она в плане почти всегда есть.
2. **Отрицание** — и отдельно проверить, в КАКОЙ части оно ставится и что бывает, когда частей две
   (в условных отрицают обе половины, и каждая по своим правилам).
3. **Вопрос** — как он строится, какая часть предложения становится вопросительной, а какая
   остаётся утвердительной.
4. **Отрицательный вопрос** («разве не…?») — по правилу ниже, оно остаётся в силе.
5. **Краткий ответ / короткая форма**, если конструкция их вообще имеет.
6. **Сокращения** (`won't`, `hadn't`, `'d`) — если пользователь встретит их в живой речи.

**Если по какому-то пункту нет уверенности — НЕ угадывать и не «обходить молчанием».** Сначала
подумать самому на живых примерах, при необходимости сверить формулировку по внешнему источнику,
и только потом писать. Молча пропустить форму — худший вариант: пользователь встретит её в жизни
и не узнает, а курс будет считать тему закрытой.

Что делать с найденной формой: если она укладывается в 1–2 абзаца — блок внутри существующей
карточки (эталон — блок про вопросы в карточке о свободной правой половине, Conditionals Card 491).
Если тянет на разбор с ловушками — отдельная карточка, и тогда **сразу дописать её в дерево плана**,
а не оставлять расхождение между планом и файлом.

### ⚠️⚠️ ЧЕМ ЗАПОЛНЯЕТСЯ СЛОТ КОНСТРУКЦИИ — ПРОГНАТЬ ИНВЕНТАРЬ (канон 12.09.2026, жёстко)

Правило-брат к чек-листу форм выше, и провал у него отдельный. Чек-лист форм следит за **внешней
сборкой** конструкции (утверждение · отрицание · вопрос) — и этого мало. Вторая половина полноты:
**что стоит ВНУТРИ конструкции, в её слоте.** Приём объясняется на одном-двух типах наполнителя,
автор видит «правило показано» и закрывает карточку — а половина живых фраз в слот не попала.

Реальный провал: `I wish` (Card 503). Карточка объяснила «после `wish` форма отодвигается назад» и
показала это на обычных глаголах (`knew`, `lived`) и на `to be` (`was`/`were`). Модальный `can` в
слот не попал ВООБЩЕ — а `I wish I could …` (`could cook` · `could come` · `could help`) и есть
самая частая форма этой конструкции в живой речи. После такой карточки человек честно скажет
`I wish I can cook` ✗, потому что перенести «отодвинь форму назад» на `can` он сам не обязан:
`can` не похож на глагол — короткий, по лицам не меняется, стоит рядом с настоящим глаголом.

**Перед сдачей карточки выписать слоты конструкции и прогнать по каждому инвентарь уже пройденного:**

1. **Обычный глагол** — база, она почти всегда есть.
2. **`to be`** — у него своя форма (`was`/`were`, `weren't`), и она почти всегда ведёт себя особо.
3. **Модальный** — `can` → `could`, `will` → `would`. Отдельно проверить, какой модальный в слот
   НЕ идёт и почему (`I wish I would …` ✗ — претензию предъявляют чужому поведению, не своему).
4. **Конструкции-обязанности и составные** — `have to` → `didn't have to`, `be going to`, `used to`.
5. **Безличное** — `there is` → `I wish there were more time`.

По каждому пункту исход ровно один из двух: **показан в карточке** либо **сознательно отложен** в
другую карточку с пометкой в дереве плана. Молча пропущенный пункт — дыра, и обнаружит её
пользователь, а не мы.

**Второе: направление переворота — давать ОБА.** Если конструкция сообщает обратное факту
(`wish` · `if only` · второй и третий тип), показать оба хода, а не один:

- факт отрицательный → жалоба утвердительная: `I can't cook` → **I wish I could cook**;
- факт утвердительный → жалоба отрицательная: `I can drive` → **I wish I couldn't drive**.

Одно направление рождает ложное правило «после `wish` всегда добавляют то, чего нет» — и человек
не умеет пожаловаться на то, что у него ЕСТЬ. Второй ход часто выглядит редким (`I wish I
couldn't`) — тем он и ценен: на нём механика видна насквозь.

**Проверка одной фразой (дёшево, делать всегда).** Карточка объяснила приём. Теперь возьмите **пять
разных предложений из уже пройденного курса**, в которых пользователь захочет этот приём применить,
и проверьте: на каждом ли ваша формулировка срабатывает без доучивания? Хоть на одном не срабатывает
целиком — в карточке дыра, и её закрывают ДО сдачи. Если закрывается в 1–2 абзаца — блок внутри
карточки (эталон — блок «Модальный глагол отодвигается точно так же» в Card 503); если тянет разбор
с ловушками — отдельная карточка плюс строка в дерево плана.

### ⚠️ Вопросы бывают и отрицательными — давать всегда

Когда карточка/микротема объясняет **вопрос** (в любом времени: Present/Past/Future Continuous,
Simple, Perfect, модальные…) — обязательно дать и **отрицательный вопрос** («разве не…?»):
`Aren't you coming?`, `Doesn't she know?`, `Didn't he call?`, `Won't they help?`. Не ограничиваться
только утвердительным вопросом. Показать форму (связка/помощник + `not` выносится вперёд, обычно в
краткой форме `isn't`/`aren't`/`don't`/`doesn't`/`didn't`/`won't`), оттенок (удивление/проверка,
ожидал обратного) и особые случаи (`aren't I?` для `I`, т.к. у `am` нет краткой формы с `not`).
Хватает короткого блока в карточке про вопрос — отдельную карточку под это заводить не нужно.

### ⚠️ Глаголы-состояния (state verbs) — напоминать во всех Continuous-временах

Глаголы-состояния (`know`, `want`, `like`, `love`, `believe`, `understand`, `need`, `see`, `hear`…)
описывают состояние, а не действие, и **в Continuous не ставятся** — даже про «сейчас» остаются в
Simple (**Do you believe me?** ✓, не **Are you believing me?** ✗). Полный разбор — в отдельной
микротеме Present Continuous (MT63 «State verbs»). Но **в любом Continuous-времени** (Past
Continuous, Future Continuous, Present/Past Perfect Continuous) при объяснении употребления давать
**короткий намёк вскользь** (плашка `**Важно:**`), что не каждый глагол идёт в это время + ссылку на
разбор state verbs. Русскоязычный охотно лепит `I am knowing`, `She was wanting` — предупреждать
заранее, а не ловить постфактум.

### Clarification Options — что это

Заранее написанные вопросы для фичи "Не совсем понял" в конце каждой карточки. Пользователь тапает на вопрос → он уходит в AI → AI объясняет то же правило другими словами и с другим примером (не повторяет теорию карточки).

Писать 2–3 вопроса которые реально могут возникнуть у пользователя после прочтения карточки. Не общие ("расскажи про это правило"), а конкретные ("Почему 'at night', а не 'in the night'?").

### Тон: "мы", а не "ты"

При отсылке на пройденный материал — писать от первого лица множественного числа:
**мы разбирали**, **мы уже видели**, **мы знакомились** — не "ты разбирал", "ты уже видел".

*"В Основах мы разбирали предлоги места..."* — правильно.
*"В Основах ты разбирал предлоги места..."* — неправильно.

"Мы" звучит как совместное путешествие, "ты" — как указание сверху вниз.

### ⚠️ Ссылки на пройденное — по НАЗВАНИЮ, а не по номеру микротемы

В прозе теории **никогда не ссылаться на микротему/тему по номеру** (`MT29`, `МТ22`, `Microtopic 8`).
Пользователь не знает внутренней нумерации — для него это пустой код. Ссылаться по **названию**:

- ✗ *«Вспомни MT29: субъект и объект — это существительные.»*
- ✓ *«Вспомни микротему «Существительное»: субъект и объект — это существительные.»*
- ✓ *«В «Основах» мы разбирали предлоги места…»* (по названию темы)

Номера `## Microtopic N` в **заголовках** — это служебный формат парсера (в БД, пользователь их
не видит), их не трогаем. Запрет касается только **текста теории, Summary, Clarification Options,
условий упражнений** — всего, что читает пользователь.

### Разнообразие имён в примерах

Активно чередовать имена — и русские, и **английские** (в EN-примерах английские имена звучат
естественнее). Чем больше разных, тем лучше.

- **Русские:** Лена, Игорь, Катя, Рома, Саша, Вера, Тёма, Оля, Коля, Миша, Ира, Настя, Паша, Юля,
  Денис, Соня, Олег, Гриша, Витя, Жанна.
- **Английские:** Tom, Jack, Emma, Lucy, Mark, Ben, Kate, Nick, Sam, Lily, Mia, Jake, Sara, Oliver, Megan.

⚠️ **Не залипать на одном имени** (частый фейл — везде `Dima`). В рамках одной микротемы каждое
новое имя по возможности другое; одно и то же имя несколько раз подряд — не писать. Максим и Анна — избегать.

⛔ **Среднеазиатские и мусульманские имена — НЕ использовать вообще** (канон 22.08.2026): Рустам,
Абдула и подобные — ни в теории, ни в примерах, ни в упражнениях. Берём имена из двух списков выше.

⚠️ **Английское имя в РУССКОЙ прозе пишется кириллицей** (там же): `Грег возвращается домой` ✓,
`Greg возвращается домой` ✗. Латиница у имени — только внутри английского предложения-примера
(**Greg has been waiting for an hour**) и в колонке EN таблицы `#### Examples`.

### Живые примеры

Примеры из реальной жизни, а не учебниковые. Не "The cat is on the mat" — а ситуации которые пользователь узнаёт:
- рабочий чат, кофейня, поездка, телефонный разговор
- эмоции, планы, бытовые действия

### ⚠️ Использовать ВЕСЬ накопленный словарь — не залипать на нескольких словах

Пользователь знает не только глаголы Present Simple (id 1–20), но и **ВСЕ слова, слитые в темах
ДО текущей** (весь накопленный `course_words`). Примеры и упражнения строить **активно и
разнообразно из этого пула**, а не гонять по кругу одни и те же `to watch` / `to sleep` / `to work` /
`to read` / `to play` и пару существительных (частый фейл — «сдвиг» на 3–4 слова).

- ПЕРЕД написанием примеров — вытащить актуальный инвентарь слитых слов (пробежать по
  `tasks/tools/seed/**/*.json` → `course_words`, вывести `word`/`translation`) и осознанно чередовать
  глаголы/существительные/прилагательные из него плюс свежие слова темы. В курсе уже слиты десятки
  глаголов (`to swim`, `to drive`, `to sing`, `to run`, `to study`, `to cook`, `to dance`, `to travel`,
  `to smile`, `to laugh`, `to carry`…) и сотни других слов (`coffee`, `tea`, `café`, `museum`, `garden`,
  `kitchen`, `party`, `dinner`, `hungry`, `busy`, `quiet`, `loud`…) — грех ими не пользоваться.
- Известную лексику при этом НЕ переводим (long-press), см. «Переводы примеров».
- Чередовать также имена и города/страны (см. «Разнообразие имён» и ⚠️-правила в §4).

### ⚠️ Обязанность по умолчанию — `have to`, не `must` (канон 06.08.2026)

Когда в примере или упражнении нужно сказать «должен / надо / приходится» — по умолчанию берём
`have to` (`has to`), а не `must`. Причина: для английского уха `must` звучит жёстко, почти приказом
сверху («так велено»), и в живой речи носители про обязанность почти всегда говорят `have to` —
`must` остаётся на табличках, в правилах, инструкциях и в официальном письменном стиле.

- `I have to leave early today.` ✓ — обычная бытовая обязанность.
- `I must leave early today.` — не ошибка, но звучит казённо/натужно; так пишут в правилах, а не
  говорят коллеге.
- Исключение: **разбор модальных глаголов как класса** («после модального идёт голый V1 без `to`») —
  там `must` наоборот удобен, потому что даёт самую наглядную ошибку `I must to go` ✗. `have to`
  на эту роль не годится вообще: это обычный глагол, и `to` у него на месте.
- Полное сравнение оттенков (внутренняя vs внешняя обязанность, `mustn't` vs `don't have to`,
  регистры) — тема «Модальные глаголы», см. `grammar8r_plan.md`.

### ⚠️ Британское ↔ американское: плашка «Кстати» при сливе, а не отдельная тема (канон 01.09.2026)

Различий BrE/AmE в лексике много (`restroom` / `toilet`, `flat` / `apartment`, `lift` / `elevator`,
`chips` / `fries`, `queue` / `line`, ⚠️`pants`), и они всплывают по одному, в разных темах. Отдельную
тему или микротему под них **не заводим** — она собрала бы в кучу слова, между которыми нет ничего
общего, кроме страны. Правило:

- Различие даётся **плашкой `**Кстати:**` ровно в той микротеме, где слово впервые сливается** —
  в момент, когда пользователь его и так видит впервые. Один раз, коротко: какой вариант где живёт
  и чем рискует тот, кто перепутает (`toilet` в США звучит грубовато — это про сам унитаз).
- **В Words8r Sync идёт ОДИН вариант** — тот, что пользователю нужнее (для туалета — `restroom`).
  Остальные остаются в плашке на узнавание, в Словарь их не тащим: два синонима = два независимых
  прогресса на одну мысль.
- Если различие грамматическое, а не лексическое (`have got` — британское, `Did you…?` вместо
  перфекта — американское), оно разбирается в своей грамматической теме, тем же способом — плашкой.
- Исключение — тема «Британское и американское **написание**» (раздел «Пунктуация и орфография»):
  она про буквы (`colour` / `color`, `-ise` / `-ize`), а не про слова, и остаётся как есть.

### Что объясняем сами, а что доучивает AI на ошибках

Курс конечный — английских нюансов бесконечно. Если тащить в теорию каждый оттенок
(`fruit` vs `fruits` в общем смысле, тонкая разница `a few`/`few`, `as` vs `like`), курс
раздуется в духоту. Критерий разделения:

- **Ломает каркас предложения → объясняем в карточке, обязательно.** Правило, без
  которого предложение просто неправильное: нет глагола-связки (`it tasty` ✗), `-s` в
  3-м лице (`she play` ✗), `to` после модального (`I can to swim` ✗), порядок SVO. Это
  фундамент — он всегда в теории.
- **Шлифует, а не ломает → по умолчанию отдаём AI.** Нюанс, от которого предложение не
  разваливается, просто звучит менее естественно/точно. Пользователь добирает это в
  AI-упражнениях: ошибётся — AI объяснит в контексте.
- **Но можем и сами — если ложится естественно и без духоты.** Жёсткого запрета нет:
  если нюанс коротко вписывается в карточку и реально помогает понять (как `at night`
  vs `in the night` выше) — рассказать можно. Чего нельзя — городить отдельные карточки
  на каждый оттенок ради полноты.

Грубо: «без этого предложение неправильное» → теория обязательно; «так просто
естественнее» → по умолчанию AI, в теории по желанию и без перегруза.

### TrueFalse — формат утверждений

Каждое утверждение — **реальное предложение на английском** (+ русский перевод), часть из которых содержит грамматическую ошибку. Пользователь сам определяет: правильно или нет.

**Запрещено** писать мета-утверждения вроде `"Please" is a correct answer to "Thank you."` или `"Many" is used with uncountable nouns.` — это не тест на понимание грамматики, а тест на знание правил в абстракции. Вместо этого — конкретное предложение, которое либо грамматически верно, либо содержит ошибку:

❌ Плохо: `"I have some good news." is correct.`
✓ Хорошо: `I have some good news.` — *У меня есть хорошие новости.* — ✓

❌ Плохо: `"Please" is a correct answer to "Thank you."`
✓ Хорошо: `— Thank you! — Please.` — *— Спасибо! — Пожалуйста.* — ✗

### Ключевые правила кратко

**⚠️ Условие задания — без подсказки-правила.** `Задание:`/prompt говорит ТОЛЬКО что сделать, не КАК.
Не «сделай отрицание (he/she/it → doesn't + V1 без -s)», а просто «сделай отрицание». Подсказка для
юзера — кнопка «?» (открывает `#### Summary`), а не текст задания. Спойлер обнуляет упражнение.

**⚠️⚠️ НЕ копировать предложения из теории в упражнения (касается ВСЕХ типов, не только сортировок).**
Упражнение НЕ должно дословно повторять предложение/конструкцию из `#### Theory` или `#### Examples`
ЭТОЙ карточки. Если в теории был `Do you work here?` — в упражнении не `Do you work here?`, а **новая
ситуация с новой лексикой** (`Do you speak French?`, `Does the train leave at six?`). Иначе пользователь
не применяет правило, а механически узнаёт готовый ответ — упражнение обнуляется. Правило проверяет
ту же грамматику на **другом** материале:
- бери другой глагол / подлежащее / ситуацию, чем в примерах карточки;
- подмешивай новую (но из пройденного курса) лексику, чтобы было над чем подумать;
- упражнения и между собой не должны дублировать друг друга.
Это расширение правила сортировок (Categorization/TableFill «~3 из теории + новые») на **любой** тип
упражнения. ConstructionMeaning на идиому-карточке: тестируй вариант конструкции (`What does your
brother do?`), а не дословно лид-пример (`What do you do?`).

**⚠️ Позицию правильного варианта — РАНДОМИТЬ, не залипать на центре.** Юзер заметил перекос: в
~80% заданий ✓ стоял на средней позиции. Распределять равномерно: 3 опции → ≈33% на каждую (верх/
центр/низ), 4 опции → ≈25%. Касается всех типов со списком `- вариант` (CHOICE/FORWARD_CHOICE/
REVERSE_CHOICE, ErrorCorrection, DialogRestore, ConstructionMeaning, FindTheOdd). При написании
каждого задания осознанно менять место ✓; в конце микротемы — глянуть распределение по всем заданиям
глазами и выровнять. Парсер/тесты для этого НЕ трогаем — просто держим в голове.

**⚠️ Никаких пояснительных скобок-гло́сс в условиях и вариантах ответа упражнений.** `(кем работает)`,
`(вообще, не сейчас)`, `(глагол to drink)` в prompt'е FORWARD_CHOICE или в тексте варианта — убирать:
это либо прямой спойлер правильного ответа, либо лишний костыль. Смысл фразы должен читаться сам;
нужна подсказка — у юзера есть кнопка «?» (→ Summary). Гло́сса допустима ТОЛЬКО в `#### Examples`/прозе
теории (там она раскрывает смысл для читателя) и в TextInput-контексте, который проверяет ФОРМУ
известного слова (`(пьёт)` — см. §4 «Подсказка к пропуску»). В выборе/сборке/суждении — нет.
(Исключение по сути: ConstructionMeaning тестирует САМ смысл — но и там верный вариант не доглоссировать
так, чтобы он стал очевиднее прочих.)

**⚠️ Города/страны/реалии — варьировать, не залипать на Москве и Лондоне.** `live in Moscow` / `in London`
уже были в курсе тысячу раз. Брать другие города и страны: Prague, Berlin, Madrid, Lisbon, Rome, Vienna,
Warsaw, Dublin, Boston, Tokyo… (как с именами — см. «Разнообразие имён»). Не выдумывать экзотику ради
экзотики, но и не сводить всё к двум столицам.

**⚠️ Ответ однозначен — выводится из условия, не угадывается.** Несколько правильных ответов = задание
сломано. Провал-классика: Transformation со сменой подлежащего на произвольное 3-е лицо («We read» →
«My sister reads» — почему `my sister`, а не любое he/she?). Цель задавать явно и одинаково: «перепиши
про he» → все `He …`. Подробнее — `exercise_templates.md` (Общие правила + Transformation).

**⚠️ У `Matching`, `Categorization`, `TableFill` строка `Задание:` — ОБЯЗАТЕЛЬНА.** Это единственная
шапка, которую видит пользователь (заголовки колонок таблицы парсер выбрасывает). Конвертер ищет её
дословно по префиксу `Задание:` — формулировка без него (`Соедини RU ↔ EN:`) молча теряется, и
задание открывается вообще без шапки. Детали — `exercise_templates.md` → «Matching».

**1 вопрос = 1 упражнение** для типов: `MultipleChoice · CHOICE`, `MultipleChoice · FORWARD_CHOICE`, `MultipleChoice · REVERSE_CHOICE`, `ErrorCorrection`, `ConstructionMeaning`, `DialogRestore`, `FindTheOdd`.

Упаковка нескольких вопросов в один `Ex N` — ошибка. Каждый вопрос получает свой `Ex N` и свой type-specific ID.

**Разнообразие обязательно.** На одну карточку — разные типы. Не делать подряд 3 MultipleChoice. Использовать менее частые типы: `Transformation`, `Categorization`, `FindTheOdd`, `Matching`, `ConstructionMeaning`, `DialogRestore` — они дают разные форматы взаимодействия.

**Прогрессия сложности:** в рамках одной карточки сначала выбор (CHOICE/FORWARD_CHOICE), потом ввод (TextInput/WordArrangement).

**⚠️ Не копировать слова теории в сортировочные/табличные задания.** В Categorization/TableFill
(и любых «распредели / впиши форму») НЕ брать ровно те слова, что разобраны в примерах ЭТОЙ ЖЕ
карточки — пользователь не думает, а механически переписывает готовый ответ. Правило: ~3 слова из
теории + остальные **новые**, которых в теории НЕ было (но из пройденного курса — он их знает) →
пусть применит правило сам. Слово давать в **начальной форме**, чтобы он сам решил, какое окончание
добавить и в какой столбик положить (а не выдавать готовую форму `goes/studies` — тогда задание
бессмысленно, ответ уже написан). Не вставлять `—`/пустые ячейки ради ровного числа — лучше подобрать слово.

**⚠️⚠️ Захотел скобки `(...)` в TextInput — СНАЧАЛА переделай задание в БАНК-РЕЖИМ.** Повторяющаяся
ошибка (замечание пользователя 01.08.2026, до этого ловилось многократно): пишется пер-пунктовый
глосс `(убирают)`, `(построили)`, `(не разрешают)` под каждым пропуском. Правило простое: **как
только под пунктами захотелось скобок с русским смыслом — это сигнал, что задание должно быть в
формате `Банк:`**, а не в скобках. Эталон — `**Ex 10 · TextInput** *(ID: 46)*` в
`theory/08-passive-basics.md`:
```
Впиши в каждое предложение подходящий по смыслу пункт из банка.
Банк: не помыли, не отправили, не убирают

1. "The parcel ___ yesterday."
   Ответ: **wasn't sent**
2. "These rooms ___ every day."
   Ответ: **aren't cleaned**
3. "The windows ___ last week."
   Ответ: **weren't washed**
```
Общий пул сверху вместо скобок под каждым пунктом: юзер сам сопоставляет смысл с предложением, а
не читает готовую подсказку прямо над полем. Порядок в банке — вперемешку, элементов ≤3, значит и
пунктов ≤3 (детали формата — `exercise_templates.md` → «Банк слов»). Пер-пунктовый `(...)` остаётся
только там, где в скобках НЕ слово-подсказка, а контекст-ситуация или инструкция.

**⚠️⚠️ ОТВЕТ `TextInput` — НЕ ДЛИННЕЕ 3 СЛОВ. Целая половина предложения → `WordArrangement`**
(канон 06.09.2026, баг пойман на устройстве). Поле ввода в упражнении — узкая полоска по ширине
пропуска: длинный ответ уезжает за границы предложения, и задание выглядит сломанным. Это не
косметика — вводить `provided that all the documents are submitted` в строчку физически неудобно.

- ✓ Так МОЖНО — форма слова или короткая связка: `**wasn't sent**`, `**were my sister**`,
  `**weren't so cold**`, `**doesn't work**`. Один-три слова, и они умещаются в пропуск.
- ❌ Так НЕЛЬЗЯ — целая половина условия/предложения: `**as long as you don't smoke inside**`,
  `**only if you book in advance**`, `**provided that all the documents are submitted**`.
- **Что делать вместо:** если по смыслу задания пользователь должен собрать целую половину —
  это `WordArrangement` (чипы переносятся по строкам и вмещают любую длину), а на выбор связки
  берётся `MultipleChoice`. Одно длинное задание разбивается на **несколько коротких**
  `WordArrangement`, а не запихивается в `TextInput`.
- Правило действует и в банк-режиме: банк даёт русский смысл, но **вписываемый ответ всё равно
  короткий**. Захотелось банка из длинных половин — значит тип выбран не тот.

**⚠️ Альтернативы ответа через `/` (`**aren't allowed** / **are not allowed**`) — НЕ писать.**
Стяжения и полную форму `AnswerNormalizer` засчитывает сам. Пишем ОДИН ответ — `Ответ: **aren't
allowed**`. Строка `Ответ: **a** / **b**` нужна только для реально РАЗНЫХ по лексике вариантов, а не
для «то же самое, но без апострофа».

**⚠️ Подсказка к пропуску — русский смысл слова, не английский инфинитив.** В TextInput/FILL_BLANKS,
где вписывается форма УЖЕ ИЗВЕСТНОГО слова, подсказка в скобках = русский смысл (`(пьёт)`, `(живёт)`),
а НЕ `(глагол to drink)`. Если слово пройдено / мы просили его выучить — пользователь его знает, пусть
сам вспомнит английское слово по смыслу и поставит нужную форму (английский инфинитив = готовый ответ,
думать не надо). **Исключение:** задание проверяет именно орфографию окончания `-s` (а не знание
слова) — там можно дать английский инфинитив `(to study)` и хоть случайные глаголы: смотрим только,
верно ли допишет `-s/-es/-ies`.

**Варианты** — только в формате:
```
- Вариант
- **Правильный вариант** ✓
- Вариант
```
Никакого `a) ... ✗ / b) ... ✓`.

**Дистракторы** — реалистичные ошибки, не абсурд. Дистрактор должен быть именно той ошибкой которую реально совершает русскоязычный.

### ErrorCorrection vs FORWARD_CHOICE — критичное различие

**ErrorCorrection** — условие задания содержит только **сломанное английское предложение**, без русского перевода.  
Пользователь читает EN и находит ошибку.

**FORWARD_CHOICE** — условие задания содержит **русское предложение** (или русский контекст), пользователь выбирает правильный EN вариант.

> Правило: если для понимания задания нужен русский контекст → FORWARD_CHOICE. Если ошибка видна из самого EN предложения → ErrorCorrection.

Никогда не добавлять русский перевод в условие ErrorCorrection — это нарушение формата.

### TrueFalse — детали формата

Всегда ровно **5 утверждений**. Обязательно минимум **2 верных** и **2 неверных** (пятое — любое).

**Темы до Present Simple (начало курса):** таблица с тремя колонками — EN, RU-перевод, Верно?:
```
| # | EN | RU | Верно? |
|---|----|----|--------|
| 1 | He go to work every day. | Он ходит на работу каждый день. | ✗ |
```

**С Present Simple и далее — колонка RU УБИРАЕТСЯ** (команда дана 25.06.2026). Две колонки —
EN + Верно?; смысл пользователь ловит сам / long-press переведёт незнакомое слово:
```
| # | EN | Верно? |
|---|----|--------|
| 1 | He go to work every day. | ✗ |
```
TrueFalse — это всегда «суди конкретное предложение», поэтому перевод тут не нужен (исключение из
§4-правила «условие-правило можно перевести» сюда не попадает — здесь нет правила-инструкции).

### Categorization — только «в столбик» (канон 15.08.2026)

Элементы пишутся **по одному на строку**, один элемент = одна ячейка:

```
| Другу               | Незнакомцу                     |
|---------------------|--------------------------------|
| Where are you?      | Do you know where the exit is? |
| What time is it?    | Could you tell me the time?    |
```

⚠️ Старый строй «несколько элементов в одной ячейке через запятую» ОТМЕНЁН — конвертер запятую больше
не режет, поэтому перечисление склеится в один чип-простыню. Весь курс переведён в столбик
(19 заданий, 15.08.2026), обратно не возвращаем. Побочная польза: запятая внутри фразы стала
безопасной (`Excuse me, do you have a pen?` — один элемент, а не два огрызка).

Пул в приложении рисуется **всегда по два чипа в ряд** (слот — половина экрана, независимо от числа
категорий), поэтому длинный элемент = высокий многострочный чип и рваная сетка: держим элементы
короткими (см. правило габаритов в `exercise_templates.md`).

### WordArrangement — формат таблицы

Таблица — **2 колонки** `| Слово | Лишнее? |`. Перевод слов НЕ пишем: чипы перевод не показывают,
пользователь зажмёт слово (long-press) и получит перевод сам.

**Дистракторов — от 3 до 5**, варьировать число. Можно добавлять «наёбки» — слова, правдоподобно
подходящие, но неверные по смыслу (напр. `evening` вместо `morning`).

```
| Слово  | Лишнее? |
|--------|---------|
| jumped | —       |
| the box| —       |
| into   | ✗       |  ← дистрактор
```

## 5. AI упражнения

**Главный источник:** `grammar8r_plan.md` → раздел "AI-упражнения — модель данных и флаги"

> **Сколько AI на карточку — гибко (обновлено 25.06.2026).** На карточке может быть **1, 2 или 3**
> AI-упражнения (`_ex1`, `_ex2`, `_ex3`), если правило стоит того и каждое проверяет свою грань;
> может не быть **ни одного** (вводные/справочные/концепт-карточки — без AI). Каждый блок
> `#### AI Exercise` пишется отдельно со своим `ID` и полным набором полей; конвертер парсит каждый
> независимо. Старое «одно `_ex1` на карточку» — отменено.

### Обязательные поля

```
**ID:** basics_card{N}_ex1
**Title:** "Глагол + объект"
**Input Mode:** FREE_WRITE / FILL_BLANKS
**Words Source:** NONE
**AI Config Profile:** EXERCISE_LIGHT
**User Instruction:** "Что делать пользователю — без технических деталей"
**Prompt Template:** "Инструкция для AI — что генерировать, как проверять, как объяснять ошибку."

Пример вывода AI: 'конкретный текст того, что AI выдаст пользователю'
```

### Критичные правила

- **⚠️⚠️ ЗНАЧЕНИЕ ЛЮБОГО ПОЛЯ — РОВНО ОДНА СТРОКА, без переносов** (закреплено 30.08.2026, фидбек
  пользователя). Касается всех полей блока, но больнее всего `**Prompt Template:**` — он длинный, и
  рука сама тянется разбить его на абзацы. Разбивать НЕЛЬЗЯ: `md_to_json.py` → `parse_ai` разбирает
  поля построчным regex `^\*\*([^*]+):\*\*\s*(.+)$`, поэтому в `promptTemplate` попадёт **только
  первая строка**, а всё, что после переноса, молча потеряется — сборка не упадёт, промт приедет
  на сервер обрезанным.
  - ❌ Так НЕЛЬЗЯ: `**Prompt Template:** "Контекст: … <перенос строки> ⚠️ ГЛАВНОЕ ТРЕБОВАНИЕ: …"`
  - ✓ Так НАДО: весь промт одной строкой, а внутренние списки-инвентари нумеруются прямо в строке —
    `… каждый запуск бери другую примету. 1. ДРЕВНОСТЬ: … 2. РУССКОЕ УЖЕ: … 3. ТОЧНАЯ ДАТА: …`
    Читаемости это не вредит: промт всё равно уходит модели сплошным текстом.
  - **Исключение ровно одно —** `Пример вывода AI:`: он и ДОЛЖЕН стоять отдельным абзацем СНАРУЖИ
    кавычек `Prompt Template` (у него свой regex `EXAMPLE_LINE`, конвертер вплетает его в промт сам).
    Но сам пример — тоже одна строка.
- `User Instruction` — только что делать. Без слов "AI", "FILL_BLANKS", технических деталей.
- После `Prompt Template` **обязательно** идёт строка `Пример вывода AI: '...'` с реальным,
  конкретным текстом того, что AI выдаст пользователю. Без неё нельзя оценить, сработает ли
  задание и понятно ли оно — по одной этой строке читающий должен сразу понять суть упражнения.

  ⚙️ **Пишется СНАРУЖИ кавычек `Prompt Template`, отдельным абзацем сразу под ним** (не частью
  значения поля!) — конвертер сам подхватывает эту строку и СОБИРАЕТ из неё финальный промт:
  ```
  **Prompt Template:** "Задай пользователю ... При ошибке исправь и объясни по-русски."

  Пример вывода AI: '1. ... 2. ... 3. ...'
  ```
  Что делает конвертер автоматически (см. `md_to_json.py` → `parse_ai`, `EXAMPLE_FRAME`):
  1. Дописывает пример к `promptTemplate` вместе с готовой обвязкой **«это ОБРАЗЕЦ СТРУКТУРЫ —
     не повторяй его дословно, придумай свою ситуацию со своими словами»** — так пример и помогает
     AI с форматом вывода (особенно для `FILL_BLANKS`), и не приводит к дословным повторам.
  2. Если `Input Mode: FILL_BLANKS` — добавляет ещё одну строку-канон про обязательный формат
     пропусков `[___]` (с квадратными скобками — именно его парсит сервер, см. `db_schema.md`
     → `AiExerciseInputMode`). Писать это самому в `Prompt Template` не нужно — конвертер добавит сам.
  3. Если строки `Пример вывода AI` нет вообще — печатает **WARNING с конкретным `id` упражнения**
     (`md_to_json.py` / `check.py` → `WARNINGS:`), чтобы сразу было видно, где забыли.

  Двойная польза одной строки: 1) AI получает живой образец формата в промте, 2) человек читает
  её же при ревью и сразу понимает суть и качество задания, ещё до похода в БД.
  ❌ Не писать пример ВНУТРИ кавычек `Prompt Template` — конвертер унесёт его как часть текста
  без обвязки «это образец», и AI рискует начать повторять его дословно.
- **⚠️ Сколько заданий за раз — зависит от типа ответа (FILL_BLANKS vs FREE_WRITE):**
  - **`FILL_BLANKS`** (пользователь **вписывает слово/форму в готовое предложение от ИИ**) → «Дай
    пользователю **сразу несколько** … предложений (всего N)», N обычно 3–4. Вписать форму в 3–4
    готовых предложения — необременительно.
  - **`FREE_WRITE`, где пользователь продуцирует ЦЕЛОЕ предложение сам** (перевод RU→EN, «опиши
    себя/свой день») → **ОДНО задание за раз**: «Дай пользователю **одно** русское предложение …»,
    и строка `Пример вывода AI` — одно предложение (без списка 1./2./3.). Писать целый перевод по
    3–4 разом — утомительно.
  - **⚠️ «НЕ по одному за раз».** Для `FILL_BLANKS` формулировать именно «сразу несколько (всего N)»,
    а НЕ «по одному за раз»: у ИИ нет памяти между сообщениями — «по одному» бессмысленно (модель не
    помнит, сколько уже выдала) и противоречит `Пример вывода AI` со списком 1. … 2. … 3. (У FREE_WRITE
    «одно предложение» — это единый вывод за раз, а не «по одному из скрытой очереди», — противоречия нет.)
- Ошибки AI объясняет **по-русски**, кратко, конкретно.
- **⚠️ В КАЖДЫЙ `Prompt Template` дописывать: не придираться к пунктуации и регистру** — проверять
  только грамматику по теме упражнения. Формулировка (в конец промта): «Не придирайся к знакам
  препинания и заглавным буквам — оценивай только грамматику». Зачем: без этого AI заваливает
  свободный ответ за пропущенную точку/запятую или строчную букву, хотя грамматика верна, — юзер
  бесится. (Хардкод-упражнения это уже игнорируют на уровне `AnswerNormalizer`; у AI-заданий за это
  отвечает сам промт — отсюда обязательная строка.)
- `Words Source: NONE` для предтемы "Основы" (слов ещё мало). `GENERAL` — для тем где слова уже накоплены.
- `FILL_BLANKS` — когда AI присылает текст с пропусками `[___]`. `FREE_WRITE` — всё остальное.
- **⚠️⚠️ AI-проверяльщик свободного ответа → `Words Source: NONE`. ЖЁСТКО (юзер жаловался многократно).**
  Если пользователь САМ пишет текст (`FREE_WRITE`: «опиши себя/друга/свой день»), а AI его только
  проверяет — это `NONE`, и строку «если в списке слов есть подходящие — желательно строить вокруг них»
  НЕ добавлять. Слова пользователя тут не используются, AI — просто валидатор; сливать/подмешивать
  лексику незачем.
  ❌ Так делать НЕЛЬЗЯ (реальная ошибка): задание «опиши свой день» со `Words Source: GENERAL` и фразой
  «желательно подсказывать ситуации вокруг них». «Юзер сам пишет» = валидатор = `NONE`, точка. Не
  рационализировать GENERAL формулировкой «подсказывать вокруг слов» — если ИИ не генерит контент из
  слов, GENERAL не нужен.
  ✓ `GENERAL` + мягкий кивок про словарь — ТОЛЬКО когда AI **сам генерирует** задание из слов юзера
  (пропуски, ситуации, предложения на перевод). Критерий: «использует ли AI присланные слова, чтобы
  что-то СОЗДАТЬ?» Нет → `NONE`.
  - 🛑 **МЕХАНИЧЕСКИЙ ЧЕК перед КАЖДЫМ AI-блоком (делать всегда, ошибка вылезала много дней подряд):**
    смотрим на первое слово `User Instruction`. Если это **«Напишите / Расскажите / Опишите / Сделайте /
    Перепишите / Вставьте / Исправьте / Ответьте»** — пользователь САМ продуцирует текст, AI его только
    судит → `Words Source: NONE`, и НИ строки про список слов в `Prompt Template`. `GENERAL` ставим
    ТОЛЬКО если AI берёт слова юзера и из них ГЕНЕРИТ контент (пропуски/ситуации/предложения на перевод).
    Реальные срывы: «опиши свой день» (MT53) и «напиши предложение о распорядке с выражением времени»
    (MT54 card169) — оба ошибочно стояли `GENERAL`, должны быть `NONE`. Фокус задания (структура/время/
    принцип) ≠ повод тянуть лексику юзера.
  - ⚠️ **УТОЧНЕНИЕ (MT55, 30.06): механический чек по первому слову — грубый, и на ПЕРЕВОДЕ он врёт.**
    Решает не «кто пишет текст», а **нужен ли ИИ список слов юзера, чтобы ПОСТРОИТЬ само задание.**
    Три случая (держать в голове все три):
    1. **RU→EN перевод, где ИИ САМ сочиняет исходное русское предложение** («ИИ даст русское
       предложение — скажи по-английски») → **`GENERAL`**. Исходник обязан состоять из слов, которые
       юзер ЗНАЕТ (иначе он не переведёт лексику), поэтому ИИ строит фразу из присланного списка.
       Здесь формулировка про слова — **жёстче «желательно»**: «бери только знакомые слова из списка,
       чтобы трудность была в грамматике, а не в незнакомой лексике». Это законная причина GENERAL,
       хотя `User Instruction` и начинается с «Напишите».
    2. **Трансформация уже ГОТОВОГО самодостаточного предложения** («сделай это отрицанием/вопросом»,
       «исправь ошибку в этом предложении») → **`NONE`**. Предложение дано целиком, юзер только меняет
       грамматику — его словарь ни при чём, подмешивать лексику незачем.
    3. **Свободный ответ юзера + ИИ только валидатор** («опиши свой день/друга») → **`NONE`** (как выше).
    Критерий-резюме: ИИ **генерит контент ИЗ слов юзера** (перевод-исходник, пропуски, ситуации) →
    `GENERAL`; юзер пишет сам ИЛИ крутит готовое предложение → `NONE`.
- **⚠️ `FILL_BLANKS` на форму известного слова → русский глосс в скобках.** Когда проверяем ФОРМУ
  (а не орфографию), в пропуске давать русский перевод глагола `(живёт)`, не английский инфинитив —
  пользователь сам вспоминает слово. Чисто орфография `-s` — английский инфинитив `(to study)` ок
  (см. §4 «Подсказка к пропуску»).

### ⚠️⚠️ ПРОМТ ПИШЕМ ПОЛНЫЙ — четыре блока, а не пара строк (канон 09.09.2026, фидбек)

Короткий промт («дай предложение, проверь форму, объясни ошибку») — брак: модель не знает, что именно
пользователь прошёл, придумывает задание не по теме, лезет в сложные обороты и оценивает не то.
`Prompt Template` — это ТЗ для модели, и оно пишется полным, одной длинной строкой, по четырёх­блочной
структуре.

**Главный принцип всех четырёх блоков: ИИ проверяет ровно то, что МЫ рассказали пользователю, и
объясняет ошибки НАШИМИ словами.** Промт — не пересказ темы «из учебника», а выжимка наших карточек:
те же формулы, те же ловушки, те же образы («get to — это приставка до-», «be — фотография, get —
щелчок переключателя»). Тогда фидбек ИИ звучит как продолжение карточки, а не как чужой урок.

1. **Контекст** — две части, обе обязательны:
   - **1а. Материал карточки (или темы, если это капстоун).** `Контекст: пользователь только что прошёл
     карточку о …. Он знает: …` и дальше ПЕРЕЧЕНЬ фактов — формулы, ловушки, пары-контрасты, ключевые
     примеры в скобках, по возможности той же формулировкой, что в теории. Модель обязана видеть
     материал, на котором проверяет, — иначе она проверяет свои представления о теме, а не наш курс.
     У капстоуна Live Practice перечень идёт по всем микротемам темы: роль → смысл → пример.
   - **1б. ГРАММАТИЧЕСКИЙ ФОН — что пользователь уже прошёл по курсу и чего ещё НЕ прошёл**
     (канон 11.09.2026, фидбек). Отдельной фразой, списком времён и конструкций, взятым по дереву
     `grammar8r_plan.md` на момент этой темы: `ГРАММАТИЧЕСКИЙ ФОН — что он уже прошёл по курсу: Present
     Simple и Present Continuous, Past Simple…` и сразу `ЕЩЁ НЕ ПРОШЁЛ: Future Continuous, Future
     Perfect… — такие формы в заданиях не используй`. Зачем: без фона модель строит фразы на
     непройденной грамматике (трудность уезжает из темы карточки) и, хуже, может придраться к
     пользователю за форму, которой мы его ещё не учили, или не засчитать верное пройденное время.
     Если в теме есть форма, которая на этом фоне даёт двусмысленность, — запретить её прямо
     (реальный случай, тема get: `I've got your email` у британцев совпадает с `have got` «у меня есть»,
     поэтому Present Perfect от get в значении «получил» в задания не пускаем).
2. **Задание** — `ЗАДАНИЕ: дай пользователю ОДНУ …` + жёсткий ограничитель сложности:
   **`ДЕРЖИ ФРАЗУ ПРОСТОЙ`** — длина в словах, одно подлежащее и один глагол, без придаточных,
   перечислений, идиом и двух действий в одной фразе; прямым текстом «в дебри не уходи, сложных
   сюжетов не выдумывай». Без этой строки модель усложняет задание до неузнаваемости, и трудность
   уезжает из грамматики в лексику. Сюда же:
   - **«в условии НЕ подсказывай правило/роль/нужную конструкцию»** — выбрать её пользователь должен
     сам (канон «без подсказки-правила» из §4 действует и для ИИ);
   - **время фразы — только из пройденного** (опирается на блок 1б), с частотой: «чаще Present Simple и
     Past Simple, иногда will, going to…»;
   - при `Words Source: GENERAL` — строка про слова пользователя (формулировки — ниже в этом разделе).
3. **Инвентарь перебора** — `ЧЕРЕДУЙ ПОВОД от запуска к запуску, не повторяя один и тот же два раза
   подряд: 1. … 2. … 3. …` с живым примером на каждый пункт, плюс чередование форм (утверждение /
   отрицание / вопрос, отрицательный вопрос, времена) с частотой («вопрос не реже чем каждый третий
   запуск»). Правила инвентаря:
   - **каждый пункт — из того, что есть в карточках**, с примером, который звучит как наша теория;
     пункта, которого мы не объясняли, в инвентаре быть не может;
   - **ловушки-границы правила** — пункты, где изучаемая конструкция НЕ подходит и нужна соседняя
     (в теме get: «я устал» → `I'm tired`, «стать врачом» → `become`, «добираюсь сорок минут» →
     `It takes`), с частотой («примерно каждый третий запуск, не два раза подряд»). Именно они
     проверяют, понял ли человек правило, а не выучил «везде ставь get»;
   - у контрастных заданий (пары, выбор) — **порядок внутри пары тоже меняется**, и прямо сказать
     «образцы дословно не повторяй».
4. **Оценка** — что считать верным + разбор ТИПОВЫХ ошибок русскоязычного **по одной строке на
   каждую ловушку из карточек** («написал `Did you got` → покажи, что после did первая форма»;
   «написал `get to home` → напомни, что home уже значит «домой»»). Сверка простая: каждая плашка
   `**Ловушка:**` и каждый `✗` из теории должны иметь свою строку в ОЦЕНКЕ — объяснение тем же
   аргументом, что в карточке. Дальше обязательно:
   - **что засчитывать**: синоним или другая формулировка при верной грамматике, сокращения
     (`didn't` / `did not`), другое ПРОЙДЕННОЕ время, подходящее по смыслу, законный вариант
     (`gotten`, `was` вместо `were`);
   - **точный, но менее разговорный вариант** (`receive`, `earn`, `arrive`) — засчитать и одной
     строкой сказать, что в разговоре привычнее;
   - «если выбрал другое слово, а грамматика верна — лексику не правь»;
   - «объясняй по-русски, коротко, без грамматических терминов» и обязательный хвост «не придирайся
     к знакам препинания и заглавным буквам — оценивай только грамматику».

Ориентир объёма — **1500–5000 символов** в одной строке (медиана по курсу ≈1500; капстоун на всю
тему с грамматическим фоном может выйти до ~7500 — это нормально, резать разбор ошибок ради цифры нельзя). Промт короче
~800 символов почти всегда означает, что выпал блок 1 или блок 4. Технического лимита длины нет:
ни `md_to_json.py`, ни проверки `check.py`, ни схема `ai_exercise_prompts` промт не режут — ориентир
держим ради стоимости запроса (промт уходит в каждый вызов ИИ) и чтобы модель не утонула в воде.

**Самопроверка промта перед сдачей (по каждому AI-блоку):**
- [ ] **Промт полный?** Есть все блоки — 1а (факты карточки), 1б (пройденная / непройденная
      грамматика), ЗАДАНИЕ, инвентарь, ОЦЕНКА — и каждая ловушка и каждый `✗` карточки имеют строку
      в ОЦЕНКЕ?
- [ ] 🚨 **Промт без воды?** (фидбек 11.09.2026) Перечитать промт целиком, как будто видишь его
      впервые, и выбросить предложения, которые не меняют поведение ИИ. Каждый символ промта уходит в
      КАЖДЫЙ запрос — вода съедает лимиты и деньги, а заодно размывает важные требования, и модель
      начинает путаться в них. **Тест на каждое предложение: убери его мысленно — ИИ станет делать
      что-то иначе?** Нет → вода, удалить. Типичная вода:
      - одно и то же требование повторено в двух блоках (в ЗАДАНИИ и ещё раз в ОЦЕНКЕ) — оставить в
        одном месте;
      - факты в 1а, на которые не опирается ни задание, ни инвентарь, ни оценка, — пересказ темы «для
        полноты»;
      - два-три примера на одну и ту же мысль там, где хватает одного;
      - вводные и связки без содержания: «важно понимать, что», «следует отметить», «как известно»,
        «постарайся сделать так, чтобы»;
      - общие правила поведения, которые уже есть в базовом промте (`phases/phase3/ai_base_prompt.md`):
        тон, дружелюбие, «будь терпеливым».
      **НЕ вода и не режется:** грамматический фон 1б, «ДЕРЖИ ПРОСТЫМ» с числами, частоты форм,
      строки разбора конкретных ошибок, список «что засчитывать», обязательный хвост про пунктуацию.
      Сокращаем формулировку, но не теряем смысл: из двух фраз про одно — одна короткая.
- [ ] В инвентаре нет ничего, чего мы не объясняли, и нет форм из «ЕЩЁ НЕ ПРОШЁЛ»?
- [ ] Условие не подсказывает правило; есть «ДЕРЖИ ПРОСТЫМ» и частоты для форм?
- [ ] `Words Source` выставлен по критерию ниже, и при `GENERAL` есть строка про слова пользователя?
- [ ] Хвост про пунктуацию на месте, промт одной строкой, `Пример вывода AI` снаружи кавычек?

### ⚠️ AI на всю микротему → `Summary` его карточки покрывает ВСЮ микротему (канон 06.09.2026)

Когда у микротемы **одно** AI-задание и оно стоит на последней карточке, гоняя весь материал
микротемы, — кнопка «?» внутри этого задания открывает `#### Summary` **той самой карточки**, а не
всей микротемы. Значит короткий конспект «только про эту карточку» оставляет пользователя без
подсказки ровно по тому, что AI и спрашивает.

Правило: **карточка, на которой стоит AI на всю микротему, получает `Summary`-конспект всей
микротемы** — формула типа, ключевые ловушки, отрицание, вопрос, соседние развилки. Пишется так
же сплошным текстом, просто плотнее (6–10 предложений вместо 3–4). Хардкод-упражнениям этой же
карточки расширенный конспект не мешает — лишняя строка подсказки вреда не наносит, а дыры в
подсказке к AI-заданию наносят.

Карточки БЕЗ AI держат обычный короткий `Summary` — по своей теме.
📌 Эталоны: `Card 489` / `Card 492` / `Card 496` в `theory/16-conditionals.md`.

### `Words Source: GENERAL` — как писать `Prompt Template`

> Базовая лексика ("пользователь это знает": предлоги, местоимения, to be, do/does/did, артикли
> и т.д.) уже подмешивается в системный промт централизованно — см. `grammar8r_plan.md` →
> «Алгоритм выборки слов» → «Что зашито в system prompt». **Повторять это в `Prompt Template`
> каждой карточки не нужно** — дублирование.

Что нужно сделать самим — добавить **мягкую** инструкцию про слова из присланного списка
(70 из Words8r + 30 из course_words пользователя — см. `AiExerciseWordsSource.GENERAL`):

```
...если в присланном списке слов пользователя есть подходящие — желательно
строить фразы вокруг них: фокус задания на <структуре/предлогах/ударении —
что именно проверяет это упражнение>, а не на конкретной лексике...
```

⚠️ **Формулировка — ровно "желательно строить вокруг них"** (а не жёстко "ТОЛЬКО из списка").
**НЕ дописывать** "но это необязательно / не строгое условие" — достаточно "желательно". Жёсткая
формулировка ("ТОЛЬКО из списка") живёт в системной инструкции для **режимов вкладки Практика**, где цель — натренировать
конкретные слова. У карточек теории цель другая — отработать грамматическую идею; жёсткое
требование вписать случайные 100 слов пользователя в грамматическое упражнение портит задание
(AI начинает натягивать лексику на структуру). Поэтому в `Prompt Template` карточек — мягкий
кивок в сторону словаря пользователя, а структурный фокус остаётся приоритетом.

Эталон — AI Exercises карточек 72–77 в `theory/03-language-structure/01-how-english-thinks.md`.

### ⚠️ Финальная карточка «Live Practice» — канон третьего задания «найди и исправь»

Каждая тема времени заканчивается микротемой-капстоуном (одна карточка, 3 AI: перевод EN→RU,
перевод RU→EN, «найди и исправь»; общая структура и Theory — `grammar8r_plan.md` → ⚠️-канон
«ФИНАЛЬНАЯ AI-МИКРОТЕМА»). У **третьего** задания есть свой жёсткий формат (закреплено 09.08.2026,
фидбек пользователя) — писать сразу так, не изобретая заново:

- **РОВНО ОДНА ошибка на три предложения.** Два других — полностью правильные. Формулировка
  «иногда ошибка в одном, иногда в двух, иногда во всех трёх» ОТМЕНЕНА: она есть в старых
  капстоунах (Present Simple, Present Continuous, Past Simple, Past Continuous) — их не
  переписываем, но новые так не пишем.
- **Номер сломанного предложения меняется от запуска к запуску** — требовать в промте явно:
  «не ставь его всё время первым».
- **Пользователь делает ТРИ вещи:** находит сломанное предложение, переписывает его правильно и
  СВОИМИ СЛОВАМИ говорит, что было не так. Требование объяснить — обязательно в `User Instruction`.
- **Объяснение пользователя ИИ оценивает по сути, а не по формулировке** (грамматических терминов
  от него не ждём). Исправление верное, а объяснение кривое или отсутствует → исправление
  засчитать, причину мягко назвать самому. Указал не на то предложение → сказать, какое было
  сломано на самом деле. Починил иначе, чем задумал ИИ, но результат верный → засчитывать.
- **Ошибка только грамматическая, не пунктуационная:** запятые и точки во всех трёх предложениях
  расставлены верно, пунктуационных ловушек не подсовывать — иначе задание конфликтует с
  обязательной строкой «не придирайся к знакам препинания».
- **Инвентарь ошибок задаётся в промте СПИСКОМ** — по одной типичной ошибке русскоязычного из
  каждой микротемы темы, плюс требование каждый запуск брать другую.
- `Words Source: NONE` — предложения даны целиком, словарь пользователя тут ни при чём.

## 6. Words8r Sync

В конце каждой **микротемы** (не карточки) — таблица слов для добавления в словарь:

```
### Words8r Sync · Краткое название

| Слово | Переводы | Транскрипция |
|-------|----------|-------------|
| word  | перевод  | [транскрипция] |
```

Включать: ключевые слова микротемы которые пользователь должен запомнить.  
Не включать: служебные слова уже изученные в предыдущих микротемах.  
Не включать: производные формы, которые логически вытекают из базовой. Если пользователь знает базу и может сам вывести форму — не добавлять.

> ⚠️ **СТРАТЕГИЯ СЛИВА: что и сколько сливать с каждой микротемы (канон, 30.06.2026).**
> Цель — пользователь параллельно с грамматикой ровно наращивает базовый словарь, а не получает
> перекос в одну часть речи.
> - **Сколько: 3–5 ещё НЕ слитых слов на микротему, ПЯТЬ — жёсткий потолок** (канон 23.07.2026;
>   раньше было «~3–6»). Причина: одна итерация изучения слов у пользователя = ровно 5 слов, и слив
>   микротемы должен ложиться в неё целиком, не разрезаясь на полторы итерации. Не влезает нужное
>   слово — не растягиваем слив, а выбрасываем менее важное (даже у вводных/концептных микротем, где
>   раньше слов не было — теперь добавляем, если по смыслу влезают в примеры). Проверять по уже
>   слитому инвентарю (Sync-таблицы всех тем), чтобы не дублировать (см. правило дублей ниже).
> - **С каких начинать:** с **самых базовых, частотных** слов. Сначала закрываем повседневную лексику
>   (есть/пить/нести/дом/быстрый/громко…), редкое и узкое — позже.
> - **⚠️ Глаголы сливаем ТОЛЬКО правильные (regular).** Неправильные глаголы в Sync-таблицы
>   микротем НЕ попадают вообще — они целиком идут отдельной колодой `irregular_verbs` (по плану,
>   где расписано, какие слова сливать). Перед тем как внести глагол в слив — убедиться, что он
>   правильный (форма прошедшего/причастия = основа + `-ed`): `to wash`/`to paint`/`to laugh` — да;
>   `to wear`/`to write`/`to run` — нет, это неправильные, не сливать. (Также [[feedback_words8r_sync_base_only]].)
> - **Баланс частей речи:** в наборе слов микротемы держать **примерно равное соотношение** —
>   существительные · правильные глаголы · прилагательные · наречия (и прочее: предлоги, местоимения).
>   НЕ сливать одни глаголы. Если в одной микротеме набрались только глаголы — добавить пару
>   существительных/прилагательных, которые встречаются в её же примерах.
> - **Наречия сливаем СРАЗУ, не дожидаясь темы «Наречия».** Их роль (образование `-ly`, позиция,
>   степени) разбирается позже в отдельной теме — но само слово-наречие можно открыть раньше как
>   лексику. Плюс: к моменту темы «Наречия» будет уже слито заметно больше наречий, чем встречается
>   в самой теме, — это нормально и желательно.
>   ⚠️ НО: наречия, которые образуются от прилагательного через `-ly` (quiet → quietly, slow → slowly,
>   careful → carefully), **НЕ сливаем** — это производная форма, выводится из базы (общее правило
>   «не включать производные» выше). Сливаем базовое прилагательное (`quiet`), а наречие пользователь
>   выведет сам. Сливать как отдельную лексику стоит только наречия, которые НЕ выводятся из
>   прилагательного: `now`, `often`, `still`, `soon`, `today` и т.п.
> - ⚠️⚠️ **КАК слово вплетается: только внутри АНГЛИЙСКОГО примера, никогда термином в русской прозе**
>   (фидбек 28.08.2026, названо кринжем). Слово слива должно попасть в карточку так, как оно попадает
>   в речь: стоять в английском предложении-примере, которое и без него было бы написано. Нельзя
>   протаскивать его в русский текст объяснения глоссом-вставкой ради галочки «слово использовано».
>   - ❌ Так НЕЛЬЗЯ (реальный брак, МТ169): «Стоит собеседнику заторопиться или начать шептать
>     (`to whisper`), и хвостик пропадает» — слово воткнуто в русскую прозу скобкой, к грамматике
>     карточки отношения не имеет, читается как отчёт о выполнении квоты.
>   - ✓ Так НАДО: **Kate had whispered something and left the room.** — слово живёт в английском
>     предложении, которое иллюстрирует правило карточки; пользователь встречает его в работе, а
>     перевод при нужде берёт long-press'ом.
>   - Критерий перед сдачей: выкинь слово слива из карточки мысленно — если рассыпается только
>     русская фраза-подводка, а не пример, значит слово было приклеено, а не вплетено. Такое слово
>     либо переносим в нормальный английский пример, либо меняем на другое, которое в примеры темы
>     ложится само.
> - **Набор слов определяем ДО написания карточек, а не после.** Сначала — какие 3–6 слов сливаем
>   с этой микротемы, потом пишем карточки и **активно вплетаем эти слова в примеры и объяснения**,
>   показывая на живом примере, как они работают (косвенно, по ходу разбора грамматики). Поэтому
>   слова обязаны быть: (1) **подходящими** под тему — чтобы естественно лечь в её примеры, и
>   (2) **базовыми** — из тех, что любой говорящий по-английски должен знать как можно раньше
>   (повседневная высокочастотная лексика), а не редкими/узкими. Слово, которое некуда органично
>   вставить в примеры микротемы, в её Sync не берём — ищем такое, что и базовое, и в тему.

> ⚠️ **ОБЯЗАТЕЛЬНО: никаких дублей слова — ГЛОБАЛЬНО по всему курсу, а не только внутри категории.**
> **Критерий дубля = одинаковое написание И одинаковый перевод** — где угодно в курсе, в любой
> категории. Пользователь идёт по курсу линейно и параллельно учит слова — встретить одно и то
> же слово с тем же переводом во второй раз (даже в другой категории/теме) означает, что он его
> уже когда-то открыл и, возможно, выучил. Перед добавлением слова в Sync — проверить, не
> встречалось ли оно (слово+перевод) раньше в ЛЮБОЙ микротеме любой темы. Если встречалось — НЕ
> добавлять повторно (дубль в Словаре = путаница, два прогресса на одно и то же слово).
> - **Разный перевод → НЕ дубль, оставляем.** Омонимы (`am` глагол vs `am`=a.m.; `past`=мимо vs
>   `past`=прошло) — это разные слова по смыслу, и каждый получает свою карточку слова.
> - **Действие: то же написание + ДРУГОЙ смысл → сливаем повторно с новым переводом.** Если слово
>   уже слито в одном значении, а в новой теме оно несёт другое — заведи его снова со СВОИМ
>   переводом (это не дубль, а второй смысл). ⚠️ **НО: если нужный смысл УЖЕ входит в слитый ранее
>   перевод — это тот же смысл, повторно НЕ сливаем.** Пример: `too` уже слит в «Основах» как
>   «тоже; слишком» — значение «слишком» там уже есть, поэтому в теме «Наречия степени» повторно
>   `too` не заводим. А вот если бы раньше было только «тоже» — тогда «слишком» шло бы вторым сливом.
> - ⚠️ Это отменяет старое допущение «дубли в разных категориях — ОК»: на практике одно и то же
>   слово+перевод в двух категориях даёт пользователю два независимых прогресса на одно и то же
>   слово, что и есть путаница, которую мы хотим избежать.
> Проверка на дубли (слово+перевод) по всему курсу — часть самопроверки (раздел 9).

> **Глаголы в Sync-таблице и в тексте теории — всегда с `to` и в базовой форме:** `to run`, `to think`, `to be`, `to have`.
> Никаких окончаний: не `to running`, не `to swam`, не `to finished` — только чистый инфинитив.
> Исключение — модальные (`can`, `must`, `should`, `may`): у них нет инфинитива с `to`, пишем без.

> **Несколько переводов и контекст в скобках.**
> У слова может быть несколько переводов — перечисляем через запятую: `любить, нравиться`.
> ⚠️ **Разделитель между переводами — ВСЕГДА запятая, никогда точка с запятой** (`прочь, в отдалении`,
> не `прочь; в отдалении`). `;` в колонке «Переводы» не использовать.
> Если одно слово переводится по-разному в зависимости от контекста — добавляем контекст в скобках
> прямо внутри перевода, но только когда без него реально непонятно:
> `any` → `любой (в утверждениях), какой-нибудь (в вопросах), никакого (в отрицаниях)`
> Не злоупотреблять: если перевод очевиден без контекста — скобки не нужны.

> **Пример:** `can` — добавить. `can't` / `cannot` — НЕ добавлять: отрицание очевидно из `can + not`.  
> Критерий: "Нужно ли учить это как отдельное слово, или оно выводится из уже известного?" Если выводится — не добавлять. (Но всякие слова с разным исуфиксами надо сливать, типа лучше спроси меня, а я скажу уже надо или нет)

> **Синонимы / варианты произношения в одной строке.**
> Если два слова значат одно и то же (someone / somebody, color / colour) — можно объединить в одну строку Sync-таблицы, перечислив через запятую в колонке «Слово»:
> `| someone, somebody | кто-то | [ˈsʌmwʌn] / [ˈsʌmbədi] |`
> Приложение отображает их как один словарный элемент. Транскрипции тоже через `/`.
> Критерий объединения: слова взаимозаменяемы в любом контексте без смысловой разницы. Если есть нюанс (any vs some) — заводить отдельными строками.

## 8. Строгий MD-формат для конвертера (machine-readable) ⚙️

> ⚠️ **Зачем это.** Теория хранится в БД не строкой, а массивом **типизированных блоков**
> (`paragraph` / `heading` / `list` / `table` / `callout` — см. `db_schema.md` → «Блоки теории»).
> Скрипт-конвертер превращает MD → JSON-блоки **по разметке, а не по смыслу слов**. Поэтому
> разметка обязана быть единой: одинаковая мысль — одинаковое оформление во всех карточках.
> Несоблюдение → блок распарсится не тем типом → кривой рендер у пользователя.

> 💡 **Рендер уже написан — можно подсмотреть, как блок будет выглядеть.** Если сомневаешься,
> как отрисуется конкретный блок (плашка, таблица, контраст ✗/✓, деление длинных слов в таблице),
> смотри реальный код:
> - **Блоки теории** — рендер `grammar-app/.../ui/components/theory/TheoryBlockView.kt`
>   (`ThinDivider` — тонкая линия-разделитель; авто-линия перед каждым `Heading`; `CalloutBlock` —
>   рамки-плашки по `CalloutVariant`; правила таблиц — `tasks/ui_table_rendering.md`).
>   Типы блоков и `enum CalloutVariant {TRAP,WARNING,TIP,FORMULA,NOTE}` — `domain/model/theory/TheoryBlock.kt`;
>   разбор JSON→домен (`variant` → `CalloutVariant`, цвет `NOTE` = `TextSecondary`) —
>   `data/mapper/TheoryContentMapper.kt::toVariant`; какое ключевое слово → какой `variant` —
>   `tasks/tools/md_to_json.py::variant_for`.
> - **Упражнения** — `grammar-app/.../ui/components/exercise/` (вью на каждый тип:
>   `SingleSelect…`, `TrueFalse…`, `WordArrangement…`, `Matching…`, `Categorization…`,
>   `TableFill…`, `Transformation…`, `TextInput…`) и общие части в `exercise/parts/`.
> Код — справка «как отрисуется», источник правды по формату остаётся этот гайд + `exercise_templates.md`.

### Как скрипт определяет тип блока внутри `#### Theory`

| Пишем так | Тип блока |
|-----------|-----------|
| Обычная строка прозы | `paragraph` |
| `**Ярлык:** текст` — ярлык = ключевое слово плашки (Ловушка/Кстати/Важно/…) | `callout` (рамка с полоской) |
| `**Ярлык:**` на отдельной строке, а блок-тело ниже | `callout`, тело = следующий блок |
| Строка целиком в болде БЕЗ ключевого слова: `**Краткие ответы:**` | `heading` (подзаголовок) |
| Строки на `- ` или `1. ` подряд | `list` (один блок) |
| Строки на `\| … \| … \|` подряд (с разделителем `\|---\|`) | `table` (один блок) |
| Строка из одних `---` (или `***`) | `divider` (тонкая линия-разделитель) |

**Разбивай длинную теорию на части — это КАНОН, а не опция** (карточка из 5+ абзацев подряд
читается как монолит). Инструмент ровно ОДИН:
- **подзаголовок (`heading`)** — строка целиком в болде, БЕЗ ключевого слова плашки
  (`**Почему английскому нужен to**`). Рендерится крупным жирным (18sp), и UI **сам рисует тонкую
  линию ПЕРЕД ним** — отдельный `---` ставить не нужно.

⚠️ **Голый `---` внутри `#### Theory` НЕ пишем** (решение 03.08.2026). Разделять куски теории —
работа подзаголовка: у каждого куска есть «заголовок мысли», и линию UI нарисует сам. Строка из
одних `---` парсером по-прежнему поддерживается (`divider`) и в старых темах остаётся как есть,
но в новом контенте её не используем. Структурные `---` МЕЖДУ секциями карточки (после Examples,
между упражнениями, перед `### Card`) — это разметка файла, а не блок теории: они остаются.

Плашки (`callout`) линиями не оборачивай — рамка уже отделяет (перед/после Ловушки/Формулы линия
не нужна). Инлайн `___` в прозе (пропуск «… ___ ?») линией НЕ становится — линия только из строки
целиком из `---`.

⚠️ **Blockquote `>` НЕ поддерживается** — конвертер (`parse_theory`) не знает `>`, и строка `> …`
внутри `#### Theory` отрендерится как обычный абзац **с литеральной «>» в начале** (мусор на
экране). Любую врезку/примечание оформляй **плашкой** (`**Примечание:** …` = note, `**Кстати:** …`
= tip) или обычным абзацем/курсивом — но НЕ через `>`. (Шапочные `>`-заметки ВНЕ карточек —
метаданные «Категория слов», счётчики IDs — для человека; парсер их игнорирует, их можно оставлять.)

### Плашки-врезки (callout) — рамка с цветной полоской слева ⭐ АКТИВНО ИСПОЛЬЗУЙ

Это то, что красиво выделяется рамкой с цветной полоской и **сразу притягивает взгляд**. Поэтому
**активно используй плашки**: ключевую мысль, ловушку, лайфхак, важное предупреждение — оформляй
плашкой, а не топи в общем абзаце. Если по смыслу что-то «Кстати…», «Запомни…», «Ловушка…»,
«Важно…», «Не путай…» — это сигнал завернуть во врезку.

⚠️ Но без фанатизма: плашка работает, **пока её немного**. Если вся карточка в рамках — выделять
перестаёт, глаз замыливается. Ориентир: **1–4 плашки на карточку**, остальное — обычные абзацы.
Не «побольше», а «к месту и активно».

**Variant определяется по ярлыку (ключевое слово; регистр и номер неважны):**

| Ярлык содержит | variant | Полоска |
|----------------|---------|---------|
| Ловушка / Ловушки (+ «Ловушка 1», «Главная ловушка», «Ещё одна ловушка») | `trap` | красная |
| Не путай / Важно / Осторожно | `warning` | оранжевая |
| Кстати / Запомни / Секрет / Совет / Лайфхак | `tip` | зелёная |
| Формула | `formula` | моноширинный бокс |
| Примечание / Заметка | `note` | серая (`TextSecondary`) — неакцентный бокс ТОЛЬКО для второстепенного, на что «почти похуй» |

Ярлык формулируй свободно, лишь бы он **содержал ключевое слово**: «Ловушка», «Ещё одна ловушка»,
«Кстати», «Запомни главное», «Не путай X и Y», «Важно», «Главная ловушка 2». Конвертер ищет
ключевое слово внутри ярлыка — точное совпадение не требуется.

⚠️ **Рамку дают ТОЛЬКО ключевые слова из таблицы.** Любой другой ярлык в болде рамкой НЕ
становится: строка целиком в болде → `heading` (подзаголовок + авто-линия), болд + проза в той
же строке → обычный `paragraph` с инлайн-жирным. Поэтому `**Две формы:**`, `**Краткие ответы:**` —
это heading, а не плашка. (Старое «любой ярлык с `:` → note» — неверно, исправлено.)
`note` **Примечание:** — для **второстепенных** пояснений, которые читатель может пропустить без потери («тут это
не разбираем — едем дальше»): серый неакцентный бокс, не оттягивающий внимание.

⚠️ **Отсылка «полный разбор позже» сама по себе НЕ всегда `note`.** Смотри, есть ли в ней полезный
для читателя takeaway прямо сейчас:
- **есть** («а у этого есть продолжение — `too … to` / `enough … to`; разберём в теме X, пока
  узнавай») → это интересное превью → `**Кстати:**` (tip, зелёная);
- **нет** (чистый служебный дисклеймер «этот нюанс тут не трогаем, детали в теме X», без пользы
  здесь и сейчас) → `**Примечание:**` (note, серая).
Критерий: даёт ли отсылка что-то полезное/любопытное в этот момент? Да → Кстати; нет → Примечание.

⚠️⚠️ **`Примечание`/`note` — ТОЛЬКО для «почти похуй» (фидбек, повторная ошибка).** Серый бокс
не притягивает взгляд — поэтому в него нельзя класть то, что важно/легко ошибиться/ловушку/
предупреждение. Как только пояснение реально ВАЖНО (без него ошибётся, «имей в виду», «не путай»,
«запомни») — берём `**Важно:**`/`**Внимание:**`/`**Осторожно:**` (warning, оранжевая) или
`**Ловушка:**` (trap, красная), а НЕ `Примечание`. Критерий: «читатель может это пропустить без
вреда?» да → note; нет → warning/trap. Не занижать важное до серой заметки.

#### ⚠️⚠️ ФОРМУЛА/СБОРКА — ВСЕГДА плашкой `**Формула:**`, никогда прозой (канон 26.08.2026)

Любая **схема сборки** — порядок элементов конструкции, шаблон предложения, «из чего собирается
форма» — пишется ТОЛЬКО плашкой с ярлыком `**Формула:**`. Она рендерится моноширинным боксом
(`CalloutVariant.FORMULA`), и в этом весь смысл: сборка должна выделяться из текста и цепляться
глазом, а не растворяться в абзаце.

- ❌ Так НЕЛЬЗЯ (реальный случай, МТ164): «Сборка простая: `so` + признак + `that` + целая часть.
  Первая половина сообщает, НАСКОЛЬКО, вторая — ЧТО ИЗ ЭТОГО ВЫШЛО.» — формула утонула в прозе.
- ✓ Так НАДО — плашка, а объяснение отдельным абзацем под ней:
  ```
  **Формула:** so + признак + that + целая часть

  Первая половина сообщает, насколько, вторая — что из этого вышло.
  ```

Правила:
- **Ярлык — ровно `**Формула:**`** (конвертер ищет корень «формул», регистр не важен). Слова
  «Сборка», «Схема», «Шаблон» рамки НЕ дают — строка целиком в болде станет обычным подзаголовком.
- **В теле плашки — только сама схема**, без пояснений и без «первая половина значит…». Пояснение,
  разбор половин, примеры — отдельными блоками ПОД плашкой.
- **Слоты пишем словами, без скобок:** `so + признак + that + целая часть`, `X + as well as + Y`
  (квадратные скобки зарезервированы под транскрипцию и пропуски — см. «ТРАНСКРИПЦИЯ»).
- Плашка `Формула` не считается против ориентира «1–4 плашки на карточку» жёстко, но и формул на
  карточку обычно одна-две: если их больше трёх, карточка перегружена и её надо делить.
- Это про **схему сборки**. Обычное предложение-пример формулой не оформляем, для него `**жирный**`.

**Три формы записи плашки — все парсятся одинаково, выбирай по удобству:**

1. **Ярлык + короткое тело в одну строку:**
   `**Ловушка:** advice — несчётное, артикль a/an с ним невозможен.`
2. **Ярлык на отдельной строке, тело-блок ниже** (когда тело — список, таблица или абзац):
   ```
   **Ловушки:**
   - "the table's leg" ✗ → "the leg of the table" ✓
   - "the film's end" ✗ → "the end of the film" ✓
   ```
   Конвертер впитает следующий блок (список / таблицу / абзац) ВНУТРЬ рамки.
3. **Ярлык с мини-заголовком в болде + тело после:**
   `**Ловушка 1: his и her.** В русском «его»/«её» — противоположности, в английском тоже.`

⚠️⚠️ **НЕ делать подзаголовок, содержащий ключевое слово плашки** (Ловушка / Важно / Не путай /
Кстати / Формула / Примечание …). Строка `**Главная ловушка: home без предлога**` НЕ станет
подзаголовком — конвертер видит слово «ловушка» и делает из неё **отдельную пустую рамку-плашку**,
а под ней висит вторая, настоящая `**Ловушка:** …` (двойной фрейм, криво). Правильно — **сразу
писать саму плашку** `**Ловушка:** тело`, без «шапки» над ней. Подзаголовок (`heading`) — только
БЕЗ ключевого слова плашки.

⚠️ **Чтобы список/таблица попали ВНУТРЬ плашки — НЕ ставить пустую строку между ярлыком-с-телом
и списком** (`md_to_json.py` впитывает следующий блок в рамку, только если он идёт СРАЗУ, без
пустой строки — иначе список «вываливается» из фрейма):
```
**Ловушка:** … предлог лишний:
- **go home** ✓, **come home** ✓, **get home** ✓      ← без пустой строки перед списком
```

⚠️ **Отменяет старое «железное» правило** «вся строка в болде = heading». Теперь: если ярлык —
**ключевое слово плашки**, это ВСЕГДА `callout` (в любой из трёх форм выше), даже когда вся строка
в болде. `heading` остаётся только для подзаголовков БЕЗ ключевого слова (`**Краткие ответы:**`,
`**Как определить роль:**`).

> Конвертер распознаёт плашку и без `**` (`Кстати: …` обычным текстом — на случай если забыл болд),
> но **канон — всегда писать с болдом** `**Кстати:** …`: так плашка видна сразу при ревью MD.

**heading — подзаголовок секции.** Строка целиком в болде, ключевого слова плашки в ярлыке НЕТ.
Дальше идёт тело (`list`/`table`/`paragraph`). Пример: `**Краткие ответы:**`, затем список.

⚠️⚠️ **ПРЕДЛОЖЕНИЕ-ПРИМЕР НЕ СТАВИМ ОТДЕЛЬНОЙ СТРОКОЙ ЦЕЛИКОМ В БОЛДЕ** (фидбек 06.09.2026).
Правило «вся строка в болде = heading» не различает подзаголовок и пример: строка
`**If I had slept more, I wouldn't be tired now.**` станет ПОДЗАГОЛОВКОМ с авто-линией, и рядом с
настоящим подзаголовком выйдут два заголовка подряд — именно так это и выглядело у пользователя.
Особенно легко нарваться сразу под плашкой `**Формула:**`, где руку тянет показать пример целиком.
- ❌ Так НЕЛЬЗЯ:
  ```
  **Формула:** if + had + V3 · would + V1

  **If I had slept more, I wouldn't be tired now.**
  ```
- ✓ Так НАДО — вплести пример в абзац (тогда это `paragraph` с инлайн-жирным):
  `По-английски это и будет: **If I had slept more, I wouldn't be tired now.**`
- ✓ Либо списком, когда примеров два и больше: `- **If it rained, I'd stay home.**`
Само выделение примера жирным остаётся каноном (см. «ЗОЛОТОЕ ПРАВИЛО» выше) — нельзя именно
оставлять его ОДИН на строке без окружающего текста.

**Контраст ✗ / ✓ — это инлайн, НЕ блок.** Пишется внутри `paragraph`, `list` или `callout`:
- Инлайн: `"I too like pizza." ✗ → "I like pizza, too." ✓`
- Списком: `- "Me too!" ✓ — правильно` / `- "Me also!" ✗ — так не говорят`

Рендер сам заменяет эти символы на **векторные иконки Material**: `✓` → зелёная галочка,
`✗`/`❌` → красный крестик, `→` → иконка-стрелка (цветом текста), `↔` → двусторонняя стрелка (ею
размечают пары противопоставлений: «был и вернулся ↔ уехал»), `·` → круглая точка-разделитель
(ею делят половины формулы: «for + сколько времени · since + с какого момента»). Пиши их обычными символами
(`✓`, `✗`, `→`, `↔`) прямо в тексте — UI подставит иконки и подгонит размер под шрифт. Не заводить
под это отдельную структуру и не описывать словами «галочка»/«стрелка». Значки работают и в
**названиях** тем/микротем (`DualTitle` рендерит их той же утилитой), а не только в теории.

⚙️ **Значки внутри бэктиков красятся заодно со вставкой.** Нейтральные символы-иконки
(`→ ← ↔ ≠ ≈ + =`), попавшие в `` `…` ``, берут цвет вставки — формула `` `to + V1` `` подсвечивается
целиком, плюс из неё не выпадает. Вердикт `✓`/`✗` держит свой зелёный/красный всегда, где бы ни
стоял. Отдельно ничего размечать не нужно — пиши формулу как обычно.

**Инлайн-разметка внутри текста любого блока — только три маркера:**
- `**жирный**` — выделение;
- `*курсив*` — перевод английского примера (`*Я жду уже час.*`) или пояснение в скобках;
- `` `бэктики` `` — инлайн-вставка английского (токен/формула): `` `to go` ``, `` `to + V1` ``,
  `` `I want to stay` ``. UI красит вставку приглушённым цветом (`InlineCode`) + `Medium`-вес,
  **сами бэктики пользователю не показываются** — это маркер для автора, чтобы английские кусочки
  в русском тексте визуально отделялись. Long-press-перевод на словах внутри продолжает работать
  (текст остаётся текстом, не «чип»). Рендер — единая утилита `parseInlineMarkdown`.

⚠️ **Альтернативы через слэш — ОДНА пара бэктиков на всё** (канон 01.07.2026). Когда перечисляем
варианты одного токена через `/`, берём в бэктики всю группу целиком, а не каждый кусок отдельно:
- ✓ `am/is/are`, `do/does`, `isn't/aren't`, `don't/doesn't`, `Do/Does`, `-s/-ed`
- ✗ `` `do`/`does` ``, `` `isn't`/`aren't` `` (слэш «голый» между двумя бэктик-вставками — рябит, слэш
  выпадает из подсветки). Слэш — часть выделяемого токена, поэтому он ВНУТРИ бэктиков.

Никакого другого markdown внутри строки (ссылок, вложенных таблиц, заголовков `#`). Структура —
только на уровне блоков.

### ⚠️ КАВЫЧКИ: ЖЁСТКИЙ КАНОН (что и когда ставить) — закреплено 25.06.2026

Раньше английские вставки оформлялись вперемешку (`` ` `` / `«»` / `"`) — бардак. Теперь правило
**по ЯЗЫКУ, а не по длине**. Три знака — три непересекающиеся роли:

| Знак | Роль | Где | Рендер пользователю |
|------|------|-----|---------------------|
| `` `…` `` | английская вставка **которую нужно акцентировать** в потоке русского текста: слово, морфема, формула, фраза, **целое предложение** (`` `to` ``, `` `-ing` ``, `` `to + V1` ``, `` `I want you to stay` ``). НЕ всё английское подряд — см. «Грань бэктиков» ниже | `#### Theory` и `#### Summary`. **НЕ** в Clarification Options и **НЕ** в упражнениях | бэктики срезаются, вставка — цвет `InlineCode` + Medium |
| `«…»` | **русскоязычное цитирование/называние**: имена тем/микротем/разделов (`«Основы»`, `«Модальные глаголы»`), вопрос-форма (`«что делать?»`), русские примеры-фразы (`«хочу спать»`), смысловые глоссы-переводы (`«к, в»`) | везде в прозе | гильеме **видны** как есть |
| `"…"` | **строка-условие упражнения** (то, что конвертер парсит как `questionText`/`wrongSentence`/`construction`/реплики `DialogRestore` и пары `Transformation`) | только блоки `#### Exercises` | кавычки срезает конвертер — **пользователь их НЕ видит** |

Следствия (важно):
- **`«»` — единственные кавычки, которые юзер реально видит.** `` ` `` и `"` — невидимые
  маркеры, просто для разных контекстов (теория vs условие задания).
- **В прозе теории прямые `"` НЕ использовать** — блок теории рендерится «как есть», конвертер
  кавычки там не срезает, и пользователь увидит литеральные `"`. Английское в теории → только `` ` ``.
- **Английское ВНУТРИ условия упражнения** (`"She wants to bought a phone."`) бэктиками **не
  оборачиваем** — оно уже выделено кавычками-условием и структурой задания. Бэктики — инструмент
  теоретической прозы, не упражнений.
- Перевод английской вставки рядом — `*курсивом в скобках*`: `` `to run` `` *(бежать)*.
- **Бэктики — только в `#### Theory` и `#### Summary`.** В Clarification Options и в упражнениях
  бэктики НЕ используем (там лишнее) — английское пишем как есть, без выделения.

**⚠️ Грань бэктиков — против перегруза (должно быть КРАСИВО).** Бэктик — акцент «посмотри именно
сюда», а НЕ разметка «здесь латиница». Если бэктить каждое английское слово — выделение обнуляется,
текст рябит, перегруз. Это явный фидбек пользователя: «если много выделений через `` ` `` — некрасиво
и перегруз».

> 🟡 **ЗОЛОТОЕ ПРАВИЛО (выучить, нарушать = брак). Бэктик — ТОЛЬКО для одного токена/морфемы/
> формулы, сидящего ВНУТРИ строки русского текста. Во всех трёх случаях ниже — `**жирный**`, НЕ бэктик:**
> 1. **любая английская строка в `- ` списке** (специмен + перевод/пояснение): `- **I work in IT.** — …`
>    ✓, `` - `I work in IT.` — … `` ✗;
> 2. **целое предложение-пример** (подлежащее + глагол + …) где угодно — в прозе, Summary, скобках;
> 3. **пара-контраст через стрелку** `✗ → ✓` (`**I read now** ✗ → **I am reading now** ✓`), в т.ч.
>    внутри плашки `**Ловушка:** …` — обе формы жирным.
> 4. **шапка (заголовок) любой таблицы** — в ячейках заголовка НИКОГДА не бэктить (и вообще без
>    инлайн-выделения): пишем `| Подлежащее | Форма be | Пример |`, а не `| … | Форма `be` | … |`.
>    Заголовок таблицы — это подпись столбца, а не объект разбора; выделение там лишнее и рябит.
>
> Бэктик уместен в одном виде: `слово`/`морфема`/`формула` стоит в гуще русской фразы как объект
> разбора («окончание `-s` уцелело», «формула `to + V1`»). Сомневаешься «бэктик или жирный?» — бери
> **жирный**. Эталон оформления — карточки 150–153 в `theory/04-present/01-present-simple.md`.
- **Бэктик уместен**, когда английское слово/короткая вставка сидит ВНУТРИ потока русского текста —
  тогда `word` слегка подсвечивается и заметен. В этом весь смысл выделения.
- ⭐ **Бэктик — это ещё и «заострить внимание» на ключевом английском токене момента.** Не только
  морфема/формула: если в абзаце разбирается конкретное английское слово и читателю нужно на нём
  задержаться — бери бэктик, даже когда слово само по себе простое. Пять рабочих ролей (все —
  живые примеры из `theory/07-past/01-past-simple.md`, эталон этого правила):

  | Роль бэктика | Пример из теории |
  |---|---|
  | Термин/название, которое сейчас объясняем | слово `Simple` здесь значит «простое» |
  | Морфема, окончание | окончание `-ed` подмяло под себя все лица; никакого `-s` |
  | Служебный/грамматический токен (помощник, связка) | `do/does` схлопывается в один `did`; глагол `to be` → `was` и `were` |
  | Лицо-условие, к которому привязано правило | то самое `-s` для `he/she/it` |
  | Одиночное слово-пример, над которым ставим мысленный опыт | уберём `yesterday` — и предложение всё равно останется прошлым; четыре русские формы против одной `remembered` |

  Во всех случаях бэктик работает одинаково — как указатель «вот про ЭТО сейчас речь».
  ⚠️ **ПЕРЕЧИСЛЕНИЕ В СКОБКАХ — ЖИРНЫМ, НЕ РОССЫПЬЮ БЭКТИКОВ** (фидбек 22.07.2026). Как только в
  скобках оказывается **несколько** английских элементов через запятую или цепочка форм через
  стрелку — это уже список, а не указатель на объект, и бэктики по нему рябят:
  - ✗ (`to go`, `to write`, `to meet`, `to buy`) → ✓ (**to go, to write, to meet, to buy**) — одна пара
    звёздочек на всю группу;
  - ✗ (`yesterday`, `last week`) → ✓ (**yesterday**, **last week**);
  - ✗ (`work → worked → worked`) → ✓ (**work → worked → worked**) — цепочка форм всегда жирная;
  - ✗ …удваиваем её (`travelled`) …добавляем k (`panicked`) → ✓ (**travelled**) / (**panicked**) —
    в плашке-сводке это готовые слова-примеры, а не разбираемый токен.
  Бэктик в скобках остаётся уместным для **одиночной формы, которую разбираем прямо здесь**:
  «написание `paniced` язык прочитал бы как «панисед»» — тут форма и есть предмет разговора.
  ⚠️ **ТРАНСКРИПЦИИ — ОБЫЧНЫМ ТЕКСТОМ, БЕЗ бэктиков** (фидбек 22.07.2026): [t], [d], [ɪd], [s], [k]
  пишем голыми, как в теме «Транскрипция» — квадратные скобки уже отделяют звук от текста.
  ⚠️ Пятая роль граничит с правилом «слова-примеры — жирным»: критерий в том, **разбираем** мы это
  слово прямо здесь (бэктик) или просто **приводим в пример / перечисляем** (жирный). `yesterday`
  в опыте «уберём его и посмотрим, что будет» — объект разбора; то же `yesterday` в списке маркеров
  времени — обычный специмен, значит жирный.
  Грань прежняя: подсвечиваем **объект разговора**, а не всякую латиницу вокруг — 2–5 таких
  вставок на карточку читаются отлично, два десятка превращают текст в синюю рябь.
- **НЕ бэктить перечисления и строки вида «англ. предложение — перевод»** (каждый пример на своей
  строке, списком). Если такой примеры-специмены по строкам надо выделить — бери `**жирный**`, либо
  оставляй без выделения. Россыпь `` ` `` по таким спискам = некрасиво.
  ⚠️ **Почему именно тут не бэктим:** в списке элемент УЖЕ визуально отделён маркером-тире, а
  английская вставка в приложении и так красится цветом `InlineCode` — поэтому бэктик в
  списке-перечислении = двойное выделение/перегруз. Канон (закреплён 26.06.2026): английское
  предложение в `- ` списке (в т.ч. формата `- **I work** — перевод`) выделяем **только** `**жирным**`,
  бэктики оставляем для вставок ВНУТРИ потока русского текста.
- Объект разбора (противопоставление форм `goed`✗/`went`✓, формула `to + V1`, ключевая форма ради
  которой написана карточка) → бэктик. Фоновое / повторное / служебное английское → голым.
- ⚠️ **Слова-примеры и пары-трансформации — ЖИРНЫМ, не бэктиком.** Сами слова-образцы
  (`study → studies`, `work → works`, `have → has`, `he works`) — в `**жирный**`. Особенно в СПИСКАХ
  правил и в скобках Summary: россыпь бэктиков по словам-примерам = сплошное синее, бьёт в глаза.
- ⚠️ **Бэктик = только РЕЗУЛЬТАТ/ключевая форма, которую карточка учит получить — не входное
  условие.** В правиле «вход → результат» цветом (бэктиком) выделяем ТОЛЬКО результат, а вход —
  **жирным** (не голым плейном и не бэктиком):
  - «Согласная + y → y меняется на `ies`» — бэктик ТОЛЬКО `ies`; буква-условие `y` НЕ бэктить.
  - «После глухого [p t k f θ] → `[s]`» — бэктик ТОЛЬКО `[s]` (звук-результат); классы-входы
    `[p t k f θ]` / `[s z ʃ tʃ dʒ]` НЕ бэктить (жирным).
  - Слова-подлежащие в начале фразы (Dima, the cat, my brother) — жирным, не цветом: они и так
    на виду в начале, подсвечивать незачем.
  Критерий: «это то, ради чего карточка (что заметить/произвести)?» → бэктик; «фон/условие/
  подлежащее?» → жирный.
- ⚠️ **ЦЕЛЫЕ ПРЕДЛОЖЕНИЯ-примеры (подлежащее + глагол + …) — ЖИРНЫМ, не бэктиком** (фидбек
  пользователя 27.06.2026: «редко когда надо выделять полное предложение через `` ` ``; несколько
  предложений подряд в бэктиках выглядит ужасно — синяя стена»). Бэктик — для отдельного слова/
  морфемы/короткой формулы, куда направляем взгляд; для предложения-специмена (`She always drinks
  coffee`, `He doesn't work here`) — `**жирный**`. Это и в прозе теории, и в Summary, и в скобках —
  не только в списках.
- ⚠️ **Контраст ✗ → ✓ и одиночный «правильный ориентир» — РАЗНОЕ выделение** (тонкость, фидбек
  27.06.2026):
  - **Сломанный и правильный стоят РЯДОМ, парой `✗ → ✓`** (`She drinks coffee always` ✗ →
    `She always drinks coffee` ✓) — оба варианта `**жирным**`. Они уже противопоставлены стрелкой и
    значками, цвет тут лишний — будет двойное выделение.
  - **Правильная форма стоит ОТДЕЛЬНО / в конце** как эталон «а верно — вот так» (когда рядом нет
    парного ✗, либо сломанные примеры идут раньше отдельным куском) — её ОДНУ можно дать `` `бэктиком` ``,
    чтобы притянуть взгляд к образцовой форме: «**He drinks never tea** ✗ и **He drinks tea never** ✗ —
    оба плохо. Наречие к глаголу спереди: `` `He never drinks tea` `` ✓». Сломанные — жирным, финальный
    правильный — цветом-ориентиром.
  - Грамматические указатели-токены, на которые «смотрим глазами» (`` `is/are/am` ``, `` `to be` ``,
    `` `-s` ``, `` `every` ``), остаются бэктиком даже среди жирных предложений — это объект-маркер, а
    не предложение.
- Критерий простой: **смотри, чтобы было красиво и выделение что-то значило.** Перегруз бэктиками —
  это запах, переписать.
- ⭐ **ЭТАЛОН бэктик/жирный — карточки 150–153 (Microtopic 50) в `theory/04-present/01-present-simple.md`.**
  Утверждено пользователем 26.06.2026 как образец баланса: заголовки без выделения; результат
  (`-ies`, `[s]`) — бэктик; вход-условие (`y`, `[p t k f θ]`), слова-примеры и транскрипции,
  подлежащие в начале — жирным. Сверяться с ними при оформлении новой теории.

### ⚠️ ТРАНСКРИПЦИЯ — ТОЛЬКО В ДВОЙНЫХ СКОБКАХ `[[…]]` (канон, 22.07.2026)

Любая транскрипция внутри текста пишется в **двойных** квадратных скобках: `[[wɜːk]]`, `[[ɪd]]`,
`[[t]]`. Пользователю показываются **одинарные** — `[wɜːk]`: внешние скобки авторский маркер,
UI их срезает, а саму транскрипцию рисует **серифным шрифтом на 10% крупнее** окружающего текста
(`parseInlineMarkdown` → `PHONETIC_SCALE`), чтобы мелкие значки IPA не сливались со строкой.

**Почему не одинарные.** Одинарные `[…]` в курсе заняты: пропуски в заданиях (`[___]`), слоты-шаблоны
(`[предмет]`, `[A] is … than [B]`), кальки-приманки в промтах (`тянет [on]`). Отличить их от
транскрипции по содержимому НЕВОЗМОЖНО: `[red]` — это и «красный» как слот, и запись чтения `read`;
`[on]`, `[for]`, `[men]`, `[wen]` выглядят одинаково в обеих ролях. Поэтому решает не догадка кода,
а явный маркер автора.

**Где действует — ВЕЗДЕ, где текст видит пользователь:** `#### Theory`, `#### Summary`,
`#### Examples`, условия и `*Explanation:*` упражнений, `#### Clarification Options`. Правило единое
для всего приложения, а не только для теории.

**Где НЕ ставим:**
- **колонка «Транскрипция» в `### Words8r Sync`** — это структурное поле (своя колонка в БД,
  контекст известен коду), маркер там был бы мусором в данных;
- **`**Prompt Template:**` и `Пример вывода AI:`** — этот текст уходит на сервер, пользователю не
  рендерится, поэтому маркер там не обязателен. Требование к самому AI («транскрипцию оформляй
  `[[…]]`») живёт в блоке «Роль» базового промта — `phases/phase3/ai_base_prompt.md`, в каждое
  задание его копировать не нужно.
  ⚠️ **НО:** если транскрипция стоит в промте как ОБРАЗЕЦ для ответа модели («объясни: an old
  `[[æn]]`, a university `[[ə]]`»), пишем её сразу двойными — модель копирует формат из примера
  перед глазами, и одинарные скобки в промте вернутся одинарными в ответе пользователю.

**Что разрешено внутри `[[…]]`:** символы IPA (`ˈ ˌ ː ə ɪ ʊ æ ʌ ɜ ɑ ɒ ɔ θ ð ʃ ʒ ŋ` …), латиница,
пробел, точка, дефис — и одиночная кириллическая `[[г]]` (нужна в «Транскрипции»: «`[[ŋ]]` звучит
без `[[г]]` на конце»). Русские слова и слоты-шаблоны внутри двойных скобок запрещены —
`smell.py` ловит это как ошибку.

**Слоты-шаблоны пишем БЕЗ скобок:** `Формула: X + as well as + Y` ✓, а не `[элемент A]` ✗ — иначе
пользователь видит слот, оформленный как транскрипция.

⚠️ `smell.py` проверяет обе стороны: (1) внутри `[[…]]` только разрешённые символы; (2) «голая»
`[…]`, похожая на транскрипцию (одиночная буква-звук или наличие IPA-знаков), — забытый маркер.

**`**…**` в текстах УПРАЖНЕНИЙ — выделение жирным (канон, июнь 2026).** Нужно подсветить
слово в условии задания (например, в Matching «определи часть речи слова **run** в предложении»,
в Transformation «замени **Vera** на местоимение») — берём его в `**…**`. Выделять можно
**не только целое слово, но и часть слова / одну букву**: `rec**o**rd` (показать ударную
гласную), `walk**ed**` (подсветить окончание) — UI делает жирным ровно то, что внутри маркеров,
хоть одну букву. Конвертер пропускает маркер в данные как есть; **UI-слой ОБЯЗАН рендерить
`**…**` как Bold** (одна общая утилита `**` → `AnnotatedString` в `ui/components/`, для всех
типов упражнений) — показывать звёздочки текстом пользователю нельзя. `smell.py` парные `**…**`
не считает запахом, НЕПАРНЫЕ звёздочки — ловит как утечку.
⚠️ Исключение: в `Правильное предложение: **…**` (WordArrangement) и `→ **"…"**` (Transformation)
жирный — это СЛУЖЕБНЫЙ маркер ответа, конвертер его съедает сам; к выделению в UI отношения
не имеет, правило на эти места не распространяется.

Заголовок упражнения — строго `**Ex N · ТочноеИмяТипа** *(ID: N)*` (имена типов — раздел 4).

### AI Exercise — конвертер делит блок на ДВА выхода ⚠️

Промт — секрет, в APK его быть не должно. Поэтому из `#### AI Exercise` конвертер пишет два места:

| Поле в MD | Куда |
|-----------|------|
| `ID`, `Title`, `Input Mode`, `Words Source`, `User Instruction` (+ `cardId` от карточки) | **client seed** → content.db `ai_exercises` |
| `Prompt Template`, `AI Config Profile` | **server seed** (`prompts_seed.json`) → серверная `ai_exercise_prompts`, в APK НЕ идёт |

Связь — по `id` (`basics_card1_ex1`): клиент шлёт серверу только id, сервер по нему берёт промт+профиль.
В MD по-прежнему пишем ВСЕ поля рядом (удобно ревьюить) — разделяет их конвертер, не автор.

> ⚠️ **`Пример вывода AI` живёт СНАРУЖИ кавычек `Prompt Template`, но не теряется** — конвертер
> сам вылавливает эту строку и вплетает её в финальный `promptTemplate` server seed вместе с
> обвязкой «это образец структуры, не копируй дословно» (+ канон `[___]` для `FILL_BLANKS`).
> Подробности и зачем такой формат — раздел 5 → «Критичные правила». Главное для автора: писать
> СНАРУЖИ кавычек как в эталоне — остальное (сборка финального промта, обвязка, валидация
> отсутствия) берёт на себя конвертер.

### Words8r Sync → `course_words` (конвертер сидирует слова автоматически)

Конвертер тянет слова не только в теорию, но и в **БД-заготовку слов** — из таблиц
`### Words8r Sync · …`. Искать слова вручную потом не нужно.

**Откуда категория/группа.** Объявляются **в шапке theory-файла** (один раз на тему):

```
**ID:** 1 | **Order:** 1 | **isPretopic:** true
**Группа слов:** basics · Основы
**Категория слов:** grammar_basics · Grammar Basics · source=course_words
```

**Категория задаётся НА ТЕМУ** (одна на весь файл). Для предтемы «Основы» это `grammar_basics`:
все слова всех 15 микротем `01-basics.md` идут в `grammar_basics` — по микротемам ничего
указывать не нужно. В других темах будет своя категория (Present Simple → basic_verbs и т.д.).

> ⛔ **Слив ОДНОЙ микротемы НЕ делится между двумя категориями** (фидбек 26.08.2026). Нельзя
> «служебные слова темы — в `linking`, а прилагательные из тех же примеров — в `descriptions`»:
> это разваливает Словарь и путает пользователя. Одна микротема = одна категория. Если слово по
> смыслу в категорию темы не лезет (бытовая лексика в служебной теме вроде «So/Such и Too/Enough»)
> — его не сливают здесь вовсе: либо тема сливает МЕНЬШЕ слов (даже одно, и это нормально), либо
> слово придерживается до подходящей темы, где оно ляжет в родную категорию. Примеры при этом
> строятся из уже накопленного словаря (§3), а не из свежесливаемых слов.
>
> ⚠️ Редкий случай: если в будущей теме ОДНА микротема должна открывать слова в ДРУГУЮ
> категорию (тема с несколькими категориями, напр. Времена → Basic Verbs + Verb Forms) —
> переопределить точечно в заголовке секции. Это исключение, не правило:
> ```
> ### Words8r Sync · Неправильные глаголы [category: verb_forms]
> ```

**Что парсит конвертер из таблицы** `| Слово | Переводы | Транскрипция |`:
- `word` ← Слово, `translation` ← Переводы, `transcription` ← Транскрипция;
- `microtopicId` ← id текущей микротемы (ключ открытия);
- `categoryId` ← категория секции/темы; `id` ← присваивается **детерминированно и стабильно**
  (чтобы не осиротел прогресс в user.db при пересборке content.db).

Правила содержания Words8r Sync (что включать/не включать) — раздел 6.

## 9. Самопроверка формата после написания (обязательный шаг)

### 🔄 Рабочий цикл написания темы (КАНОН)

1. **Пишем 1–3 микротемы** по эталонам (раздел 8 + `exercise_templates.md`: эталоны и «❌ Антипаттерны»).
2. **Claude отдельным проходом проверяет СВОЁ оформление** по чеклисту ниже (до показа пользователю).
3. **Пользователь делает ревью** содержания.
4. **Правки** вносятся вместе с пользователем.
5. **⚠️ ТОЛЬКО после явного одобрения и явной команды пользователя** — прогон `py check.py <файл>`.
   **Claude НЕ запускает тесты сам** (ни после написания, ни после правок) — ждёт явной команды.
6. `ALL GREEN` → коммит / следующие микротемы.
7. **⚠️ Отметить ✅ в `grammar8r_plan.md`** — у написанной микротемы дописать пометку СТРОГО в виде
   `✅ (написана, ALL GREEN <дата>)` и больше НИЧЕГО. Дата — формат `ДД.ММ.ГГ` (напр. `09.07.26`).
   ⚠️ **Пометка ставится в ТУ ЖЕ строку, где стоит номер и название микротемы** — не переносить её
   на отдельную строку ниже (фидбек 18.08.2026: так пользователю с одного взгляда видно, что
   написано, а что нет). Эталон строки:
   `├── МТ139 · Been vs Gone · Был и вернулся ↔ уехал (2 карточки) ✅ (написана, ALL GREEN 18.08.26)`
   ⚠️ **Ради нескольких символов строку НЕ дробить** (фидбек 21.08.2026). Заголовок микротемы,
   `(N карточек)`, хвост-описание («концепт-интро, БЕЗ упражнений и AI», «структура как MT56») и
   `✅ (написана, …)` живут ОДНОЙ строкой — пусть она вылезет за 120 символов, это план, а не код.
   Ронять вниз короткий хвост ради ширины — нельзя, читать мешает больше, чем длинная строка.
   Общая же вёрстка планов остаётся прежней: длинные многострочные описания под узлом дерева
   переносятся как и раньше — правило только против дробления ради «письки» в пару слов.
   Стрелка-акцент («← сердце темы») идёт ПОСЛЕ пометки, в той же строке.
   ⚠️ **Номера в самой ✅-пометке НЕ пишем** — ни `MT id`, ни диапазон `cards N–M`, ни счётчики
   AI/слитых слов. Все номера живут на ЗАГОЛОВКАХ: реальный ID микротемы стоит у неё (`МТ69 · …`),
   реальные ID карточек — у каждой карточки (`Card 202 · …`). Дублировать их в пометке не нужно.
   **⚠️ Поэтому при написании проставить РЕАЛЬНЫЕ номера в дереве плана:** плейсхолдеры `МТ · …` и
   `Card 1/2/3…` (сквозные-по-теме, не настоящие ID) заменить на фактические из `_id-registry.md`
   (`МТ69 · …`, `Card 202 · …`). У ещё НЕ написанных микротем плейсхолдеры оставляем (ID — при написании).
   Если это была ПОСЛЕДНЯЯ микротема темы — отметить `✅ ТЕМА НАПИСАНА` и у самой темы (как у
   «Транскрипция»). Делать сразу после ALL GREEN, не откладывая — иначе план разъезжается с прогрессом.

> Разделение «пишу → ревью → правки → (по команде) тесты» резко снижает ошибки и не гоняет
> скрипты вхолостую. Тесты — финальный шаг, и только по слову пользователя.

Что проверять на шаге 3 (по каждой новой карточке):
- [ ] 🚨 **ПОЛНОТА, а не формат — первым делом** (§3 → «ПОЛНЫЙ НАБОР ФОРМ» + «ЧЕМ ЗАПОЛНЯЕТСЯ СЛОТ»).
      Два прогона, оба обязательны: **формы** конструкции (утверждение · отрицание · вопрос ·
      отрицательный вопрос · сокращения) и **инвентарь слота** (обычный глагол · `to be` · модальный
      `can`→`could` · `have to` · безличное `there`), плюс **оба направления переворота**, если
      конструкция сообщает обратное факту. Финальная проверка — взять пять предложений из
      пройденного курса, где пользователь применит приём, и убедиться, что формулировка карточки
      срабатывает на каждом. Дыра здесь стоит дороже любой ошибки оформления: формат ловят скрипты,
      а недосказанное правило не ловит никто, кроме пользователя (реальный провал — `I wish I could`
      в Card 503)
- [ ] **Нет «стены»:** в `#### Theory` нет 5+ абзацев прозы подряд без разрыва — длинные куски
      разбиты подзаголовком (`heading` = вся строка в болде, даёт авто-линию). Голый `---` внутри
      `#### Theory` не используем (раздел 8)
- [ ] 🚨 **Ни одной формулы в прозе:** каждая схема сборки (элементы через `+`, порядок слов
      в конструкции) стоит в плашке `**Формула:**`, а пояснение — отдельным блоком ПОД ней
      (§8 → «ФОРМУЛА/СБОРКА»). Проверять поиском по `+` внутри абзацев теории
- [ ] Каждая ловушка — `**Ловушка:** тело` (тело снаружи болда), а не целиком в `**…**`
- [ ] Подзаголовки секций — строка целиком в болде; после `**` ничего нет
- [ ] 🚨 **Ни один ПРИМЕР не стоит отдельной строкой целиком в болде** (§8 → «ПРЕДЛОЖЕНИЕ-ПРИМЕР»).
      Грепнуть `^\*\*[A-Za-z].*\*\*$`: английская фраза одна на строке в болде превратится в
      подзаголовок с линией, и рядом с настоящим подзаголовком выйдут два заголовка подряд. Чаще
      всего вылезает сразу под плашкой `**Формула:**` — вплести пример в абзац или дать списком
- [ ] 🚨 **НИ В ОДНОМ ПОДЗАГОЛОВКЕ НЕТ КЛЮЧЕВОГО СЛОВА ПЛАШКИ** (ловится глазами плохо, поэтому
      проверять списком — фидбек 05.09.2026, реальный брак: `**Возможность и совет: формулы с can,
      might, should**` — «совет» и «формул» превратили подзаголовок в пустую рамку-плашку).
      Полный список корней, которые ловит `md_to_json.py::variant_for` (регистр не важен, ищется
      ПОДСТРОКА в любом месте ярлыка): `ловушк` · `не путай` · `важно` · `осторожно` · `кстати` ·
      `запомни` · `секрет` · `совет` · `лайфхак` · `формул` · `примечани` · `заметк`.
      Как проверять: прогнать глазами (или грепом) все строки вида `**…**` целиком в болде и
      убедиться, что ни одна не содержит этих корней. Нашёл — переформулировать подзаголовок
      синонимом без ключа (`совет` → `рекомендация`, `формулы с can` → `конструкции с can`,
      `важно` → `главное`), а НЕ оставлять как есть.
      ⚙️ **Это ловит `smell.py` автоматически** (`[рамка-обманка: подзаголовок с ключевым словом
      плашки]`): в сиде такой брак опознаётся однозначно — callout, у которого тело РОВНО один
      абзац, целиком обёрнутый в `**…**`. Если запах вылез, а плашка задумана: перенеси двоеточие
      в КОНЕЦ ярлыка (`**Ловушка 1: пропустить to**` → `**Ловушка 1 — пропустить to:**`) — тогда
      конвертер впитает следующий блок (абзац/список/таблицу) ВНУТРЬ рамки, и она перестанет быть
      пустой. Если это был подзаголовок — переформулируй без ключевого слова.
      `variant: formula` из проверки исключён: там жирная схема в теле и есть содержимое плашки.
      ⚠️ Коварство в том, что слово может быть где угодно внутри заголовка и в любой форме:
      `**Четыре формулы на каждый день**`, `**Почему это важнейшая ловушка русского**`,
