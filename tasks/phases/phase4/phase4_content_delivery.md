## TL;DR

Контент (дерево тем/микротем + карточки + упражнения) раздаётся **как статические JSON-файлы
из объектного хранилища** (Object Storage, S3-совместимое), а не из «сервера с эндпоинтами».
ID микротемы — это просто имя файла (`microtopic/{id}.json`). Сервера с кодом и БД для контента
**не нужно**. Хранилище — в РФ (ниже риск блокировки, латентность, изоляция). AI/auth/платежи
остаются на отдельном зарубежном узле. Стоит копейки (единицы рублей/мес на старте).

---

## Зачем отделять раздачу контента от «рабочего» сервера

Раздача контента и боевой API (auth, платежи, AI-прокси) — **разные по природе** нагрузки.
Их разносят по разным узлам по конкретным причинам:

1. **Разный характер нагрузки.** Контент — почти статика: read-only, одинаков для всех,
   идеально кэшируется. API — stateful-компьют: запись в БД, секреты, вызовы DeepSeek/YooKassa.
   На одном узле трафик скачиваний конкурирует за ресурсы с платежами.
2. **Кэшируемость / CDN.** Статику можно раздавать через edge-кэш дёшево и быстро; динамический
   API так не кэшируется.
3. **Независимое масштабирование.** Выкатил новую тему → все разом качают. Этот пик не должен
   класть auth и оплату.
4. **Изоляция отказов.** Контент-узел лёг → AI/оплата живы, и наоборот.
5. **Поверхность атаки.** Контент-хранилище **не держит ни одного секрета** (ни ключа DeepSeek,
   ни `JWT_SECRET`, ни данных YooKassa, ни персональных данных). Тупой read-only раздатчик —
   ломать нечего. Все секреты — только на боевом сервере.
6. **Разный темп деплоя.** Контент бампается часто, API — редко. Разные жизненные циклы.

## Архитектура: Object Storage, не «CDN с эндпоинтами»

Важно не путать два кирпича:

- **Object Storage** (объектное хранилище, S3-совместимое) — «папка файлов в облаке», каждый файл
  доступен по своему HTTPS-URL. Никакого кода, БД, Spring. Просто файлы. **Это основа.**
- **CDN** — это **кэш поверх origin** (поверх Object Storage). Сам ничего не хранит и эндпоинтов
  не имеет — раздаёт с ближайшей к юзеру точки то, что лежит в хранилище. **Опционален**, добавляется
  сверху для скорости/экономии трафика на объёме.

«Эндпоинты» контента — это **обычные файлы-URL**, без серверной логики:

```
version.json            → { "version": 42 }
tree.json               → дерево: категории → темы → микротемы (id, заголовки, порядок, флаги)
                          + ПОИСКОВЫЙ ИНДЕКС: теги микротем и названия карточек (см. ниже). БЕЗ тела карточек.
microtopic/101.json     → карточки + упражнения микротемы 101
microtopic/102.json     → карточки + упражнения микротемы 102
...
```

`microtopic/{id}.json` — это и есть «по ID пришли карточки»: ID прямо в пути файла.

## Поток на клиенте

```
GET https://content.grammar8r.ru/version.json        ← раз в день при первом запуске: сверить версию
GET https://content.grammar8r.ru/tree.json           ← тянется при смене версии
GET https://content.grammar8r.ru/microtopic/{id}.json ← лениво при входе в микротему, кэш с TTL
```

1. Раз в день при старте — `GET version.json`, сверить с локальной версией.
2. Версия совпала → ничего не делаем.
3. Не совпала → подтянуть **лёгкое дерево** (`tree.json`) и только ПОСЛЕ успешной загрузки
   атомарно заменить им старое + инвалидировать кэш микротем (никогда не `user.db`!).
   Карточки — **не качать разом**.
4. Карточки микротемы (`microtopic/{id}.json`) — **лениво при входе** в микротему, кэшируются с TTL.

### ⚠️ Порядок замены кэша: «скачать → заменить», НЕ «снести → качать»

Речь о порядке операций для КАЖДОГО ОТДЕЛЬНОГО файла (дерево при смене версии; одна микротема
при входе в неё) — ленивая пофайловая загрузка из потока выше остаётся как есть, весь курс разом
НЕ качается. Правило: **новый файл докачали до конца → старую копию атомарно заменили**.
Сносить старую копию ДО успешной загрузки новой — запрещено. Почему именно так:

- **Сеть может отвалиться между «снёс» и «скачал»** (метро, лифт, кончился трафик, лёг бакет).
  При порядке «снести → качать» пользователь в этот момент остаётся с ПУСТОЙ теорией — приложение
  сломано до появления сети, хотя секунду назад всё работало. При порядке «скачать → заменить»
  худший исход любого сбоя — юзер ещё день видит старую версию контента. Старый контент — это
  штатное состояние (он у всех был вчера); пустой контент — сломанное приложение.
- **Обновление перестаёт быть критической операцией.** Любая ошибка (битый JSON, недокачка,
  таймаут) просто оставляет всё как было — не нужны код восстановления и «полу-обновлённые»
  состояния.
- Тот же принцип на уровне файлов: не перезаписывать рабочий кэш по кускам, а собрать новое
  рядом и переключиться одним действием (запись во временный файл/таблицу → атомарная подмена).
  Классический паттерн атомарной публикации.

> **Две жёсткие оговорки (из S23, остаются в силе):**
> - **`user.db` (прогресс) при сбросе НЕ трогаем никогда.** Сбрасывается только кэш контента.
> - **Не качать весь курс разом** — один глобальный номер версии + ленивая дозагрузка карточек.

**Почему переезд дешёвый:** у всех сущностей контента — разные **стабильные ID** (ведём в
`_id-registry.md`), прогресс (`user.db`) ссылается на них. Пока ID стабильны — контент можно
перенести/обновлять, не трогая прогресс: он сматчится по тем же ID.

## ⚠️ tree.json несёт ещё и ПОИСКОВЫЙ ИНДЕКС (решение 25.07.2026)

Поиск по теории (ТЗ — [`search_feature_brief.md`](../../search_feature_brief.md)) обязан находить
микротемы, которые пользователь **ещё ни разу не открывал**. Иначе результаты зависят от того, что
уже скачано: сегодня находит, завтра нет — поиск неконсистентен.

Отсюда жёсткое требование к формату: **весь поисковый индекс живёт в `tree.json`**, а не в
`microtopic/{id}.json`. В дерево кладутся:

- заголовки категорий / тем / микротем (уже есть);
- **теги микротем** (`searchKeywords`) — новое поле;
- **названия карточек** (`id`, `microtopicId`, `title`) — раньше карточек в дереве не было вообще.

Тело теории и упражнения остаются в лениво качаемых `microtopic/{id}.json` — поиск в них не лезет
(полнотекстовый поиск по телу теории отвергнут отдельно, см. бриф: с ленивой загрузкой он
несовместим принципиально).

Цена вопроса ничтожна: к релизу ~150 микротем и ~500 карточек → дерево порядка 60–80 КБ,
под gzip ~20 КБ, качается раз в смену версии.

## Холодный старт: APK без контента (решение 25.07.2026)

> ⚠️ **ОТМЕНЕНО прежнее решение** «забандлить в APK минимальный сид (`tree.json` + предтема
> «Основы»)». Причина смены: интернет на первом запуске есть практически у всех, а бандл сида
> означает вторую копию контента, которая живёт своей жизнью и протухает между релизами.

**APK поставляется пустым — без теории вообще.** Контент подсасывается сам:

1. Первый запуск → приложение тянет `version.json`, затем `tree.json` целиком. До этого момента
   показывается состояние загрузки, а не пустое дерево.
2. Дальше версия сверяется **при заходе в карточку/микротему**: клиент спрашивает версию, и если
   она разошлась с локальной — тянет свежее `tree.json` и инвалидирует кэш микротем (порядок —
   строго «скачать → атомарно заменить», см. блок выше).
3. Тело микротемы (`microtopic/{id}.json`) — как и раньше, лениво при входе, с кэшем и TTL.

Что учесть при реализации (не меняет решение, снимает его минусы):

- **Сверка версии на каждом заходе — троттлить.** `version.json` крошечный, но дёргать его на
  каждый тап незачем: сверять не чаще раза в N минут, с `ETag`/`If-None-Match`, чтобы в норме
  прилетал `304` без тела.
- **Нет сети на первом запуске** — единственный сценарий, где приложение бесполезно. Нужен
  честный экран «нужен интернет, чтобы загрузить курс» с кнопкой повтора, а не пустое дерево и
  не краш.
- **Нет сети позже** — не проблема: скачанное дерево и открытые микротемы лежат в кэше, работа
  продолжается на старом контенте.

Остальной контракт (стабильные ID, глобальная версия, ленивая дозагрузка) — без изменений.

## Сборка и заливка

У проекта уже есть конвейер **MD → JSON → `content.db`** (скрипты в `tasks/tools/`). Добавляется
один шаг: генерировать те же данные как **раздельные JSON-файлы** (`version` / `tree` /
`microtopic/{id}`) и **заливать в бакет** (S3-совместимый CLI: `aws s3 cp` или `yc storage`).

Цикл обновления:
1. Поправил контент в MD → пересобрал JSON.
2. Залил изменённые `microtopic/{id}.json` (+ `tree.json`, если поменялась структура).
3. Бампнул `version.json`.
4. Приложения при следующей ежедневной сверке увидят новую версию и подтянут изменения.

**Релиз приложения не нужен** — ровно как уже сделано для AI-промтов.

## Контроль доступа

Контент **бесплатный**. Различие тиров — в **лимитах**, не в доступе к контенту (см.
[subscription.md](../../subscription.md)). Поэтому файлы в бакете **публичные**, и прятать их не нужно.

Два гейта — оба **НЕ на уровне файлов**:

1. **Регистрация** (без аккаунта доступна только предтема «Основы»). Это **клиентский UI-гейт**:
   приложение просто не пускает незарегистрированного дальше Основ. Файлы при этом физически
   доступны по URL — но это бесплатный учебный контент, не платный, и абсолютная защита от
   скачивания не цель (бандленный SQLite и так распаковывается тривиально).

2. **Дневной лимит микротем** (free = 3/день). Это **серверный гейт** через уже существующий
   `POST /limits/microtopic` (см. [phase4_server.md](phase4_server.md)). Логика: **качать файл
   пусть качает** — но при входе в микротему клиент спрашивает сервер, и если лимит исчерпан,
   сервер отвечает «3 микротемы за сегодня пройдено» → приходи завтра (сброс в 00:00 МСК).
   То есть пейс рулит лимит на сервере, а не закрытость файлов.

> **Если когда-нибудь понадобится жёстко закрыть контент на уровне сети** (не наш случай, контент
> бесплатный) — это делается через **pre-signed URL**: загран auth-сервер (он и так аутентифицирует
> юзера) выдаёт короткоживущую подписанную ссылку на файл. На MVP не нужно, фиксируем как опцию.

## Стоимость (Yandex Cloud, ориентир — проверить в калькуляторе)

> Цены приблизительные (прайс Яндекса рендерится скриптом, числа по памяти). С 1 мая 2026 тарифы
> Yandex Cloud менялись — **сверить актуальные в калькуляторе/прайс-листе перед запуском.**

Ключевой факт: **контент — это текст, его микроскопически мало.**

**Объём данных:**
- `tree.json` ~ 100–200 КБ; каждая `microtopic/{id}.json` ~ 30–50 КБ.
- Весь курс (пара сотен микротем) ≈ **10–30 МБ в бакете суммарно**.

**Тарифные статьи (≈, ₽):**
- Хранение (Standard): ~₽1.5–2 / ГБ / мес → у нас 0.02 ГБ → **доли копейки**.
- Операции GET: порядка копеек за 1000 запросов.
- Исходящий трафик (egress): ~₽1–1.5 / ГБ — **главная статья** (через CDN на объёме дешевле).

**Расход на активного free-юзера:** ~3 микротемы/день минус кэш с TTL (повторные открытия — с диска)
→ ~**3–5 МБ/мес** + копеечные version-проверки.

| Активных юзеров | Egress/мес | Стоимость/мес |
|---|---|---|
| 100 | ~0.5 ГБ | **~₽1** |
| 1 000 | ~5 ГБ | **~₽6–8** |
| 10 000 | ~50 ГБ | **~₽60–80** |

На старте — **единицы рублей**, дешевле VPS за 500₽, и **ничего не администрируешь** (нет ОС,
патчей, падений бокса). Хранилище и операции — фоновые копейки.

## Рекомендации по реализации

1. **Брать Object Storage, не поднимать VPS** ради раздачи статики.
2. **CDN на старте можно не подключать** — Object Storage сам отдаёт по HTTPS (есть режим хостинга
   статического сайта + свой домен, напр. `content.grammar8r.ru`). CDN добавить сверху позже, если
   нужна скорость в РФ-регионах или вырос трафик. Меньше сущностей сейчас.
3. **Object Storage надёжнее одиночного дешёвого VPS** для теперь-критичной (контент не забандлен
   целиком) раздачи: переживает пики выкатки, не требует обслуживания.
4. **APK без контента** (решение 25.07.2026): курс подсасывается при первом запуске, сид в APK НЕ
   бандлится. Обязательное следствие — честный экран «нужен интернет» на первом запуске без сети.
5. **`user.db` при любых сбросах кэша не трогать.** Безопасность переезда держится на стабильных ID.
6. **Замена кэша — только «скачать → заменить»** (см. блок «Порядок замены кэша» выше): сбой сети
   на обновлении оставляет старый контент, а не пустое приложение.

## Эндпоинты (это просто файлы-URL)

```
GET /version.json            → { version: <int|hash> }     # ежедневная сверка
GET /tree.json               → дерево + поисковый индекс     # при смене версии
GET /microtopic/{id}.json    → карточки + упражнения        # лениво при входе, кэш с TTL
```

Никакой серверной логики — это статические объекты в бакете. ID в пути = «эндпоинт по ID».
