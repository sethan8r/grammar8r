## 1. Словарный запрос — через сервер или напрямую из приложения

**Исходное опасение пользователя:** фичей будут пользоваться часто, прогон всего через свой
сервер = лишняя нагрузка; может, приложение должно ходить в словарные API само.

**Позиция Claude — через сервер, и нагрузка тут аргумент «за», а не «против»:**

- **Квоты у провайдеров выданы на КЛЮЧ, а не на пользователя.** LingvoLive — 50 000 символов/день
  (≈10 000 коротких слов) на весь ключ. Yandex Dictionary — 1 000 запросов/день на весь ключ.
  Ключ, зашитый в APK, остаётся одним на всех: при 1 000 пользователей это ~10 слов в день на
  человека по Lingvo и одно по Яндексу. Прямые вызовы квоту не увеличивают — только лишают
  контроля над ней. Плюс любой, кто вытащит ключ из APK, выжигает дневной лимит всем остальным.
- **Общий серверный кэш переворачивает арифметику.** Слово значит одно и то же для всех
  пользователей. Сервер кэширует каждый ответ апстрима → лексика курса закэширована после первых
  сотен пользователей → обращения наружу стремятся к нулю. При прямых вызовах каждое устройство
  переоткрывает те же слова заново, то есть апстрим-нагрузка умножается на число пользователей.
- **Смена провайдера без релиза.** LingvoLive в статусе Beta. За сервером замена провайдера —
  правка на сервере (как с промтами), при прямых вызовах — релиз APK и ожидание обновления у всех.

**Нагрузка на наш сервер — самый дешёвый эндпоинт из всех планируемых:** принять ~200 байт,
индексный SELECT, вернуть ~500 байт. Ни LLM, ни транзакций. Для сравнения `POST /ai/exercise`
держит соединение 2–10 с в ожидании модели. Прикидка: 1 000 DAU × 30 зажатий = 30k запросов/день
= ~0.35 rps в среднем.

**Статус:** открыт.

## 2. Локальный словарь как первый слой (идея пользователя, Claude согласен)

**Предложение пользователя:** сначала искать слово в нашем шиппованном словаре и показывать все
найденные значения, схлопывая дубли; если перевод не устроил — отдельная кнопка, по которой
запрос уходит уже на сервер за полноценным словарным ответом.

**Оценка Claude — это лучше автоматического фолбэка, который он предлагал изначально:** запрос в
сеть становится **ручным**, то есть наружу уходят только слова, где локальный ответ реально не
подошёл. Фоновый трафик исчезает как класс, квотная проблема почти испаряется.

**Замеры по живому `tasks/words8r.db` (21.09.2026):**

```
17 170 строк  →  10 051 уникальное английское слово
17 150 строк с транскрипцией (то есть почти всё)
 9 098 строк, где перевод уже составной (несколько значений через запятую)

 4 274 слова лежат более чем одной строкой:
   3 997 из них — перевод ОДИН И ТОТ ЖЕ (чистый шум от раскладки по категориям)
     277 — переводы РАЗНЫЕ, и вот ради них мерж и нужен
```

Примеры расхождений, которые мерж показывает пользователю целиком:

```
about   → «о, об, обо»            + «примерно, приблизительно, около, почти»
acid    → «кислота»               + «кислотный, кислый»
affair  → «дело, событие»         + «роман, любовная история»
account → «аккаунт, счёт»         + «отчёт, доклад, мнение»   (9 строк, 2 смысла)
```

**Дедуп схлопывает не строки целиком, а отдельные переводы.** Иначе `adult` («взрослый (человек)»
и «взрослый, для взрослых») даст пользователю «взрослый» дважды. Алгоритм: собрать все `russian`
по слову → разбить по запятой → `trim` → дедуп с сохранением порядка. Транскрипция — первая
непустая (у дублей она совпадает).

**Две известные дыры локального слоя:**
- Глаголы лежат как `to allege`, фразы целиком (`to give someone a lift`) — при поиске нормализовать
  ключ (срезать `to `).
- Словоформы (`went`, `running`, `cats`) точным матчем не найдутся. `irregular_verbs` в `content.db`
  закрывает неправильные глаголы (`went → go`), остальное — срезание окончаний. Что не нашлось,
  уходит на кнопку «запросить перевод».

**Статус:** направление принято обоими, детали не проговаривались.

## 3. Слои перевода — как это выглядело бы целиком

```
зажал слово
 ├ L0  content.db: словарь 17k (+ irregular_verbs для форм)  ← офлайн, бесплатно, мгновенно
 ├ L1  user.db: DictionaryCache                               ← уже в db_schema.md
 ├ L2  кнопка «запросить перевод» → наш сервер, общий кэш     ← обсуждалось здесь
 └ L3  сервер наружу: LingvoLive → Yandex → «перевод недоступен»
```

Фолбэк между провайдерами целиком уезжает на сервер: клиент получает нормализованный DTO из
`grammar-shared` и не знает, кто ответил. `DictionaryRepository` в `grammar-core` (уже
запланирован) прячет за собой все четыре слоя, UI видит один вызов.

**Следствие для схемы, если так и сделаем:** поля `provider` и `responseJson` в `DictionaryCache`
(`db_schema.md`) на клиенте становятся лишними — сырой ответ клиент больше не видит,
`responseJson` место на сервере.

**Статус:** открыт.

## 4. TTL на серверном кэше — единственное, где Claude спорил с пользователем

**Позиция пользователя:** кэшировать на сервере с TTL в несколько дней, «так правильнее».

**Возражение Claude:** словарные статьи не протухают — `cat` будет «кошкой» и в 2030-м. А
накопленный кэш и есть главный актив всей конструкции: он копится месяцами и сводит обращения
наружу почти к нулю. TTL в три дня означает, что каждые три дня заново выжигается квота
1 000 запросов/день на слова, которые уже известны.

Реальная причина захотеть обновить запись — не протухание, а **изменение нашей логики парсинга**
ответа провайдера. Это решается полем `parser_version` рядом с `fetched_at`, а не будильником:
поменял парсер → записи со старой версией перезапрашиваются лениво.

**Где TTL всё-таки обязателен — юридически.** У Яндекс-словаря в условиях использования есть
требования по атрибуции, и в подобных API встречается пункт про предельный срок хранения
результатов. Точную текущую редакцию Claude не знает и не утверждает. **Читать ToS обоих
провайдеров до того, как строить вечный кэш.** Есть потолок — ставим ровно требуемый срок, это
не техническая настройка, а обязательство. Потолка нет — храним бессрочно, `fetched_at` оставляем
под ручную чистку.

**Статус:** разногласие, не разрешено. Упирается в ToS — проверить первым делом.

## 5. Redis — Claude против, пользователь спрашивал

**Вопрос пользователя:** не поставить ли Redis рядом — в Postgres переводы с TTL в несколько дней,
в Redis те же данные на 5 часов; будет ли легче по нагрузке.

**Позиция Claude — не ставить:**

- Таблица кэша даже на 100 000 слов ≈ 100 МБ, целиком ложится в `shared_buffers`. Точечный SELECT
  по первичному ключу из прогретого кэша — 0.1–0.3 мс. Redis `GET` — 0.05 мс. Выигрыш 0.2 мс при
  сетевом round-trip телефон↔сервер 20–60 мс, то есть ~0.4% времени ответа.
- Postgres на 4 ядрах делает такие селекты десятками тысяч в секунду при ожидаемом пике в единицы.
- Цена: ещё контейнер, ещё 256–512 МБ памяти (Redis без `maxmemory` на маленькой машине — классический
  OOM, который убивает Postgres), второй источник правды для тех же данных, новый режим отказа
  (Redis лёг — эндпоинт падает или идёт в Postgres? это надо написать и проверить).

**Лестница, если когда-нибудь упрёмся:** сначала in-process кэш в самом Spring (Caffeine,
`@Cacheable` — десяток строк, ноль контейнеров). Redis оправдан, когда инстансов приложения
**два и более** и им нужен общий горячий кэш. И тогда первыми в него попросятся не переводы, а
счётчики рейт-лимитов (атомарный `INCR` с экспирацией — его родная задача), но они у нас уже
спланированы в Postgres, и механизм лучше держать один.

**Статус:** ✅ решено 26.09.2026 — **Redis не ставим**; кэш переводов, лимиты, счётчики и стрики — в
PostgreSQL. Решение и объяснение — `phase4_server.md` → «Инфраструктура: хостинг, бэкапы, восстановление».

## 6. Отдельный Postgres под словарь — Claude против, но seam оставить

**Вопрос пользователя:** не завести ли под слова свою базу, отдельно от основной, как задел на будущее.

**Позиция Claude:** второй **инстанс** СУБД — это второй контейнер, своя память (резервируется
отдельно и не переиспользуется), свой бэкап, свой апгрейд мажорной версии, свой риск забить диск.
Ради таблицы на ~100 МБ, которая почти только читается. Клиентский сплит `content.db`/`user.db`
вынужденный — его диктует `createFromAsset`; на сервере принуждающей причины нет.

**Задел, который стоит ноль:** держать словарные таблицы в **отдельной схеме** того же Postgres
(`dict.*`) и ввести правило — **никаких JOIN между `dict.` и юзерскими таблицами**. Пока изоляция
на уровне запросов соблюдается, вынос в отдельный инстанс = `pg_dump` одной схемы плюс смена
строки подключения, работа на час в тот день, когда понадобится.

**Триггер реального сплита:** словарный трафик начал влиять на латентность основной БД, либо
словарь захотелось вынести на отдельный узел.

**Статус:** открыт.

## 7. Железо

**Рассматривались два варианта (~2–3 тыс. ₽/мес, названы пользователем):**

| | Вариант A | Вариант B |
|---|---|---|
| CPU | 4 ядра, 3–3.3 ГГц | 6 ядер, 3–3.3 ГГц |
| RAM | 6 ГБ | 12 ГБ |
| Диск | 80 ГБ NVMe | 150 ГБ NVMe |
| Канал | 1 Гб/с | 1 Гб/с |
| Цена | 2 040 ₽/мес | 3 600 ₽/мес |

**Рекомендация Claude — вариант A.** Раскладка памяти под всё, что там будет жить:

```
Postgres (shared_buffers ~1.5 ГБ)       ~2.0 ГБ
Spring Boot JVM (heap 1 ГБ + overhead)  ~1.5 ГБ
Caddy/nginx: сайт + reverse proxy       ~0.05 ГБ
Docker daemon + ОС                      ~0.5 ГБ
────────────────────────────────────────────────
занято ~4 ГБ, свободно ~2 ГБ на page cache
```

Вариант B покупает запас, который не выберется минимум год (~19 000 ₽/год за простаивающую
память), а вертикальный ресайз VPS — десять минут даунтайма в тот день, когда упрёмся.

**Реальный риск на маленькой машине — диск, не RAM.** 80 ГБ забивают неротируемые логи и старые
Docker-образы (Spring-образ 200–300 МБ × двадцать деплоев = 5 ГБ мусора). `logrotate` и
`docker system prune` по крону — с первого дня.

**Образ собирать локально или в CI.** Gradle-сборка Spring-проекта на самой машине съест всю
память и уронит то, что на ней работает.

**Статус:** ✅ решено 26.09.2026 — **вариант A, это тариф Beget VPS** (4 ядра, 6 ГБ, 80 ГБ NVMe, 2 040 ₽/мес,
Россия; Timeweb отброшен — его часто DDoS-ят). Прикидка нагрузки на 1 000 пользователей, раскладка памяти
и «когда расти» — `phase4_server.md` → «Инфраструктура: хостинг, бэкапы, восстановление».

## 8. Контейнеры, сайт, админка

**Вопрос пользователя:** внутри `grammar-server` должен быть сервер + админка, и отдельно проект
сайта — это два разных контейнера или как?

**Предложение Claude — три контейнера на одной машине, нарезанные иначе:**

```
caddy      — TLS, раздаёт сайт (статика), проксирует /api и /admin в app
app        — Spring Boot: API + админка
postgres   — данные, volume наружу, порт наружу не публикует
```

- **Сайт — не контейнер-приложение, а папка статики**, примонтированная в веб-сервер, который и так
  стоит спереди ради TLS. Отдельный контейнер понадобился бы, будь сайт приложением (Next.js, SSR).
  Логин и оплата этого не меняют (см. ниже).
- **Caddy вместо nginx** — сам получает и продлевает сертификаты Let's Encrypt, без certbot, крона
  продления и хука на релоад. Конфиг ~8 строк.
- **Админка — пакет внутри того же Spring**, не отдельное приложение: работает с теми же сущностями
  (`users`, `subscriptions`, `announcements`, `fcm_tokens`), отдельный сервис означал бы второй
  комплект entity/репозиториев к той же базе — Правило №0 на уровне сервисов. Технически:
  контроллеры под `/admin`, Spring Security с одной ролью и паролем из `ADMIN_PASSWORD` (уже в
  env-списке `phase4_server.md`), Thymeleaf для страниц — form-login и сессия из коробки, JS писать
  не придётся. Закрыть панель от интернета — строчка allowlist в Caddy, не отдельный контейнер.
- **Сайт лежит снаружи Spring**, не в `src/main/resources/static/` — иначе правка текста политики
  конфиденциальности превращается в пересборку и передеплой jar.

**В репозитории это выглядело бы так:**

```
grammar-server/            ← один Gradle-модуль, админка — пакет внутри
site/                      ← статика лендинга, НЕ Gradle-модуль, ничего не компилируется
docker-compose.yml
Caddyfile
```

**Что важнее самой нарезки:** данные Postgres на именованном volume (`docker compose down -v` не
должен уносить базу); Postgres в compose через `expose`, а не `ports`; `pg_dump` по крону с
выгрузкой на другой носитель; `mem_limit` каждому сервису; `restart: unless-stopped`.

**Статус:** ✅ **Caddy — решено 26.09.2026** (вместе с тремя контейнерами caddy / app / postgres, см.
`phase4_server.md` → «Инфраструктура: хостинг, бэкапы, восстановление»). Открыт по-прежнему вопрос
разнесения: пользователю не нравится сосуществование бэкенда приложения и сайта на одной машине;
договорились пока делать на одной и вернуться к разнесению, когда вырастем.

## 9. Сайт с логином и оплатой

**Уточнение пользователя:** сайт не чисто статический — на нём можно войти в аккаунт и провести оплату.

**Оценка Claude — второго бэкенда всё равно не появляется:** вход и покупка это `POST /auth/login`
и создание платежа, то есть **те же эндпоинты, что уже есть для приложения**; страница «мой
аккаунт» — это `GET /subscription`. Сайту нужен фронтенд, а не свой сервер.

Про оплату: карта пользователя нашего сервера не касается. Схема YooKassa — фронт жмёт «купить» →
бэкенд создаёт платёж секретным ключом и получает confirmation URL → редирект на страницу
YooKassa → она дёргает наш `POST /webhook/yookassa`. На сервере живут только создание платежа и
приём вебхука.

⚠️ **Расходится с текущим `phase4_server.md`**, где мини-сайт описан как чисто статический лендинг
с юридическими страницами. Про логин и оплату там ничего нет — дописать, когда договоримся.

**Статус:** открыт.

## 10. DDoS и разнесение по машинам

**Опасение пользователя:** если всё живёт на одном сервере, DDoS положит заодно и приложение.

**Ответ Claude — разделение по контейнерам от DDoS не защищает вообще.** Контейнеры изолируют
процессы (один упал — другие живы, `mem_limit` не даёт сожрать чужую память), но делят **один
канал и одни 4 ядра**. Волюметрике безразлично, один там контейнер или пять: пакеты забивают
канал до того, как что-либо доходит до Docker.

**Что защищает на самом деле, по приоритету трат:**

1. **Фильтр впереди** — Cloudflare на бесплатном тарифе или базовая L3/L4-защита хостера.
   Волюметрику съедают у себя. Стоит ноль, настройка ~10 минут. У РФ-хостеров базовая фильтрация
   обычно включена или стоит копейки — **спросить хостера, что входит, до атаки, а не во время**.
2. **Бэкап БД на другой носитель** — защищает от невосстановимого. Приложение и сайт безстейтовые,
   пересобираются за час; базу с оплаченными подписками взять неоткуда.
3. **И только потом разнесение по машинам**, причём выносить надо **БД** (или брать managed
   Postgres), а не сайт: смысл изоляции — уберечь то, что нельзя восстановить. Вынести сайт,
   оставив общую БД, — полумера: логин с сайта всё равно идёт в ту же базу.

Плюс **rate limit на входе** (от долбёжки `/auth/login`) и **авторизация на дорогих ручках** —
единственная, которая стоит живых денег за вызов, это AI, и она уже за JWT/device-id и лимитами.

**Трезво про вероятность:** целенаправленно валят тех, чей простой кому-то выгоден. Реалистичные
сценарии отказа здесь другие и скучнее — свой баг течёт по памяти, краулер долбит сайт, кто-то
нашёл AI-ручку и скриптует её. Все три лечатся `mem_limit`, rate limit и авторизацией.

**Смягчающее обстоятельство, уже заложенное в дизайн:** приложение по плану работает офлайн для
теории и хардкодных упражнений. Падение сервера отключает AI, синк и покупку, но не учёбу — цена
часа простоя низкая.

**Статус:** ✅ **п. 2 (бэкап БД на другой носитель) — решено 26.09.2026:** ночной зашифрованный дамп в
Yandex Object Storage (другая компания, не Beget), хранение 7/4/3, ключ в трёх местах, снимки Beget как
вторая линия, проверка восстановления раз в месяц, алерт в Telegram — `phase4_server.md` →
«Инфраструктура: хостинг, бэкапы, восстановление». Фильтр DDoS впереди — спросить у Beget, что входит
(в чек-листе настройки). Разнесение по машинам — открыт, пользователь хочет вернуться к нему при росте.

## 11. Рейт-лимит на словарный эндпоинт

**Позиция пользователя:** бесплатным поменьше, чтобы упирались в фичу; платным заметно больше.

**Уточнение Claude:** при схеме «локальный словарь → кнопка → сервер» до лимита органически почти
никто не дойдёт, так что роль у него скорее **анти-абузная** — чтобы эндпоинт не приспособили как
бесплатное словарное API. Поэтому у Free он может быть довольно щедрым: упираться будет только тот,
кто долбит специально. Слишком маленький лимит ударит по сценарию «зажал → локальный перевод не
устроил → нажал кнопку → лимит исчерпан», а это раздражение, а не мотивация к покупке.

**Статус:** открыт, конкретные числа не обсуждались.

## 13. Мониторинг, алерты и Telegram-бот

> ⚠️ Как и весь файл — **не решения**. Направление пользователю нравится, конкретика не выбрана,
> к каждому пункту вернуться при старте Фазы 4.

### Telegram-бот — единственное, что пользователь назвал решённым

Роль шире, чем просто «сервер упал». Две функции:

1. **Алерты.** Пингер дёргает `/actuator/health` раз в минуту; ответ не `UP` → сообщение в телегу.
   ⚠️ **Пингер обязан жить СНАРУЖИ нашего сервера.** На той же машине он умрёт вместе с ней, и
   сообщение отправить будет некому. Либо внешний сервис (UptimeRobot и похожие умеют слать в
   телегу без единой строчки кода), либо крон где-то ещё.
2. **Сводка по запросу** — пользователь жмёт кнопку в боте и получает: сколько человек пользовалось
   (за день/неделю), живы ли все сервисы, что с базой. По сути — витрина поверх тех же данных,
   что уже собираются для админки и статистики.

**Статус:** бот будет точно. Набор кнопок и состав сводки — не проговаривались.

### Ловля и сохранение исключений — пользователь хочет, инструмент не выбран

Смысл: чтобы ошибка сама прилетала **с текстом и стеком**, а не обнаруживалась походом в логи после
жалобы. Два пути, оба не требуют своих контейнеров:

| | Плюс | Минус |
|---|---|---|
| **Sentry** (бесплатный тариф) | одна зависимость в приложении; группирует одинаковые ошибки, показывает стек-трейс и частоту | сторонний сервис, данные уезжают наружу |
| **Свой logback-аппендер** ERROR → телега | полностью свой, ~30 строк | без группировки: один баг у ста пользователей = сто сообщений |

**Статус:** направление принято, выбор инструмента открыт.

### Grafana — «на всякий случай», по словам пользователя не точно

⚠️ Частая путаница: **Grafana сама логи не собирает и метрики не хранит** — она их только рисует.
Чтобы получилось «нормально мониторить», нужен стек из трёх частей:

| Компонент | Роль |
|---|---|
| **Prometheus** | ходит к `/actuator/prometheus` и копит цифры: память, нагрузка, латентность ручек |
| **Loki** | собирает и хранит строки логов из Docker |
| **Grafana** | показывает и графики, и поиск по логам в одном окне |

**Цена самохоста:** +3 контейнера, ~0.5–1 ГБ памяти. В раскладке п. 7 свободными оставались ~2 ГБ —
то есть половину запаса съест наблюдение за сервером, на котором пока нечего наблюдать. Плюс
Prometheus и Loki со временем забивают диск историей, а диск на маленькой машине и так узкое место.

**Ленивая альтернатива:** Grafana Cloud с бесплатным тарифом — хранение и интерфейс у них, на нашей
машине только маленький агент. Наши 6 ГБ не трогаются, настройка проще. Если графики понадобятся,
идти этим путём, а не поднимать три контейнера у себя.

**Триггер, когда заводить вообще:** появился вопрос, на который отвечают именно графики («почему по
вечерам тормозит», «сколько JVM реально ест под нагрузкой»). До этого графики посмотрят из
любопытства пару раз.

**Статус:** отложено, пользователь пометил как «не точно».

### Логи — как смотреть, пока ничего из этого нет

```
docker compose logs -f app           # живой поток
docker compose logs --tail 500 app   # последние строки
```

Работает из коробки, настраивать нечего. Для одного разработчика и небольшой базы пользователей
этого хватает надолго.

⚠️ **Actuator логи НЕ показывает.** `/actuator/loggers` умеет только менять уровень логирования на
лету (включить DEBUG на один пакет, воспроизвести баг, выключить) — без перезапуска приложения.
Содержимого логов там нет.

### Безопасность при открытии метрик

Сейчас в `application.yaml` наружу открыт только `health`. Когда для Prometheus понадобится открыть
`/actuator/prometheus` — **остальное наружу не выставлять**: `/actuator/env` печатает переменные
окружения, а там `JWT_SECRET`, ключ модели, `YOOKASSA_SECRET_KEY`, `DATABASE_URL`, `ADMIN_PASSWORD`.
Открытый `env` на публичном сервере — это не утечка конфига, а полная компрометация одним GET.
Закрывать `/actuator/**` (кроме health) allowlist'ом по IP в Caddy либо админской авторизацией.

### Предлагаемый порядок

1. **Сразу с появлением сервера** — внешний пингер на `/actuator/health` → телега. Бесплатно, минут десять.
2. **С появлением живых пользователей** — ловля исключений (Sentry либо свой аппендер).
3. **Всегда под рукой** — `docker compose logs` для ручного разбора.
4. **Графики** — по триггеру выше, и скорее облаком, чем своими контейнерами.

### Про админку

Показывать состояние сервера в веб-панели можно, но пользы немного: страницу надо не забыть открыть,
а алерт приходит сам. Админку держать под дела (пользователи, подписки, объявления, рассылки), за
здоровьем сервера пусть следят бот и уведомления.
