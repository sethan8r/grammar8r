# Уроки из Words8r — установки для разработки Grammar8r

> **Кому адресован файл:** мне самому (Claude) при написании кода Grammar8r.
> **Зачем:** в Words8r был проведён полный аудит кода. Приложение работает, но содержит системные
> костыли и дублирование. Grammar8r — продакшен-продукт с монетизацией, в разы больше по контенту
> и функциональности. Ошибки ниже повторять **запрещено**. Перед написанием любого нового модуля —
> сверяться с этим файлом.
>
> Words8r переписывается с нуля внутри Grammar8r (Фаза 2). Функционал сохраняется 1:1,
> архитектура — новая. `words8r_plan.md` — референс только по поведению, НЕ по коду.

---

## Планка качества — как я обязан писать Grammar8r

Grammar8r — не пет-проект и не «приложение одного разработчика». Это продакшен-продукт
с подпиской, который должен выглядеть и ощущаться на уровне Duolingo, и быть написан так,
как будто над ним работает большая опытная команда сеньоров. Это значит:

- **Я пишу код как сеньор в команде, а не как единственный автор.** Каждый файл должен быть
  понятен человеку, который видит его впервые: предсказуемая структура, говорящие имена,
  никаких «я-то знаю, что тут имелось в виду». Если решение требует пояснения — значит,
  оно либо слишком хитрое, либо нужен комментарий о неочевидном ограничении.
- **Сначала best practice, потом код.** Перед каждой задачей проверяю: как это делает
  официальный Android-гайд / Material3 / крупные продакшен-приложения. Готовый Jetpack-API
  всегда побеждает самописное решение. «Работает же» — не аргумент; аргумент — «так делают
  в продакшене и это переживёт три года развития продукта».
- **Дизайн до кода.** Для каждой фичи сначала продумывается модель данных, состояния и
  границы модулей, и только потом пишется UI. В Words8r было наоборот — отсюда god-файлы
  и логика в композаблах.
- **Качество как у Duolingo — это в первую очередь невидимые вещи:** мгновенный отклик UI,
  ни одного фриза на main thread, корректное поведение при повороте/смерти процесса/офлайне,
  анимации через стандартные API (поэтому они плавные), состояние, которое невозможно
  «сломать» быстрыми тапами. Полировка UX — не последний этап, а свойство архитектуры.
- **Масштаб закладывается сразу.** Контента будет много (десятки тем, сотни микротем, тысячи
  упражнений) — значит, никаких захардкоженных списков, всё данные-ориентированное: контент
  в БД/assets, UI рендерит любую структуру. Добавление темы или типа упражнения не должно
  требовать правок по десяти файлам.
- **В этом проекте легко увязнуть** — контента и функциональности очень много. Защита от
  этого: маленькие модули с чёткими границами, один источник правды для каждой сущности,
  тесты на доменную логику. Каждый срезанный угол сегодня — неделя долгов завтра.
- **Никаких «потом исправим».** Костыль, попавший в main, становится фундаментом следующей
  фичи. Если правильное решение требует обсуждения — останавливаюсь и обсуждаю с
  пользователем, как предписывает CLAUDE.md, а не вставляю времянку.

## Правило №0 — главный вывод аудита

Почти все проблемы Words8r — одна и та же ошибка в разных формах: **знание о предметной области
не имеет единственного источника правды**. Диапазоны повторений существовали в 4 местах, режим
перевода — строками в 5 файлах, логика проверки ответа — в двух ViewModel'ах, свайп-карточка —
в двух Composable по 370 строк. Каждая фича добавлялась копированием соседней.

**Установка:** прежде чем писать код, спросить себя: «эта сущность/логика уже где-то существует?»
Если да — выносить и переиспользовать, а не копировать. Если сущность доменная (тип упражнения,
уровень темы, режим перевода) — она обязана быть типом (enum / sealed class), а не строкой.

## 1. Архитектура

### 1.1. Dependency Injection — Hilt с первого коммита
**Как было:** каждый из 9 ViewModel'ов сам вызывал `WordDatabase.getInstance(application)` и
собирал себе репозитории (11 точек создания БД). Все ViewModel — `AndroidViewModel` только ради
контекста. Юнит-тестирование невозможно: зависимости не подменяются.

**Как надо:**
- Hilt: `@HiltViewModel`, репозитории и DAO — через `@Inject`, БД — `@Singleton` в `@Module`.
- ViewModel'ы — обычные `ViewModel`. Контекст в ViewModel не попадает вообще; если нужны
  ресурсы/prefs — инжектится репозиторий/обёртка, а не Context.
- Любой класс с логикой должен быть тестируем без Android (чистый Kotlin + подменяемые зависимости).

### 1.2. Слои: логика живёт в domain, а не в ViewModel
**Как было:** репозитории — анемичные прокси DAO (1 строка на метод, ноль логики), при этом
доменная логика (выбор слов по диапазону, взвешенный рандом пулов слов, расчёт периодов
статистики) лежала внутри ViewModel'ов по 18–19 КБ.

**Как надо:**
- ViewModel = только UI-state и реакции на действия пользователя. Толстый ViewModel (> ~300 строк) —
  сигнал, что в нём застряла доменная логика.
- Алгоритмы (SRS-планировщик, подбор дистракторов, взвешенный выбор слова, агрегация статистики) —
  отдельные классы в domain-слое (use case / контроллер), покрываемые юнит-тестами.
- Репозиторий имеет право на существование, только если несёт логику (маппинг, объединение
  источников, транзакции). Прокси «метод-в-метод» не писать — инжектить DAO напрямую либо
  наполнять репозиторий смыслом.

### 1.3. Общая механика — через композицию, а не копипасту
**Как было:** `LearnViewModel` и `LearnNewWordsViewModel` дублировали ~150 строк: `checkAnswer`,
`selectAnswerMethod`, `checkGridAnswer`, `buildGridOptions`, `getHint`, `showAnswer`,
`proceedAfterThreeStrikes`, `clearAnimation` + одинаковые поля state. Копии уже разъехались:
`getHint` в одном классе считал лимит через state, в другом — через локальную переменную.

**Как надо:** повторяющаяся механика («ответ на карточку»: попытки, методы ввода, подсказки,
сетка вариантов) — отдельный класс-делегат со своим `StateFlow`, который ViewModel'ы включают
композицией. В Grammar8r это критично: 14 типов хардкодных упражнений + AI-упражнения обязаны
разделять общую механику (проверка, фидбек, попытки, избранное), различаясь только контентом.

## 2. Типизация — запрет на stringly-typed код

**Как было:**
- Режим перевода — строки `"RU_TO_EN"` / `"EN_TO_RU"` в 5 файлах (37 вхождений).
- Диапазоны повторений `"1-3"`, `"4-6"`, `"problem"`, `"all"` — строки, а знание о них
  продублировано в 4 местах: ViewModel (строка → SQL-запрос), два места маппинга строка → заголовок
  (две независимые копии!), захардкоженный список кнопок в UI.
- Направление свайпа — `"left"` / `"right"`.
- 7 копий одного DAO-запроса (`countQRep1to3` … `countQRepOver26`), продублированных полями
  ещё в репозитории и двух ViewModel'ах.

**Как надо:**
- Любое конечное множество значений — enum или sealed class. Строки в `when` по доменным
  значениям — запрещены.
- Доменная сущность определяется ОДИН раз со всеми атрибутами. Пример: бакеты повторений —
  `enum class RepetitionBucket(val from: Int, val to: Int?, val label: String)`; запрос —
  один параметризованный метод DAO `countByQRepRange(from, to)`; UI строит кнопки итерацией
  по `RepetitionBucket.entries`. Добавление бакета = одна строка.
- В Grammar8r таких множеств много: типы упражнений, уровни тем, статусы прохождения,
  тиры подписки, режимы AI-ввода (`FREE_WRITE`/`FILL_BLANKS`) — все строго типами.
  В БД/JSON они сериализуются строкой — конвертация в тип на границе data-слоя, один раз.

## 3. Навигация

**Как было:** роуты — конкатенация строк (`"wordly_result/$won/$wordId/$attempts/$length"`),
на принимающей стороне — ручной парсинг `arguments?.getString(...)?.toLongOrNull() ?: 0L`
с молчаливыми дефолтами. Видимость нижней панели — чёрный список роутов через
`!startsWith(...)` + флаг `learnSessionActive`, прокинутый колбэком из вкладки наверх
(сессия была состоянием внутри вкладки, а не экраном).

**Как надо:**
- Type-safe navigation (Navigation Compose 2.8+): роуты — `@Serializable` data class/object,
  аргументы типизированы, парсинг исчезает.
- Видимость панели — белый список: панель есть только у 4 корневых вкладок, всё остальное
  полноэкранно по умолчанию. Новый экран не может «случайно» получить навбар.
- Полноэкранные состояния (активная сессия обучения) — отдельные роуты, а не локальный
  стейт вкладки с колбэком наверх.

## 4. UI / Compose

### 4.1. Никаких самописных жестов там, где есть API
**Как было:** свайп карточки — ручной `dragX` + `Animatable` + `detectDragGestures` +
`pendingSwipe` + `flyOutAngle`, и весь этот механизм скопирован в два файла по ~370 строк
(`CardContent.kt` и `TypingContent.kt` совпадают на ~90%).

**Как надо:**
- Жесты с позициями-якорями — `AnchoredDraggable`. Смахивание — `SwipeToDismissBox`.
  Появление/исчезновение — `AnimatedVisibility`. Ручные `Animatable`-машины — только если
  официального API нет, и тогда по протоколу из CLAUDE.md (2 правильных варианта + почему
  не подходят + ждать одобрения).
- Повторяющийся UI-паттерн (свайп-карточка слова, карточка упражнения, прогресс-шапка) —
  один параметризованный компонент в `ui/components/`, а не копия на каждый экран.

### 4.2. Размер файлов
**Как было:** `DictionaryScreen.kt` — 39 КБ / ~1000 строк (экран + 6 подкомпонентов + оверлей
редактирования), `SelectionContent.kt` — 26 КБ.

**Как надо:** один файл = один экран ИЛИ один компонент. Ориентир — до ~300–400 строк;
больше — сигнал к разбиению. Экраны тонкие: собирают компоненты и подключают ViewModel.

### 4.3. Строковые ресурсы
**Как было:** `stringResource` не используется ни разу — весь текст захардкожен в композаблах,
надписи вроде «ЕЩЁ РАЗ» повторяются в 4 местах.

**Как надо:** `strings.xml` с первого экрана. Это даёт: локализацию в будущем, отсутствие
дублей, единое место для проверки тона «на Вы». Динамический контент (теория, упражнения) —
из БД; интерфейсные строки — только из ресурсов.

### 4.4. События ViewModel → UI (анимации, навигация)
**Как было:** ViewModel ставил флаг `cardAnimation` + `threeStrikes`, UI проигрывал анимацию
в `LaunchedEffect`, потом UI же вызывал `clearAnimation()` и `proceedAfterThreeStrikes()` —
то есть продвижение бизнес-логики зависело от того, доживёт ли `LaunchedEffect` до конца.
Танец скопирован в оба Content-файла.

**Как надо:** одноразовые события — через `Channel`/`SharedFlow` (events), либо state с явным
подтверждением. Решения «что происходит после третьей ошибки» принимает ViewModel; UI только
отображает. Анимация не должна быть звеном в цепочке бизнес-логики.

### 4.5. Туториалы / спотлайт
**Как было:** 17 ручных `onGloballyPositioned` с прокидыванием `Offset` через state для каждой
подсвечиваемой кнопки.

**Как надо:** если в Grammar8r будет онбординг со спотлайтом — один `Modifier.spotlightTarget(key)`,
регистрирующий координаты в общем реестре. Замер координат пишется один раз.

## 5. Данные

### 5.1. Настройки — DataStore, а не зоопарк SharedPreferences
**Как было:** 6+ отдельных prefs-файлов (`hint_prefs`, `stats_prefs`, `tutorial_prefs`,
`notification_prefs`, `wordly_prefs`, `pending_words`), каждый со своим самописным враппером,
причём три из них лежали в пакете `viewmodel`.

**Как надо:** Jetpack DataStore (Preferences или Proto), обёртки — в `data/preferences`,
доступ — через инжектируемый класс с типизированными `Flow`. Деление — по доменам, без
размножения файлов на каждую мелочь.

### 5.2. Данные обучения — в БД, не в prefs
**Как было:** очередь недоученных слов (`pending_word_ids`) хранилась в SharedPreferences —
данные домена обучения жили мимо БД и мимо бекапа.

**Как надо:** всё, что описывает прогресс/состояние обучения пользователя — таблицы Room.
Prefs/DataStore — только настройки поведения приложения. (Критерий: «должно ли это пережить
перенос на новый телефон вместе с прогрессом?» Если да — БД.)

### 5.3. Room
- `exportSchema = true` + схемы в VCS + автотесты миграций (`MigrationTestHelper`). В Words8r
  схемы не экспортировались — миграции не тестировались.
- Миграции писать честно с первого релиза (в Words8r это было сделано правильно — сохранить).
- `OnConflictStrategy.REPLACE` на пользовательских insert не использовать бездумно: молча
  перезаписывает строку при конфликте. Для пользовательских данных — `ABORT`/`IGNORE` + явная
  обработка конфликта.
- Серии однотипных запросов — параметризовать, а не копировать (см. правило №2).
- Агрегатную статистику считать SQL-агрегатами (`GROUP BY`), а не 20 последовательными
  suspend-запросами из ViewModel, как было в `StatisticsViewModel.loadStats`.

### 5.4. Даты и время — java.time
**Как было:** ручная математика на `Calendar` (полночь, начало недели, циклы по 7/30 дней)
продублирована в 4 местах: MainActivity, StatsPrefs, StatisticsViewModel, воркеры.

**Как надо:** `java.time` (`LocalDate`, `ZonedDateTime`, `Duration`) + один утилитный класс
для доменных периодов (день/неделя/цикл стрика). Никакого `Calendar` в новом коде.

## 6. Надёжность и релиз

### 6.1. Крэш-хендлер
**Контекст из Words8r:** был реальный случай — крэш после миграции снёс БД, и AppMetrica его
НЕ поймала. Поэтому локальное сохранение крэша + блокирующий экран ошибки с отчётом — это
**осознанное и оправданное** решение, его сохранить.

**Что было костылём:** запись отчёта в clipboard прямо из uncaught-хендлера с
`Thread.sleep(300)` для гонки с main looper.

**Как надо:** в хендлере — только синхронная запись файла (это надёжно) + проброс в исходный
хендлер. Копирование в буфер — кнопкой «Скопировать отчёт» на экране ошибки при следующем
запуске, где UI живой и clipboard работает гарантированно.

### 6.2. Фиче-флаги вместо TODO-комментариев
**Как было:** `val isSubscriber = true // TODO: в релизе false` и закомментированный кулдаун
подсказок — мина: забыл раскомментировать → платная фича бесплатна в проде.

**Как надо:** поведение, различающееся между dev и релизом, — только через `BuildConfig`-поля
или удалённый конфиг. Код с «раскомментировать перед релизом» не пишется вообще. Для Grammar8r
с подписками и AI-лимитами это критично: проверка тира/лимита — единый инжектируемый
`EntitlementsProvider`, в debug-сборке подменяемый, а не комментарии.

### 6.3. Аналитика
**Как было:** строки событий AppMetrica разбросаны по ViewModel'ам.

**Как надо:** один объект/интерфейс `Analytics` с типизированными методами
(`fun lessonStarted(mode: TranslationDirection)`), имена событий — константы в одном файле.
Инжектится, в тестах подменяется no-op'ом.

### 6.4. Мёртвый код
**Как было:** неиспользуемая перегрузка `exportTable`, закомментированные блоки «на потом».

**Как надо:** мёртвый код удаляется сразу — история есть в git. (Исключение по правилам
проекта: закомментированные строки пользователя не трогать без запроса.)

## 7. Что в Words8r было сделано ХОРОШО — перенести идеи

- **Бекап через пересечение колонок** (`FileRepository`): экспорт/импорт по общим колонкам
  старой и новой схемы → прямая и обратная совместимость бекапов. Дизайн сохранить;
  улучшить только обработку ошибок (sealed result вместо `throw Exception("текст для UI")`).
- **`AppInitState` (Loading/Ready/Error)** с экраном критической ошибки и retry до показа UI.
- **Честные миграции Room** без destructive fallback.
- **Чистые функции проверки ответа** (`AnswerChecker`) — образец того, как выносить логику:
  без состояния, без Android, легко тестировать.
- **Двухпроходный алгоритм Wordly** (корректная обработка дублей букв) — переносить как есть.
- **TTS через `IdleHandler`** после первого кадра Compose (гонка с ICU) + правило LF для
  `tokens.txt` — задокументированное решение реальной проблемы, сохранить вместе с
  `.gitattributes`.

## 8. Чек-лист перед каждым новым модулем Grammar8r

1. Зависимости приходят через Hilt? (`getInstance`/`new` внутри ViewModel — стоп.)
2. Доменные значения — типы, а не строки? Источник правды — один?
3. Эта логика/UI уже существует где-то? Выносим и переиспользуем, а не копируем?
4. Есть ли официальный Jetpack/Material3 API для этой задачи? (Проверить ДО написания своего.)
5. Логика тестируема без Android? ViewModel тонкий?
6. Все интерфейсные строки — в `strings.xml`, на «Вы»?
7. Данные прогресса — в Room (попадут в бекап/синк), настройки — в DataStore?
8. Файл не разросся за ~400 строк?
9. Нет «TODO раскомментировать перед релизом»? Dev/prod-различия — через BuildConfig?
10. События аналитики — через общий `Analytics`?
