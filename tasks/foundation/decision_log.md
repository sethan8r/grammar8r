### 2026-06-14 · JSON-поля хранятся как String, разбор — в domain-маппере (не Room TypeConverter)
- **Контекст:** `GrammarCard.theory` (массив блоков), `examples`, `clarificationOptions`, а также
  `options/items/rows/pairs/words/...` в таблицах упражнений и `topicsVisited` в DailyStats.
- **Варианты:** (а) Room `@TypeConverter` String↔типизированная модель прямо в Entity;
  (б) Entity держит сырой `String` (колонка TEXT), типизированный разбор делает domain-маппер
  при чтении Entity→domain-модель.
- **Выбор:** (б). TypeConverter оставлен ТОЛЬКО для enum↔String.
- **Почему:** колонка в обоих вариантах TEXT (на identity hash content.db не влияет), но (б)
  не пускает kotlinx.serialization в data-слой и держит границу data→domain чистой; разбор
  блоков — это уже задача читалки (Шаг E), а не схемы. Entity остаётся «глупым» отражением строки.
- **Уверенность:** средняя — Fable пусть подтвердит, что разбор JSON в маппере (а не в конвертере)
  ему ок с точки зрения границ слоёв.
- **Обратимость:** средняя — перенос разбора в TypeConverter не трогает схему БД (тип колонки тот же),
  меняет только где живёт сериализация.

### 2026-06-14 · Между БД нет FK; внутри content.db FK тоже не ставим — только индексы
- **Контекст:** связи `categoryId`/`topicId`/`microtopicId`/`cardId` и т.п.
- **Варианты:** (а) `@ForeignKey` внутри content.db (между БД нельзя — это правило db_schema);
  (б) только `@Index` на FK-колонках, без `@ForeignKey`.
- **Выбор:** (б) везде.
- **Почему:** content.db сидируется из JSON скриптом (Шаг C) — `@ForeignKey` потребовал бы строгого
  порядка вставки и падал бы на любой осиротевшей ссылке, что противоречит правилу «осиротевшее
  игнорируется». Целостность контента гарантируется на этапе авторства (id_report.py), а не БД.
  Индексы под выборки оставлены.
- **Уверенность:** высокая.
- **Обратимость:** средняя — добавить `@ForeignKey` = bump версии (меняется identity), но для
  read-only content.db это дёшево (destructive fallback).

### 2026-06-14 · ⚠️ ПЕРЕСМОТР Шага B: MultipleChoiceExercise PK → составной (id, choiceType)
- **Контекст:** при первом сидинге `json_to_db.py` упал на `UNIQUE multiple_choice_exercises.id`.
  Расследование: в сиде `id=1` существует трижды — как `CHOICE`, `FORWARD_CHOICE`, `REVERSE_CHOICE`
  (это РАЗНЫЕ упражнения). Канон ID (`id_report.py`, `exercise_templates.md`) ведёт три отдельных
  трека `MultipleChoice·CHOICE/·FORWARD_CHOICE/·REVERSE_CHOICE` — т.е. истинный ключ строки —
  пара `(id, choiceType)`. Шаг B зафиксировал одиночный `@PrimaryKey id` (ошибка).
- **Варианты:** (а) подогнать данные под одиночный PK — переразметить сотни упражнений, сломать
  канон; (б) исправить схему под канон — составной PK `(id, choiceType)`.
- **Выбор:** (б). Entity: `@Entity(primaryKeys = ["id","choiceType"])`. DAO `getMultipleChoice`
  теперь принимает `(id, choiceType)` (раньше `WHERE id=:id` вернул бы случайную из 3 строк —
  латентный баг). Маппинг `HardcodedExerciseType.{MULTIPLE_CHOICE→CHOICE/…}` — задача Шага F.
- **Почему:** источник правды по распределению ID — канон, и он сознательно на паре. Все остальные
  21 таблица проверены — глобально уникальны по `id` (полная сверка всех 5 сидов).
- **Уверенность:** высокая (3 независимых подтверждения: коммент Entity, id_report, exercise_templates).
- **Обратимость:** схема ре-экспортирована (новый identityHash `10739e65a00ee7e3480a765fb3cbdf0a`),
  версия НЕ бампалась (content.db не выпущена, user.db не затронут). Откат = вернуть PK + ре-экспорт.

### 2026-06-14 · identity content.db: пишем room_master_table + PRAGMA user_version в файл
- **Контекст:** Room при `createFromAsset` должен открыть БД без пересоздания/миграции.
- **Варианты:** (а) положиться на сравнение Room'ом фактической структуры (TableInfo) с Entity;
  (б) записать в файл `room_master_table(id=42, identity_hash)` + `PRAGMA user_version` из схемы.
- **Выбор:** (б). При совпадении хеша и версии Room открывает файл вообще без валидации схемы.
- **Почему:** ⚠️ без `user_version` (=0) Room решит, что нужна миграция 0→1, не найдёт её и по
  destructive fallback СОТРЁТ засиданные таблицы. С верным hash+version — детерминированное открытие.
  identity hash и version берутся ИЗ экспортированной схемы, руками не дублируются.
- **Уверенность:** высокая. **Обратимость:** тривиальная (правка скрипта).

### 2026-06-14 · CREATE TABLE/индексы — из createSql схемы; вставка по пересечению колонок
- **Контекст:** как генерировать DDL и вставлять строки, чтобы исключить расхождение с Entity.
- **Выбор:** DDL — из `createSql` каждой entity (плейсхолдер `${TABLE_NAME}` → имя). Вставка:
  колонки = пересечение ключей JSON-строки с колонками таблицы → `INSERT (cols) VALUES (?)`.
- **Почему:** генерация DDL руками = риск разойтись по типу/NOT NULL/порядку (=краш identity).
  Пересечение колонок само закрывает `card_exercise_index` без `id` (autoincrement) и пропущенные
  nullable-поля; отсутствие NOT NULL-колонки = громкое падение (ловим неполный сид).
- **Уверенность:** высокая. **Обратимость:** тривиальная.

### 2026-06-14 · Gradle: generateContentDb mustRunAfter ksp, merge*Assets dependsOn него
- **Контекст:** схему пишет `ksp<Variant>Kotlin` при компиляции; БД строится ИЗ схемы. Первая

- **Уверенность:** средняя — в CR работает (content.db в APK). Fable пусть глянет, не лучше ли
