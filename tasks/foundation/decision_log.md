### 2026-06-14 · JSON-поля хранятся как String, разбор — в domain-маппере (не Room TypeConverter)
- **Контекст:** `GrammarCard.theory` (массив блоков), `examples`, `clarificationOptions`, а также
  `options/items/rows/pairs/words/...` в таблицах упражнений и `topicsVisited` в DailyStats.
- **Варианты:** (а) Room `@TypeConverter` String↔типизированная модель прямо в Entity;
  (б) Entity держит сырой `String` (колонка TEXT), типизированный разбор делает domain-маппер
  при чтении Entity→domain-модель.
- **Выбор:** (б). TypeConverter оставлен ТОЛЬКО для enum↔String.
- **Почему:** колонка в обоих вариантах TEXT (на identity hash content.db не влияет), но (б)
  не пускает kotlinx.serialization в data-слой и держит границу data→domain чистой; разбор
  блоков — это уже задача читалки (Шаг E), а не схемы. Entity остаётся «глупым» отражением строки.
- **Уверенность:** средняя — Fable пусть подтвердит, что разбор JSON в маппере (а не в конвертере)
  ему ок с точки зрения границ слоёв.
- **Обратимость:** средняя — перенос разбора в TypeConverter не трогает схему БД (тип колонки тот же),
  меняет только где живёт сериализация.

### 2026-06-14 · Между БД нет FK; внутри content.db FK тоже не ставим — только индексы
- **Контекст:** связи `categoryId`/`topicId`/`microtopicId`/`cardId` и т.п.
- **Варианты:** (а) `@ForeignKey` внутри content.db (между БД нельзя — это правило db_schema);
  (б) только `@Index` на FK-колонках, без `@ForeignKey`.
- **Выбор:** (б) везде.
- **Почему:** content.db сидируется из JSON скриптом (Шаг C) — `@ForeignKey` потребовал бы строгого
  порядка вставки и падал бы на любой осиротевшей ссылке, что противоречит правилу «осиротевшее
  игнорируется». Целостность контента гарантируется на этапе авторства (id_report.py), а не БД.
  Индексы под выборки оставлены.
- **Уверенность:** высокая.
- **Обратимость:** средняя — добавить `@ForeignKey` = bump версии (меняется identity), но для
  read-only content.db это дёшево (destructive fallback).

## Аудит Fable (2026-07-02) — точечные правки по итогам ревью фундамента

### 2026-07-02 · Правки аудита: портрет-лок, отмена диалога повтора, дерандж MATCHING, null вместо -1
- **Контекст:** Fable провёл аудит provisional-участков (см. notes_for_fable). Архитектурных ошибок
  не найдено, движок и читалка подтверждены. Внесены точечные правки:
  1. **Портрет-лок в манифесте** (`screenOrientation="portrait"`). Причина: drag-задания
     (WORD_ARRANGEMENT/CATEGORIZATION) держат состояние сборки в локальном стейте рендерера — поворот
     пересоздаёт композицию, поле пустеет, а `answer` во VM переживает → «Проверить» активна при
     визуально пустом поле. Лок закрывает весь класс проблемы одной строкой (продуктово портрет и так
     единственный сценарий).
  2. **Диалог повторного прохождения ОТМЕНЁН** (решение пользователя): вход в завершённую микротему
     просто открывает карточки, перепрохождение свободное, статистика write-once не трогается.
     Канон в CLAUDE.md обновлён (заодно исправлена устаревшая ссылка на удалённую
     `UserCardHardcodeStats` → `UserExerciseResult`).
  3. **MATCHING: честный дерандж-шафл** — было `any { != }` (принимал старт, где 4 из 5 пар уже на
     местах), стало `all { != }` × 32 попытки (вероятность фолбэка ~4e-7).
  4. **`CardCompletion.microtopicId: Int?` вместо сентинела `-1`** — случай «карточки нет в content.db»
     (рассинхрон контента, актуально при будущей доставке с сервера) теперь явный в типе: обе точки
     навигации (MainActivity, MicrotopicScreen) обрабатывают null «просто назад, без сводки»;
     в `ProgressRepositoryImpl` — `Log.w` + `TODO(metrics)` на отправку в будущую Analytics.
  5. **Дубли текстов → проверка в deepcheck.py:** рендер MATCHING различает правые ячейки по тексту
     (реванш/дерандж) — дубли ломают показ ответа. Для CATEGORIZATION проверка уже была; добавлена
     для MATCHING (right + left). Компромисс `first { text == right }` теперь безопасен навсегда.
  6. **Токены:** `Dimens.sessionFooterTopGap` (бывш. сырой `20.dp`), `Dimens.arrangementFieldMinHeight`
     (бывш. `100.dp`); дубль `CenteredText` в TheoryScreen заменён общим `CenteredHint` (Правило №0).
- **Уверенность:** высокая. **Обратимость:** высокая (всё точечное, UI/манифест/скрипт проверок).

### 2026-06-14 · identity content.db: пишем room_master_table + PRAGMA user_version в файл
- **Контекст:** Room при `createFromAsset` должен открыть БД без пересоздания/миграции.
- **Варианты:** (а) положиться на сравнение Room'ом фактической структуры (TableInfo) с Entity;
  (б) записать в файл `room_master_table(id=42, identity_hash)` + `PRAGMA user_version` из схемы.

### 2026-06-14 · CREATE TABLE/индексы — из createSql схемы; вставка по пересечению колонок
- **Контекст:** как генерировать DDL и вставлять строки, чтобы исключить расхождение с Entity.
- **Выбор:** DDL — из `createSql` каждой entity (плейсхолдер `${TABLE_NAME}` → имя). Вставка:
  колонки = пересечение ключей JSON-строки с колонками таблицы → `INSERT (cols) VALUES (?)`.
- **Почему:** генерация DDL руками = риск разойтись по типу/NOT NULL/порядку (=краш identity).
  Пересечение колонок само закрывает `card_exercise_index` без `id` (autoincrement) и пропущенные
  nullable-поля; отсутствие NOT NULL-колонки = громкое падение (ловим неполный сид).
- **Уверенность:** высокая. **Обратимость:** тривиальная.

### 2026-06-14 · Ошибки запроса: доменный ApiResult/RequestError; контрактный код ошибок отложен
- **Контекст:** репозитории, ходящие на наш сервер (auth, AI), должны возвращать типизированный
  результат с ошибками (limit_exceeded, ai_error, prompt_not_found, account_banned, unauthorized).
- **Варианты:** (а) `ApiErrorCode` в shared + доменный `RequestError` + маппер сейчас; (б) только
  доменный `ApiResult<T>`/`RequestError` сейчас, контрактный enum кодов + маппер — позже с remote-слоем.
- **Выбор:** (б). `ApiResult<T> = Success|Failure(RequestError)` и `enum RequestError` — в domain/model.

- **Выбор:** жесты (tap + drag) повешены на КОНТЕЙНЕР-обёртку (assembly + pool), а не на чипы. По
  нажатию — хит-тест слова под пальцем (по захваченным центрам/размерам в координатах обёртки),
  дальше таскаем его. Чипы — чистые визуалы, свободно мигрируют пул⟷строка, жест не зависит от их
  жизненного цикла. Оверлей перетаскиваемого чипа — отдельным узлом обёртки с `zIndex` (поверх и поля,
  и пула). Drag МГНОВЕННЫЙ (`detectDragGestures`, без long-press). Принадлежность строке = отпущено
  над полем сборки (`assemblyBounds.contains(pointer)`), иначе — возврат в пул с анимацией
  (`Animatable<Offset>` оверлея, `Durations.dragReturnMs`). Без цветовой подсветки перетаскиваемого.
  Поле сборки стартует с ~2 строк (`heightIn(min=100.dp)`), увеличенный зазор до пула (`spaceXXLarge`).
- **Почему:** единственный надёжный способ DnD между двумя контейнерами в Compose без официального API
  (его нет) — стабильный жест-хост + хит-тест, иначе ломается lifecycle перетаскиваемого. По протоколу
  костылей (CLAUDE), пользователь явно просит это поведение.
- **Уточнения (фидбэк по скринам):** (1) оверлей вынесен СИБЛИНГОМ `ExerciseFrame` (внешний `Box` —
  жест-хост + оверлей, фрейм внутри), чтобы перетаскиваемое слово не обрезалось клипом фрейма и было
  поверх фона; геометрия/жесты в координатах внешнего Box. (2) на месте вставки — видимый слот-индикатор
  (рамка размером со слово: `Background` + `Inactive`, текст alpha 0), а не пустой зазор. (3) результат
  показывает РАМКА ПОЛЯ сборки (заливка+обводка как у варианта REVERSE_CHOICE): верно — зелёная, 2-я
  ошибка (REVEALED) — красная, 1-я ошибка/ввод — нейтральная; слова-чипы остаются обычными. «Правильно:»
  опущено (верхний отступ = нижнему до разделителя объяснения).
- **Уверенность:** средняя — геометрия/ощущения обкатываются, пользователь даёт фидбэк. Известный
  компромисс: drag по пустым местам внутри фрейма не скроллит страницу (жест-хост перехватывает slop) —
  скролл доступен вне фрейма; если мешает — вернёмся. **Обратимость:** высокая (всё в одном UI-файле).

## Шаг F2 — группа «выбор варианта» (2026-06-19)

### 2026-06-19 · Зонтик `Exercise.SingleSelect` — 7 типов на одной механике выбора варианта
- **Контекст:** F2 добавляет ERROR_CORRECTION / CONSTRUCTION_MEANING / DIALOG_RESTORE / FIND_THE_ODD.
  Все они (и 3 трека Choice из F1) — «выбери один вариант из списка, ровно один правильный»; отличаются
  ТОЛЬКО подачей условия (шапкой). Механика ответа (`SingleChoice` + evaluator + рендер вариантов +
  делегат 2 попыток) у них идентична.
- **Варианты:** (а) 4 независимых доменных типа + 4 копии рендера/механики; (б) общий sealed
  sub-interface `SingleSelect(options, explanation, type)`, который реализуют все 7, + один рендерер
  со слотом-шапкой.
- **Выбор:** (б). `Choice` теперь реализует `SingleSelect`; добавлены `ErrorCorrection`/`ConstructionMeaning`/
  `DialogRestore`/`FindTheOdd`. Движок (`ExerciseEvaluator`, VM `refOf`/`prepareForIndex`/`canCheck`,
  рендер-ветка экрана) свёрнут с `is Exercise.Choice` на `is Exercise.SingleSelect` — одна ветка на все 7.
- **Почему:** Правило №0 — механика выбора варианта живёт ровно один раз; добавление родственного типа =
  новый вариант данных + шапка, без дублирования логики/UI. Прямо по плану roadmap F2 («на одном базовом
  компоненте, различие в подаче условия»).
- **Уверенность:** высокая. **Обратимость:** высокая (зонтик — чистый рефактор, типы можно расщепить назад).

### 2026-06-19 · FIND_THE_ODD ложится на «выбери правильный»: лишний элемент → `isCorrect`
- **Контекст:** FIND_THE_ODD семантически «выбери ЛИШНИЙ», данные — `items[{text, isOdd}]`, а не `options`.
- **Варианты:** (а) отдельная механика «выбор лишнего» (свой answer/evaluator); (б) маппить лишний элемент

### 2026-06-19 · ERROR_CORRECTION multi-correct: evaluator по выбранному, reveal подсвечивает все верные
